# 2026-03-11 (113th TC39 Meeting, Day 2)

## Temporal for Stage 4

- wiki: [Temporal](../../proposals/temporal.md)
- slide: [link](https://ptomato.name/talks/tc39-2026-03/)
- [PFC](../../people/PFC.md) asked for Stage 4 for [Temporal](../../proposals/temporal.md). It entered Stage 3 in 2021 (before Stage 2.7 existed), and they looked back over a long Stage 3 in which feedback from the polyfill and from implementations improved it.
- They showed that the Stage 4 entrance criteria are met. test262 has about 5,000 tests (about 10% of the suite). Firefox, the V8 line, and Ladybird are about 100% conformant, and several implementations have shipped unflagged. There are PRs for both ECMA-262 and ECMA-402, and the editors have looked at them.
- [MF](../../people/MF.md) presented three options for how to publish the spec text: (1) include it in ECMA-262 as it is, (2) a separate page (ECMA-262-2), (3) a separate standard (ECMA-4xx) with its own TG and editor group. The weight of the committee supported "keep it integrated in ECMA-262 for now," and was cool on a dedicated TG.
- Conclusion: [Temporal](../../proposals/temporal.md) advanced to Stage 4. For now there will be neither a separate spec document nor a dedicated TG. Within a year, check whether the premises still hold ([NRO](../../people/NRO.md) owns the follow-up).

## Import Text for stage 2.7 or 3

- wiki: [Import Text](../../proposals/import-text.md)
- slide: [link](https://docs.google.com/presentation/d/1mbkpHjqihHBx6rp07Snb8uB8XevJk7jz2xPSyQppSjE/edit?usp=sharing)
- [EAO](../../people/EAO.md) asked for Stage 2.7 and further advancement for a new import-attribute value `type: "text"` (import a file as a string). Most of the spec lives on the HTML / Fetch / CSP side, and there are PRs for test262 and WPT. Bun has it unconditionally. Deno has it under `--unstable-raw-imports`.
- The only open item was PR #10, which describes the input of the `CreateTextModule` abstract operation as a string value that "should represent textual data." Around importing non-textual data (WASM, JPEG, and so on) as text, [SFC](../../people/SFC.md) argued for a stronger constraint (`must`, or a definition of human-readable) from a "good strings / bad strings" point of view. [NRO](../../people/NRO.md), [RGN](../../people/RGN.md), and [KM](../../people/KM.md) opposed that, and it was settled that defining that behavior is HTML's job.
- PR #10 was merged, reflecting [MF](../../people/MF.md)'s editorial suggestion. The stage 2.7 reviewer [JHD](../../people/JHD.md) also approved it.
- Conclusion: after merging PR #10, it advanced continuously through Stage 2.7 to Stage 3.

## Intl Unit Protocol for Stage 2

- wiki: [Intl Unit Protocol](../../proposals/intl-unit-protocol.md)
- slide: [link](https://docs.google.com/presentation/d/1ECuRD0MU6-Z5DzBJaOi5W3u7f2kf_PZYZU9cXjg5Ock/edit?slide=id.p#slide=id.p)
- [SFC](../../people/SFC.md) presented, for Stage 2, a proposal that introduces an options bag for passing "a number and a unit as a pair" to Intl number format's format function. That gives a protocol-like place to hand data that userland types such as [amount](../../proposals/amount.md) can implement.
- Changes since Stage 1: the field name moves from number to value (number / BigInt / string, and [decimal](../../proposals/decimal.md) in the future), and currency is renamed to unit. Opinions were invited on whether the proposal name should be "[Intl Unit Protocol](../../proposals/intl-unit-protocol.md)" or "Intl NumberFormat options bag."
- At Stage 2 the continuing questions are (1) how far conversion availability is a blocking condition, and (2) web compatibility. [RGN](../../people/RGN.md) and [ACE](../../people/ACE.md) volunteered as Stage 2.7 reviewers.
- Conclusion: approved as Stage 2.

## Intl Energy Units Stage 1 Update

- wiki: [Intl Energy Units](../../proposals/intl-energy-units.md)
- slide: [link](https://docs.google.com/presentation/d/1iwknifQLEIA42KIoveoNLrRZlhEitZQ_JTKADP20rMA/edit?slide=id.p#slide=id.p)
- [SFC](../../people/SFC.md) looked back at which "usage" the current 45 ECMA-402 units were chosen for, and recast the energy-units proposal as "energy usages." The targets are electricity bills, utility dashboards, EV charging, solar generation, and similar (the units needed are kilowatt-hour / watt / kilowatt).
- Scientific use, industrial scale, automotive horsepower, natural-gas heating, batteries and small devices, and nutrition were settled as clearly out of scope. [MM](../../people/MM.md) and [JSC](../../people/JSC.md) asked about excluded units such as Kelvin and mmHg, and about whether full SI coverage is desirable. [SFC](../../people/SFC.md) answered that completeness is a non-goal and that the judgment is by usage.
- The committee wanted quantitative selection criteria for adding a usage in the future. A CLDR survey confirming the units in every locale (regions that use megajoule, and so on) is unfinished, so Stage 2 was not requested this time.
- Conclusion: Stage 2 will be requested at a future meeting.

## Error code property for Stage 1, 2, or 2.7

- wiki: [Error code property](../../proposals/error-code-property.md)
- slide: [link](https://github.com/jasnell/proposal-error-code-property/blob/main/slides-export.pdf)
- [JSL](../../people/JSL.md) presented a proposal that passes `code` (any value; by convention a string) in Error's options bag and installs it as an instance property. It is thin syntactic sugar of the same kind as `cause`, and the aim is to standardize an existing pattern that Node.js introduced in 2017 and that spread to Axios, the AWS SDK, Deno, Bun, and others. They explained that it does not clash with DOMException's existing `code`.
- [MM](../../people/MM.md) raised a possible follow-on that would also give a code to each error the spec throws. [PFC](../../people/PFC.md) and [KM](../../people/KM.md) pointed out the concern that more observability would take away an implementation's freedom to reorder steps, and the enormous [amount](../../proposals/amount.md) of work to assign a code across the whole spec. [EAO](../../people/EAO.md) and [WH](../../people/WH.md) were concerned about a namespace land grab, and argued that whether to pursue spec-mandated codes should be decided at an early stage.
- [ACE](../../people/ACE.md) pointed out that `code` also needs to be reflected by structuredClone, as `cause` is. [JGT](../../people/JGT.md) supported it as a standard place for error information, and also mentioned over-reliance on code and how few error types there are. [JHD](../../people/JHD.md) volunteered as a reviewer and said the namespace problem does little real harm.
- Conclusion: Stage 1 approved ([JSL](../../people/JSL.md) transferred it to the tc39 org that night). Whether the language defines codes, and how, stays under discussion.

## Update on ESM Phase Imports

- slide: [link](https://docs.google.com/presentation/d/1inTcnb4hugyAvKrjFX_XHTnxYaPW0rodWwn0VFmlq24/edit?usp=sharing)
- [GB](../../people/GB.md) gave the first update in about a year. After restating the current semantics of source phase imports and WebAssembly imports, they explained the current ESM phase imports spec in detail. `import source` obtains a compiled module rather than an instance, and you can instantiate it yourself by supplying a custom import.
- They presented and explained two normative changes (PR 58 / 61), and also introduced an editorial refactoring that separates the module source record from the module record (PR #56). [CZW](../../people/CZW.md) asked for host integration with Node.js (especially the VM module) to be made clearer. [GB](../../people/GB.md) showed a plan not to make that a requirement for Stage 3.
- Conclusion: there was no opposition to PR 58 / 61, but the presentation was late, so consensus was deferred to the next meeting to leave enough review time. Until then, discussion of builtin source, HTML, and Node.js integration continues.

## First-class Protocols Update

- slide: [link](https://tc39.es/proposal-first-class-protocols/slides/2026-03/)
- [LVU](../../people/LVU.md) restarted this proposal, which [MF](../../people/MF.md) started in 2017 and which had stalled for a long time, with new co-champions ([LVU](../../people/LVU.md) and [JHD](../../people/JHD.md)). No stage advance was sought. The aim was committee feedback on the current state, what has changed since 2018, and the unresolved design questions (Stage 2 is planned for a future meeting).
- The motivation is to reify the ad hoc protocols scattered through the language (iterator, thenable, toPrimitive, and others) so an author can declare, introspect, and compose their own protocol or interface on a symbol basis. It covers provided members as well as requirements. Uses were also presented for turning DOM EventTarget and various web-component capabilities into protocols.
- Committee feedback: [MM](../../people/MM.md) cared about protocol immutability, judging by a property test rather than branding, and not making generated symbols into registered symbols. [ACE](../../people/ACE.md) and [DRR](../../people/DRR.md) were concerned about the effect of `implements` in the class head on type-stripping tools, and about the confusion of changing the meaning of `implements`, which previously had no runtime behavior. [SHS](../../people/SHS.md) and [OFR](../../people/OFR.md) were concerned about writing generated symbol members by identifier name. [DRR](../../people/DRR.md) suggested splitting the proposal into three (bulk generation of a group of symbols / copying a group of properties / checking that an interface is satisfied).
- Conclusion: the discussion did not finish in the time box and carries on (no stage transition today).
