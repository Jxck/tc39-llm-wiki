## IDL for ECMAScript with WebIDL

- proposal: [proposal-idl](https://github.com/tc39/proposal-idl)

TFA (Tooru Fujisawa, Mozilla) presented proposal-idl: representing ECMAScript built-ins in WebIDL so that bindings, types, and tooling can be generated from the spec HTML automatically (a prototype exists). It continues the old "IDL for ECMAScript" exploration — the JS IDL alternative was rejected as unnecessary — and is purely editorial, with no normative intent. What it needs from the language's notation: a new `property` syntax for data properties, a non-enumerable extended attribute, `@@symbol` syntax, prototype/instance syntax, a function-`length` attribute, `NoBrandCheck`, abstract operations as types, lazy coercion, and an enum-throws-`RangeError` attribute. Three integration plans were sketched: an appendix, a dual view, or fully integrated spec text. [TAB](../../people/TAB.md) liked the project but warned "if for ever in the future, any ECMAScript API defined using it has to be extensively annotated with extended attributes, that's a failure of the project" — new syntax preferred; [NRO](../../people/NRO.md) and [MF](../../people/MF.md) cautioned against changing language design for IDL's sake; [WH](../../people/WH.md) preferred one source generating both formats and worried about a circular WHATWG dependency; [YSV](../../people/YSV.md) asked why WebIDL rather than JS IDL (embedders, WinterTC, reuse) and [SFC](../../people/SFC.md) noted an options read-ordering difference; [LCA](../../people/LCA.md) raised the unsolved legal question of a normative reference to a WHATWG spec inside an ECMA standard (the TG4 source-maps problem — Aki/Samina to be consulted); [DRR](../../people/DRR.md) asked how much stays implicit for implementers ([CZW](../../people/CZW.md): Node does not generate from WebIDL and prefers explicit steps).

The conclusion was that none was sought — the speaker's summary records the next steps, with a preference for integration path 2 (the dual view).

## Continuation: `Decimal` Stage 1 Update

- wiki: [Decimal](../../proposals/decimal.md)
- proposal: [proposal-decimal](https://github.com/tc39/proposal-decimal/)

[JMN](../../people/JMN.md) resumed the [Decimal](../../proposals/decimal.md) `Decimal.Amount` discussion. [WH](../../people/WH.md)'s π-to-72-digits question exposed that the rounding guarantees only hold for Decimal128-representable values, there is no method to force exponential notation, and all five IEEE rounding modes are supported — with ties-to-even left without a good answer for 0.95 at one significant digit (both choices are odd; [SFC](../../people/SFC.md) to check ICU). On `Decimal.Amount.prototype.equals` ([SFC](../../people/SFC.md): a value type needs it for HashMap/HashSet; [WH](../../people/WH.md): it "reduces but doesn't fix" the confusion with arithmetic equality, and what about NaN?), [MM](../../people/MM.md) argued that if Composites existed, Amounts could be composites and `.equals` would be wasteful (NaN equal under composites, not under IEEE). [EAO](../../people/EAO.md) called the 34-digit limit arbitrary (Intl's precedent allows far more); [MM](../../people/MM.md) revisited the superset question and acknowledged the string-backed case is narrower than he thought (amounts do no arithmetic — only a convenience loss). [WH](../../people/WH.md)'s double-rounding example — Number 0.15 → Decimal → round to one significant digit gives 0.2, but `(0.15).toPrecision(1)` is "0.1" — split the room: [DMM](../../people/DMM.md) objected that rounding the decimal representation "is generally a bug", while [WH](../../people/WH.md) held "It is not a bug" (IEEE arithmetic operates on the float64); [NRO](../../people/NRO.md) explained the float64↔Decimal128 round-trip with 1.1. A 90-minute numerics breakout was announced for the next day.

The conclusion was that none was reached — the summary records three open uncertainties: rounding edge cases, the equality/Composites relation, and Decimal-vs-Number backing.

## SeededPRNG for Stage 2

- wiki: [SeededPRNG](../../proposals/seeded-prng.md)
- proposal: [proposal-seeded-random](https://github.com/tc39/proposal-seeded-random)

[TAB](../../people/TAB.md) (Tab Atkins-Bittner, Google) presented [SeededPRNG](../../proposals/seeded-prng.md) for Stage 2: a class constructed from a `Uint8Array` (112-byte state / 32-byte seed; wrong length throws) or a convenience integer 0-255, with a `fromRandomSeed` static drawing genuine entropy, `.random()` (Rust-style 64→53-bit float), `.randomSeed()` for spawning child sequences, and a `state` get/set for pause/resume — specified on **ChaCha12**, the Rust/NumPy choice suggested by bakkot (Go uses ChaCha8). [MM](../../people/MM.md)'s running quarantine concern resurfaced: `Date` and `Math.random` are the nondeterminism hardened JS must censor or virtualize, and he praised how `Temporal.now` isolated it — though [KG](../../people/KG.md) noted that knowing the seed enables a communications channel between two holders, and the exposed state getter defeats the no-channel claim. [DLM](../../people/DLM.md) relayed Mozilla security's feedback: is ChaCha12 overkill, the 32-byte seed is not cryptographically secure, and misuse is a concern ([TAB](../../people/TAB.md): the API is deliberately shaped away from crypto use); he also asked why this belongs in the language at all (the CSS custom paint use case).

The conclusion was Stage 2, with 2.7 reviewers [KG](../../people/KG.md), [JMN](../../people/JMN.md), and [MM](../../people/MM.md) — and the class renamed `Random.Seeded` on the strength of the next topic.

## More Random Functions for Stage 1

- wiki: [More Random Functions](../../proposals/more-random-functions.md)
- proposal: [proposal-random-functions](https://github.com/tc39-transfer/proposal-random-functions/)

[TAB](../../people/TAB.md) followed with a deliberately wide-net proposal: a new **`Random` namespace object** (`Math.random` stays; `Random.random` duplicates it) covering random numbers/ints/BigInts with range and step, array shuffle (in-place and returning), weighted take/sample, non-uniform distributions (normal, log-normal, binomial, …), random bytes filling a `Uint8Array`, booleans, and strings — all ChaCha12 and spec-mandated, with the same methods mirrored on `SeededPRNG`. [MF](../../people/MF.md) called it an omnibus proposal to split into 3-4 pieces — "within a range, choose a random value" is the strong core. [MM](../../people/MM.md) suggested a class-prototype with a single global entropy instance instead of a namespace, which [KG](../../people/KG.md) dismantled (the global instance exposes its state, and the replay use case needs extractable seeds — [MM](../../people/MM.md) retracted); [EAO](../../people/EAO.md) and [SFC](../../people/SFC.md) pushed the single-`Random`-namespace shape ([SFC](../../people/SFC.md): the Seattle breakout consensus to prefer namespaces over globals, Temporal as the example — while noting the tension with small proposals); [DRR](../../people/DRR.md) asked for uniform signatures between namespace functions and instance methods.

The conclusion was Stage 1 for the `Random` namespace with a core of methods (.number/.int/.bigint plus the seeded mirroring), with the array methods and non-uniform distributions split off to new proposals — and all methods also living on `Random.Seeded`.

## Immutable `ArrayBuffer` for Stage 3

- wiki: [Immutable ArrayBuffer](../../proposals/immutable-arraybuffer.md)
- proposal: [proposal-immutable-arraybuffer](https://github.com/tc39/proposal-immutable-arraybuffer)

[RGN](../../people/RGN.md) (Richard Gibson, Agoric) presented the [Immutable ArrayBuffer](../../proposals/immutable-arraybuffer.md) testing plan — by his account the best conformance to the testing-plan concept of any proposal — with the Stage 3 ask deferred to the next meeting. Resolved edge cases: `sliceToImmutable` with reversed bounds follows `slice` (clamps to zero); TypedArray writes over immutable data fail visibly (`Set` returns false, strict mode throws); DataView validates the receiver first, then rejects; transfer methods check immutability after argument coercion and detachment; Atomics reject as early as possible. Test categories cover `ArrayBuffer.prototype` methods (resize/slice/transfer throw `TypeError` before touching arguments), the new properties (the `immutable` getter, `sliceToImmutable`'s length 2, `transferToImmutable`), `TypedArray.from`/`of`, mutating methods throwing even at length 0, `[[Get]]`/`[[Define]]`/`[[Set]]`, DataView, and Atomics — to be landed as a series of small PRs. [NRO](../../people/NRO.md) called it "probably one of the best I've seen"; [MM](../../people/MM.md) observed that implementers will not look until Stage 3, so the order-of-operations tests carry the weight; [PFC](../../people/PFC.md) noted the testing-plan docs have landed in test262.

The conclusion was that the test262 PRs completing the plan should satisfy Stage 3 at the next meeting.

## Iterator Chunking for Stage 2.7

- wiki: [Iterator Chunking](../../proposals/iterator-chunking.md)
- proposal: [proposal-iterator-chunking](https://github.com/tc39/proposal-iterator-chunking)

[MF](../../people/MF.md) presented [Iterator Chunking](../../proposals/iterator-chunking.md) for Stage 2.7: receivers now close on invalid arguments, matching all iterator helpers. The open question is `.windows()` with fewer items than the window: option 1 yield nothing (current), option 2 throw on next, option 3 yield an undersized window, option 4 padding — against `chunks`, which intentionally yields an undersized final chunk (a length check detects it). A survey of other languages mostly lands on option 1 (Elm 1|3, Java 3, Kotlin 1|3 via parameter, Python's more-itertools 4, Scala 3); [MF](../../people/MF.md) prefers 1 or 3, calling throwing an abuse of exceptions and padding without a pad value unreasonable. [JHD](../../people/JHD.md) floated a `done: true` result carrying the remaining values (lost when chaining); [PFC](../../people/PFC.md) noted option 3 is bad for TypeScript (optional element types); [DMM](../../people/DMM.md) preferred 3 (dropping values hides future bugs; [MF](../../people/MF.md): `drop`/`filter` already drop); [MM](../../people/MM.md) was unsure `windows` pays for itself at all (chunks is well motivated); [RGN](../../people/RGN.md) asked for real call sites ("filling out a grid") — [SFC](../../people/SFC.md) posted about 15, [KG](../../people/KG.md) gave the pair-scanning example, [LCA](../../people/LCA.md) reported Rust's GitHub counts (chunks 90k vs windows 41k), and [CM](../../people/CM.md) image processing (often implemented in hardware); [DRR](../../people/DRR.md) prefers 1 or 2.

The conclusion was that options 1 and 3 are both useful for different use cases — [MF](../../people/MF.md) will split `.windows()` into two methods, settle naming in the issue tracker, and the proposal was not advanced.
