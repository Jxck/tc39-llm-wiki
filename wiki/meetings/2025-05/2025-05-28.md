## Normative: Add "Late Errors for Function Call Assignment Targets" to Annex B (#3568)

- proposal: [spec PR #3568](https://github.com/tc39/ecma262/pull/3568)

[RKG](../../people/RKG.md) (Ross Kirsling, Sony) presented a normative PR codifying the web's "late errors" for function-call assignment targets: in sloppy mode on the web, `f() = value` is not an early syntax error but throws a runtime `ReferenceError` immediately after the call — the function's return value is never resolved to a primitive and the right-hand side is never evaluated. The PR follows the new Annex B convention of normative-optional blocks (ecma262#2952) so implementations can keep the spec's early error. He also surfaced a SpiderMonkey inconsistency the work exposed: `f()++` calls `valueOf` on the result while `f() += 1` does not. [WH](../../people/WH.md) asked about web reliance — fixing sloppy-mode behavior outright would break the web, which is why it lands as Annex B.

The conclusion was consensus on merging the PR (support from [DLM](../../people/DLM.md), [MF](../../people/MF.md), and [DMM](../../people/DMM.md)).

## Temporal status update and normative change

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [proposal-temporal](https://github.com/tc39/proposal-temporal)
- slide: [link](https://ptomato.name/talks/tc39-2025-05/)

[PFC](../../people/PFC.md) (Philip Chimento, Igalia) reported that [Temporal](../../proposals/temporal.md) **shipped in Firefox as of May 27** ([DLM](../../people/DLM.md) confirmed), with V8 integrating `temporal_rs` — the Rust implementation grown out of Boa, in a collaboration between Boa, V8, and the University of Bergen with Kevin Ness leading — JSC progressing, and SpiderMonkey at 99% Test262 conformance. The normative change tightens UTC offset parsing: when an offset is written with optional parts (seconds), the parts must match exactly or a `RangeError` is thrown — motivated by Pacific/Niue's 1952 offset change from -11:19:40 to -11:20, where inexact matching would accept an offset that was never valid; SpiderMonkey supports the change.

The conclusion was consensus on tightening the optional-seconds matching.

## AsyncContext web integration brainstorming

- wiki: [AsyncContext](../../proposals/async-context.md)
- proposal: [proposal-async-context](https://github.com/tc39/proposal-async-context)

[ABO](../../people/ABO.md) (Andreu Botella, Igalia) ran a brainstorming session on [AsyncContext](../../proposals/async-context.md)'s web integration — the blocker keeping it at Stage 2. The state of play: Mozilla negative (niche use case plus implementation cost), Chrome engaging (it needs task propagation internally), WebKit silent, and Canva feedback asking for context through the rendering pipeline (e.g. `ResizeObserver` callbacks). The per-API analysis: `await` is the core case (V8's `ContinuationPreservedEmbedderData`), `setTimeout` is easy via WebIDL, `addEventListener` async events propose "drop" — no special handling, the default engine behavior ([CZW](../../people/CZW.md) clarified) — Streams pull may drop too ([JSL](../../people/JSL.md)'s feedback), observers are hard through CSS/layout, and the registration-time fallback context (a Bloomberg ask) is likely droppable if events are dropped. Ad-hoc ideas included an `unhandledrejection` `.rejectioncontext` property and `postMessage` scheduling. [MM](../../people/MM.md) worried about surprise when multiple causes produce one effect; [NRO](../../people/NRO.md) reported that frameworks (Solid, Svelte, Vue) need only the `await` basics; [SHS](../../people/SHS.md) argued at least half of DOM events are async, tracing needs implicit propagation, and properties are unsuitable (cargo-culting, reintroducing userland memory leaks); [LCA](../../people/LCA.md) framed it as "users first, designers second, implementers third" against [YSV](../../people/YSV.md)'s "users over developers over implementers"; MNY pointed to `<style>`/`<img>` load events as continuations and a Chromium task-attribution prototype where the link is owned by the context; [DLM](../../people/DLM.md) said the concerns are DOM-side and the proposal should reach out to WHATWG.

The conclusion was that this was a discussion, not consensus-seeking — the topic resumes at the Web Engines Hackfest.

## Keep trailing zeros in `Intl.NumberFormat` and `Intl.PluralRules` for Stage 1

- wiki: [Intl Keep Trailing Zeros](../../proposals/intl-keep-trailing-zeros.md)

[EAO](../../people/EAO.md) (Eemeli Aro, Mozilla) proposed retaining trailing zeros from numeric strings: today `"1.0"` is treated as exactly 1, so `Intl.NumberFormat` renders "1" and `Intl.PluralRules` selects a category that loses the "other"-style nuance English gives "1.0"; the proposal keeps the trailing zeros through formatting and selection. ## `Decimal` Stage 1 update

- wiki: [Decimal](../../proposals/decimal.md)
- proposal: [proposal-decimal](https://github.com/tc39/proposal-decimal/)

[JMN](../../people/JMN.md) (Jesse Alama, Igalia) updated the [Decimal](../../proposals/decimal.md) design around `Decimal.Amount`: a thin class wrapping a canonicalized subset of IEEE-754 decimal128 plus separately tracked precision (significant digits, fraction digits, trailing zeros), immutable, with functional precision updates that round, `.toLocaleString` support, and units to come later via Measure. Use cases are data-exchange round-tripping and UI stepper quanta. [MM](../../people/MM.md) confirmed the cohort-observability ban still stands (Decimal strips trailing zeros; precision is tracked separately) and that equality means equal underlying decimals and equal precision — which [WH](../../people/WH.md) questioned ("why have an equals operation at all?"; it was removed, with equality falling out of arithmetic). [MM](../../people/MM.md)'s main objection was tying Amount to Decimal at all — it should be a generic/`Number.Amount` — while [SFC](../../people/SFC.md) argued the decimal-backed version is a superset (string round-trips work) and a polymorphic amount means enum variants, branching, and heap allocation (engine feedback); [EAO](../../people/EAO.md) sided with [MM](../../people/MM.md) (BigInt/numeric-string use cases; Intl supports 400 digits). [NRO](../../people/NRO.md) observed that string parsing cannot be split from precision extraction, which [MM](../../people/MM.md) conceded breaks his symmetry argument.

The conclusion was to continue in the continuation topic — no consensus between Decimal-backed and String-backed, and the polymorphic-versus-concrete question open.

## Iterator Sequencing for Stage 3

- wiki: [Iterator Sequencing](../../proposals/iterator-sequencing.md)
- proposal: [proposal-iterator-sequencing](https://github.com/tc39/proposal-iterator-sequencing)

[MF](../../people/MF.md) (Michael Ficarra, F5) presented [Iterator Sequencing](../../proposals/iterator-sequencing.md) (`Iterator.concat`) for Stage 3. Since reaching 2.7: tests merged ([ABL](../../people/ABL.md)), the underlying-iterators slot fixed, a December consensus to reuse `IteratorResult` objects, and [ABL](../../people/ABL.md)'s final-`.value` PRs (#19/#23). But the `yield*`-alignment thread has turned: `yield*` can leave the source iterator open (its `return` can get `done: false`), while `concat` always closes — and chasing alignment with `yield*` keeps producing worse decisions. As he put it: "We are doing language design. We're not doing implementation design." [DLM](../../people/DLM.md) was fine diverging from `yield*` ([ABL](../../people/ABL.md) is mistaken on the semantics); [MM](../../people/MM.md) objected to `IteratorResult` reuse (an Agoric-internal concern about communications channels); [RGN](../../people/RGN.md) was enthusiastic about revisiting the `yield*`-based decisions; [LCA](../../people/LCA.md) retracted his earlier dislike.

The conclusion was to back out PR #18 (`IteratorResult` reuse) and PRs #19/#23 (final `.value`), stop matching `yield*` further, update the tests, and bring the proposal back for Stage 3 later.
