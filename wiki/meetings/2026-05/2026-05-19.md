# 2026-05-19 (114th TC39 Meeting, Day 1)

## Needs-consensus PR: use Numbers instead of reals as counters in Iterator builtins (#3776)

- slide: [link](https://docs.google.com/presentation/d/1WVjZyIAjTPl3TDV6X2cxNp1n-bzulIy_XWyKOsSq7i4)
- A needs-consensus PR that changes the counter passed to an iterator-helper callback from an arbitrary-precision integer in the spec to a float64-style count. The trigger was a problem JSC found while implementing `Iterator.prototype.includes`.
- The targets are the seven iterator helpers that have a counter, plus `Iterator.prototype.take` / `Iterator.prototype.drop`. take and drop throw a RangeError immediately for a large finite value past 2^53.
- In practice no implementation uses an arbitrary-precision int; they all use float64. [MF](../../people/MF.md) does not like the change itself but said the spec should match implementation reality. [DLM](../../people/DLM.md) / [OFR](../../people/OFR.md) / PST opposed making it a BigInt, on performance.
- Conclusion: consensus to merge the PR.

## Needs-consensus PR: Support BigInt coercion of integers expressed as exponential-notation strings (#3857)

- A needs-consensus PR so the `BigInt` constructor accepts an exponential-notation string (for example `4.2000e+4`) when it denotes an integer. Today the Number constructor accepts it and BigInt throws a SyntaxError; this removes that asymmetry. The [Amount](../../proposals/amount.md) proposal is what surfaced it.
- This changes the behavior of a built-in function, not the grammar of bigint literals. [OFR](../../people/OFR.md) / [CLA](../../people/CLA.md) raised an unresolved question: does exponential notation express precision (is it all right to treat `1.00` as an integer)?
- Opinion split on whether this should stay a needs-consensus PR or enter the stage process. [MF](../../people/MF.md) / [OFR](../../people/OFR.md) leaned slightly toward staging. [RGN](../../people/RGN.md), taking the most conservative line, asked for stage one once, but the agenda addition had been late, so the conclusion was deferred.
- Conclusion: discuss it again next meeting as a needs-consensus PR.

## Needs-consensus PR: Require internal consistency w.r.t. prefixing {get,set} in SetFunctionName (#3855)

- A needs-consensus PR, presented by [RGN](../../people/RGN.md), that makes it consistent per implementation whether SetFunctionName prefixes an accessor function's name slot with `get` / `set` (today each function may choose freely; this makes the choice normative optional).
- The survey: V8 and others always add the prefix, SpiderMonkey and engine262 always omit it, and both are consistent. Only JSC was reported as inconsistent, on DataView's byteLength and byteOffset.
- [YSZ](../../people/YSZ.md) raised a web-compatibility concern. When JSC previously added the prefix across the board, major sites that detect Safari from the getters of `location.search` / `location.href` broke and it was reverted. Further investigation was promised. [KM](../../people/KM.md) also flagged the risk.
- Conclusion: the PR did not reach consensus and will be revisited next time, waiting on JSC's investigation. A continuation was requested during this meeting to offer a narrower alternative.

## Dynamic Code Brand Checks for stage 4, or normative change (PR #23)

- wiki: [Dynamic Code Brand Checks](../../proposals/dynamic-code-brand-checks.md)
- slide: [link](https://docs.google.com/presentation/d/1v8vJ3JpjRwof_P1MSp9264zQJUsO4NfBwzZQFTyczII/edit)
- A proposal for ECMA-262 to support the web's Trusted Types (formerly names such as allow code-like object evaluation). It adds a host hook to `eval` and `new Function` and passes the host not only the string to evaluate but also the original object.
- [NRO](../../people/NRO.md) reported that the current proposal and implementations have drifted from the committee consensus of 2024-04. `eval` does not call `toString` on a trusted object, but `new Function` does. [NRO](../../people/NRO.md) preferred aligning the proposal and the implementations with the consensus side (do not call `toString`).
- Every browser has already shipped an implementation. [DLM](../../people/DLM.md) supported the normative change and was not worried about changing implementations. [KM](../../people/KM.md) was fine either way.
- Conclusion: consensus on the normative change. Update the proposal and the implementations, then ask for Stage 4 again.

## `Atomics.pause` for Stage 4

- wiki: [Atomics.pause](../../proposals/atomics-pause.md)
- proposal: [proposal-atomics-microwait](https://github.com/tc39/proposal-atomics-microwait)
- [KM](../../people/KM.md), in place of [SYG](../../people/SYG.md), asked for Stage 4 for `Atomics.pause`. It gives engines a hook for a short spin before suspend in a spin lock (the equivalent of x86 pause and ARM ISB).
- At the same time, a normative change to remove the optional pause-count parameter, which no implementation uses. [RBN](../../people/RBN.md) worried this would close off future backoff control. [NRO](../../people/NRO.md) / [WH](../../people/WH.md) replied that the parameter has no effect anyway if the behavior is ignored.
- [RBN](../../people/RBN.md) did not treat the concern as blocking. [WH](../../people/WH.md) said it should not be included now, so that a future parameter can still be given meaning.
- Conclusion: the normative change (removing the parameter) was accepted, and `Atomics.pause` reached Stage 4.

## RegExp Buffer Boundaries for Stage 2.7 or 3

- wiki: [RegExp Buffer Boundaries](../../proposals/regexp-buffer-boundaries.md)
- slide: [link](https://1drv.ms/p/c/934f1675ed4c1638/IQBpJAD8CJutTpZ3x70Mr8C6AQ6Z26p2_nowaDED0_XQfRY?e=FLSMPe)
- [RBN](../../people/RBN.md) presented [regexp buffer boundaries](../../proposals/regexp-buffer-boundaries.md). It adds `\A` (start of input) and `\z` (end of input), which match the start or end of the whole input regardless of the multiline flag. Limited to `/u` or `/v`. Easy to implement as syntactic sugar over modifiers.
- The main motivation is portability. It improves interoperation with the regexp syntax shared by TextMate grammars and build tools, and it answers demand for a replacement for the archived oniguruma.
- Proposed reintroducing `\Z` (which allows an optional line terminator at the end), removed in 2021. [CPC](../../people/CPC.md) / [MF](../../people/MF.md) supported both advancing `\A` / `\z` and reintroducing `\Z`. [DLM](../../people/DLM.md) had no concerns. Tests for `\Z` are not ready.
- Conclusion: consensus on reintroducing `\Z`. Consensus on a conditional advance to Stage 2.7, conditional on the `\Z` spec text landing. A Stage 3 follow-up was planned the same week (Thursday).

## isTemplateObject status update and possible withdrawal

- proposal: [proposal-array-is-template-object](https://github.com/tc39/proposal-array-is-template-object)
- [JHD](../../people/JHD.md) gave a status update on `isTemplateObject` and raised whether it should be withdrawn. [ZTZ](../../people/ZTZ.md) explained a design problem: it does not work cross-realm. An iframe srcdoc and similar cases can build a string that another same-origin realm treats as non-dynamic and pass it to the original realm, so the feature only means something within one realm, and a string primitive gets a realm-dependent break in identity.
- [RGN](../../people/RGN.md) said the proposal is under-motivated (it is unnecessary if you do not pass untrusted input to a trusted-types policy). [MM](../../people/MM.md)'s concern about SES transpilation was also mentioned.
- [KM](../../people/KM.md) was attached neither to implementing it nor to withdrawing it. [RGN](../../people/RGN.md) explicitly supported withdrawal.
- Conclusion: consensus to make the proposal inactive (specifically, withdrawn). The reasons are insufficient need and interest on the implementation side, and the realm-related concerns.

## `export defer` Stage 2 status update

- slide: [link](https://docs.google.com/presentation/d/1uYgMUqz5bZT3wwPARnyq7GrJlWFesIrmoCJA1iDH3W8)
- [NRO](../../people/NRO.md) and the new champion [CLA](../../people/CLA.md) presented a Stage 2 update on `export defer` (deferred re-exports). The same Promise leak as `import defer`, through `%Promise.all%`, is fixed with a safe PerformPromiseAll abstract operation. Bugs in the interaction with `export * from`, and in binding validation through a namespace import, were also fixed (both are bug fixes at Stage 2, so they do not need consensus).
- As a solution to tree shaking being lost when `export defer` is combined with `import defer *`, they proposed filtered namespaces. `import { foo, bar } as obj` creates a fresh namespace object each time that contains only the exports that are needed (meeting TG3's no-cache requirement). Expansion to `export as`, `import defer`, and dynamic import is also in view. `*` keeps importing everything, as today.
- People on the bundler side were interested in this change on its own, because it makes tree shaking easier. [LCA](../../people/LCA.md) also supported it strongly as a direction that completes the module system. Applying it to dynamic import is planned as a new property on import's second argument (filter, or names).
- Conclusion: the source text has no Speaker's Summary or Conclusion. The plan is to merge the filtered-namespaces change and bring the whole picture, including dynamic import, back to the next meeting.
