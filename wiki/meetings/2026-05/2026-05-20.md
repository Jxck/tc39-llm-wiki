## Iterator Chunking for Stage 3

- Stage 3 ask for [iterator chunking](../../proposals/iterator-chunking.md). The test262 tests have been open for more than a month and a half and [KG](../../people/KG.md) has reviewed them, but they are not merged.

- [NRO](../../people/NRO.md) strongly warned against shipping while the tests are unmerged, citing a past case that shipped on PR approval alone and produced a bug. [DLM](../../people/DLM.md) replied that they would run the tests at ship time and confirm they all pass.

## Iterator Includes for Stage 3

- wiki: [Iterator Includes](../../proposals/iterator-includes.md)
- Stage 3 ask for [iterator includes](../../proposals/iterator-includes.md). The test262 tests have been open for more than a month and [KG](../../people/KG.md) has reviewed them.
- Includes a PR that reflects the previous day's agreement to treat the counter as a number rather than a mathematical value. Extremely large counters are not tested in test262, so the behavior is unaffected.
- [SFC](../../people/SFC.md) asked about the case where the counter saturates on an infinite iterator. [MF](../../people/MF.md) answered that the problem exists only when the second argument of includes (a float) is Number.MAX_SAFE_INTEGER + 2 or greater, and that saturation does not occur: the counter simply stops changing.
- Conclusion: consensus for Stage 3.

## Stable Formatting for Stage 2

- wiki: [Stable Formatting](../../proposals/stable-formatting.md)
- slide: [link](https://docs.google.com/presentation/d/1Vnt2-ejFMpk3NstM2DS0TtSRIoDqm9jqE4siiuMe4qE/edit)
- Stage 2 ask for a proposal that provides stable, locale-agnostic formatting through the `zxx` locale, because Intl output is unstable and depends on ICU / CLDR. To avoid a null / undefined distinction, it introduces a constant `Intl.STABLE` that returns the string `zxx`.
- `Intl.DateTimeFormat` uses a 24-hour clock, matching [Temporal](../../proposals/temporal.md) output. `Intl.NumberFormat` gains short unit identifiers drawn from SI and similar sources. `Intl.Collator` / `Intl.Segmenter` and others cannot be given a stable behavior, so they are excluded from this proposal and left to a follow-on.
- Discussion concentrated on the short unit identifiers for `microsecond` (the Unicode character for µ: U+00B5 or U+03BC) and `mile-scandinavian` (`mil` / `smi` / `SE mil`, and others). [SFC](../../people/SFC.md) said the biggest open problem is that it is not yet confirmed whether zxx is safe in CLDR terms.
- Conclusion: approved for Stage 2. The microsecond and mile-scandinavian identifiers, and the remaining issues, continue at Stage 2. Reviewers are [RGN](../../people/RGN.md) and [DLM](../../people/DLM.md).

## Default Behaviours for some Intl APIs for Stage 1

- wiki: [Default Behaviours for some Intl APIs](../../proposals/intl-default-behaviours.md)
- slide: [link](https://docs.google.com/presentation/d/1xPQ6WDDYf2MYCLPxFlaRBKARPWhaZ7fVCPFA8e6xRaY/edit?slide=id.p#slide=id.p)
- Stage 1 ask for a proposal that gives users a well-defined, locale-independent default behavior for `Intl.Collator` / `Intl.Segmenter` and `String.prototype.toLocaleLowerCase` / `toLocaleUpperCase`, which fell out of [Stable Formatting](../../proposals/stable-formatting.md).
- The plan adds `"und"`, which denotes the root locale, as a supported locale. Collator returns the CLDR root collation. Segmenter returns UAX 29 behavior with no tailoring. Passing zxx falls back to `"und"`.
- [SFC](../../people/SFC.md) supported the motivation, and pointed out that `"und"` has meant the default locale for 14 years, so the string used to obtain the root locale should be considered separately in TG2.
- Conclusion: approved for Stage 1.

## Intl Sequence Units for Stage 1 or 2

- wiki: [Intl Sequence Units](../../proposals/intl-sequence-units.md)
- slide: [link](https://tc39.es/proposal-intl-sequence-units/slides/stage_1_or_2.html)
- A proposal to add to `Intl.NumberFormat` a way to format several units in a row, as in "5 ft 11 in." Today you have to compose several formatters and ListFormat by hand, and there are many footguns, including sign handling.
- Units are specified with an `-and-` infix (from CLDR / UTS 35), as in `foot-and-inch`, and format is passed an object whose fields are the subunits. A negative sign is attached only to the largest unit, and intermediate units must be integers. The allowed combinations are limited to six sanctioned groups and do not depend on locale.
- Scalar input versus object input was a large issue. [JHD](../../people/JHD.md) said it is not intuitive whether a scalar 6.5 is feet or inches. [EAO](../../people/EAO.md) supported the object because of ambiguity when fractionDigits applies. [WH](../../people/WH.md) said that if it is a scalar it should be the smallest unit, to avoid floating-point error.
- Conclusion: Stage 1, and Stage 2 for the object-based design. A scalar can be reconsidered later. Reviewers are [EAO](../../people/EAO.md) and [DLM](../../people/DLM.md).

## SetFunctionName refinement

- A PR about whether `Function.prototype.toString` of an accessor function gets a get / set prefix. The normative version discussed the previous day (forbidding a free choice per function) was judged too far for this meeting, so this PR (#3874) is the editorial version.
- Two layers: a normative optional step that sets `[[InitialName]]` unconditionally, and a legacy step that leaves the presence of the prefix implementation-defined. Whether there is a prefix should be implementation-defined and uniform, and mixing it across built-ins is noted as discouraged legacy behavior.
- [JHD](../../people/JHD.md) argued the note's "should" ought to be "must." [RGN](../../people/RGN.md) settled that a note cannot be normative and that this change only clarifies the status quo (editorial). [NRO](../../people/NRO.md) also thought it should be treated as normative, while allowing editorial discretion.
- Conclusion: PR #3874 is left to the editor group's discretion. The normative #3855 will be brought back at a future meeting.

## Amount for Stage 2

- wiki: [Amount](../../proposals/amount.md)
- slide: [link](https://docs.google.com/presentation/d/1Wq4uT0-lx8A_rfoSQ9uy5cnH1WHZXVjRmfYuugqkjQo/edit?slide=id.p#slide=id.p)
- Stage 2 ask (resubmission) for [Amount](../../proposals/amount.md), a container type that combines a number, BigInt, or numeric string with an optional unit. It includes unit conversion, `convertTo()`, as a feature.
- Improvements since last time: better precision for convertTo, exponential notation for numeric strings, and `~` for the no-unit form (from YAML null). The direction for conversion math is to treat CLDR ratios as mathematical values, though there is also a concern that an implementation would have to hold about 2,100 numbers.
- [WH](../../people/WH.md) called the error from implicit string-to-number conversion an important problem (halfEven for 825g → kg, and the example where 3\*3 becomes 8, issue #108) and said conversion should be limited to numbers. [WH](../../people/WH.md) also asked that it ship in coordination with sequence units. The plan is to keep a design that does not require rational arithmetic of implementers.
- Conclusion: approved for Stage 2. Reviewers are [WH](../../people/WH.md) and [JHD](../../people/JHD.md). Improving the precision of the conversion math continues at Stage 2.

## export all from for Stage 1

- wiki: [export all from](../../proposals/export-all-from.md)
- slide: [link](https://docs.google.com/presentation/d/1IKj6GdnvI25gbqq_GUH-LQZOyfp0W1NFWc0hD4LU4CU)
- Stage 1 ask for a proposal that solves the problem that `export * from` does not re-export `default`, so a proxy module (a CDN version alias, and similar) cannot be written generically. A reconsideration of a plan Guy Bedford and others presented in 2016, which was blocked at the time.
- The champion's ([NRO](../../people/NRO.md)) preferred solution is to change the behavior of `export * from` so it always re-exports `default` too. When the `default`s of several modules collide, it is ambiguous in the same way as a named export and errors at import time. Adding new syntax was judged not worth the problem space.
- On web compatibility, the concern is that a namespace import gains `default`, but it was judged low risk, like adding an export to a library. JHX asked for caution in light of the reason it was blocked ten years ago (the specialness of default). [JHD](../../people/JHD.md) said they also intend to champion `export default from` separately.
- Conclusion: consensus for Stage 1 (no speaker summary or conclusion is written in the source). [ZTZ](../../people/ZTZ.md) will look into the effect on CommonJS interoperation.

## Module Scope Ceiling

- slide: [link](https://github.com/endojs/proposal-module-global/tree/main/slides)
- Status update on the former module-global proposal. The direction has changed to a surgical change that does not create a new Global and stops a module's lexical lookup from reaching the global scope.
- In `InitializeEnvironment`, the module environment record's `[[OuterEnv]]` is replaced with a `ScopeCeiling` (named by [CM](../../people/CM.md)) whose `[[OuterEnv]]` is null, rather than the Realm's globalEnv. `Object`, `Function`, and the rest of the same Realm remain available. The motivations are DSLs (a test runner injecting `describe` / `it`) and supply-chain security (LavaMoat).
- [JRL](../../people/JRL.md) was concerned about integration with the HTML spec, which puts a settings object on the global environment record. [NRO](../../people/NRO.md) added that HTML obtains the global through the Realm, not through lexical scope, so it can still line up. Whether `OuterEnv` is a spec fiction (implementation-dependent) is an open question.
- Conclusion: status update only (no stage transition). How to expose `ScopeCeiling`, and whether browsers can implement it, stay under investigation.

## RegExp Buffer Boundaries Continuation

- wiki: [RegExp Buffer Boundaries](../../proposals/regexp-buffer-boundaries.md)
- slide: [link](https://1drv.ms/p/c/934f1675ed4c1638/IQBpJAD8CJutTpZ3x70Mr8C6AQ6Z26p2_nowaDED0_XQfRY?e=FLSMPe)
- A correction: explaining `\Z` on Day 1 as equivalent to CRLF or LF was a simplification, and it was wrong. The proposal at Stage 1 matches the same way as `\R` (LineTerminatorSequence), which is different from multiline `$` (which does not handle CRLF).
- `\Z` is a zero-width assertion that allows an optional line-terminator sequence (CRLF / LF / CR / LS / PS) just before the end of the buffer. Java and .NET already handle CRLF by default (issue #20). [CPC](../../people/CPC.md) pointed out that the equivalent group should be non-capturing.
- [RBN](../../people/RBN.md) offered two options: ask for consensus on this correction, or split `\Z` into a separate proposal and advance `\A` / `\z` first. They asked for consensus first.
- Conclusion: consensus on the corrected definition of `\Z`, `(?=(?:\r\n|\n|\r|\u2028|\u2029)?(?-m:$))`. Reviewers were recruited toward a Stage 3 advance the next day.

## AsyncContext (Stage 2) web integration status update

- slide: [link](https://docs.google.com/presentation/d/1Q3wGg0YbYXio6lO3fzbo2gKJFiTb1t4Z1W4313CHZ3I)
- Status update on web integration of AsyncContext, which propagates a value implicitly through an async code flow. Nothing changes on the TC39 side. Most of the complexity is integration with the large set of web async APIs.
- Events are the hardest part. The direction changed to drop the registration context and handle only the dispatch context, and that reached Stage 1 at WHATWG. Whether propagation happens is defined by five principles (an EventTarget itself is synchronous and does not interfere, a listener from an external cause gets an empty context, events of the same target or of the object that created them do propagate, and so on).
- [ABO](../../people/ABO.md) is writing a set of PRs that apply the principles to web specs (a WebIDL extended attribute, HTML, IndexedDB, and others). [RGN](../../people/RGN.md) said the propagation rules are complicated next to how clear the opening example is, and asked for a form that can be explained on one sheet, like lexical scoping.
- Conclusion: feedback that the propagation rules should be as simple as lexical scoping. Awkward behavior that can be explained clearly should be preferred to an edge case that is hard to explain. Collaborators with specialist knowledge of particular web APIs were invited.

## Source Phase Imports, Request for Consensus for Normative Change: Ambiguous re-export handling for Source Phase Imports

- slide: [link](https://docs.google.com/presentation/d/1h7tHdRqdkR0s_x6TOiSlOIH-wA17cN7Hz0BLjeuLhqc)
- A consensus check on a normative change so that, when a source-phase-import binding resolves to the same thing through several star re-exports, it is deduped and does not throw, the same way a namespace does (issue #75, PR #76, ecma262 #3775). An edge case with no effect on 99.9% of developers.
- Source phase import follows the principle that an import declaration does not introduce a new binding. The question is whether several paths to the same module source can be treated as the same binding. [LCA](../../people/LCA.md) argued that, from the contract that a host hook returns the same source for the same input, it can be treated as a slot-like binding, as a namespace is. [GB](../../people/GB.md) confirmed that the abstract module record has a slot for the module source.
- [NRO](../../people/NRO.md) said internal consistency is weaker than for import star, because there are not two forms that ought to be unified, but that it is good for consistency with the other kinds of import.
- Conclusion: consensus on the normative change that lets source phase imports participate in dedup of ambiguous re-exports. The current rebase already has this behavior naturally, so no explicit spec change is needed.

## ESM Phase Imports normative PRs

- slide: [link](https://docs.google.com/presentation/d/1RHIYufBtt6LuAIqsbaOpkr2gZckC7NROzm_Zl9yTFYY/edit)
- A return of two normative PRs (#58 and #61) already presented last time (March). They were added after the deadline, so approval had to be secured at the next meeting.
- PR #58: change module-source identity from source-text equality to real object identity. Source-text equality produces odd behavior, such as whitespace and comments affecting equality. postMessage to a worker produces a different identity, and identity can no longer be judged across a round trip.
- PR #61: remove the artificial restriction on cross-realm imports (throwing when a source is brought into an iframe and similar), now that the identity model is established.
- [JHD](../../people/JHD.md) was concerned about losing a way to judge identical source text. [NRO](../../people/NRO.md) explained that identity has to be preserved to avoid a race in HTML's module map. [MAH](../../people/MAH.md) asked about the effect on identity uses of shared structs. [RBN](../../people/RBN.md) did not yet understand the effect on shared structs and asked to hold consensus.
- Conclusion: no consensus, because of [RBN](../../people/RBN.md)'s hold. Continuation planned for the last session the next day (about 40 minutes). [RBN](../../people/RBN.md) and [GB](../../people/GB.md) will discuss it outside the meeting.

## Thenable Curtailment status update

- wiki: [Thenable Curtailment](../../proposals/thenable-curtailment.md)
- slide: [link](https://docs.google.com/presentation/d/1SW8xSjuWqrdix_MOE3O-ZJcR-_XgO4z2ajhJInz0IwE/view)
- Update on a proposal that addresses an ongoing security exploit: a thenable (an object with `then`) is special-cased when a Promise resolves, and defining `Object.prototype.then` keeps producing vulnerabilities. More vulnerabilities have appeared since last time.
- The direction is a new abstract operation (provisionally SafeResolve) that resolves a Promise without starting user code. A temperature check on whether this capability should be exposed to users came out probably 12 / no 6 / yes 3.
- The best current idea for how to expose it is a second argument to the resolve function, but [LCA](../../people/LCA.md) was concerned about compatibility risk from Boolean coercion and suggested a well-known Symbol or `resolve.safe`. Also discussed: making `Object.prototype.then` exotic ([KM](../../people/KM.md) / [MF](../../people/MF.md)), and a plan from [JRL](../../people/JRL.md) that resolves including user code (it would break Svelte, but improve security).
- Conclusion: this proposal aims at Stage 2.7 next meeting, and [MAG](../../people/MAG.md) keeps writing the spec text ([JHD](../../people/JHD.md) and Justin Ridgewell are reviewers). User exposure is split into a separate proposal so this one can move faster. People opposed to exposure were invited to share their reasons on the repository.
