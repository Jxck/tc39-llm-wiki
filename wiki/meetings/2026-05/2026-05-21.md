- [JSH](../../people/JSH.md) brought the [comparisons](../../proposals/comparisons.md) proposal, which provides deep equality natively, back for Stage 1 (the delta from the previous two presentations, cleaned up). Use cases include HTTP-patch deltas, React state comparison, logging, and testing; userland implementations are deliberately "incorrect" for performance.
- The API is based on `compare(a, b)`: a fast mode returns a boolean, and a full mode returns an iterator of deviations that carry `expected` / `actual` / reason. An alternative that splits `deepEqual` and `compare` was also presented.
- [OFR](../../people/OFR.md) said the definition of equality itself is the biggest issue (`NaN`, signed zero, holey arrays, proxies, floats, and so on). [JSH](../../people/JSH.md) set the baseline near SameValueZero (`NaN` is equal, signed zero is not, holes in the same position are equal) and showed a plan to extend it as needed.
- Conclusion: the motivation was broadly accepted (many voices asking for a native solution), and a continuation was set the same day so a written statement for the vote could be prepared.

## An introduction to the EU CRA & how it matters to all of you

- slide: [link](https://hosted.akiro.se/2026/Ecma/TC39/Cyber%20Resilience%20Act%20primer.pdf)
- AKI gave an overview of the EU Cyber Resilience Act (CRA). Selling a product on the EU single market requires compliance. Software, and products that contain it, are in scope (pure SaaS and websites are out of scope and fall under other regimes such as NIS2). The core is a risk-based approach: 14 essential cybersecurity requirements, and documenting a vulnerability-handling policy.
- Technical documentation needs an SBOM (e.g. CycloneDX, standardized at Ecma) and a risk assessment. The main text applies from December 2027, but vulnerability reporting (an early warning to ENISA within 24 hours, notification within 72 hours) applies from September 2026.
- Open source without economic activity has no legal obligation, and ECMA-262 is neither a product nor an open-source project, so Ecma has no obligation. Vulnerabilities in the spec itself are the product side's duty to report ([JHD](../../people/JHD.md), as TG3 convener, added that there is still an ethical responsibility).
- Conclusion (Speaker's Summary): the CRA affects almost every product company. Open source is protected from penalties, but in practice aligning with the cybersecurity requirements is desirable. On SHN's proposal, later plenaries will keep a 30-minute follow-up slot.

## agreeing to consider impact of RegExp proposals to linear implementations

- slide: [link](https://aurele-barriere.github.io/ecma_amsterdam_handout.pdf)
- [AUR](../../people/AUR.md), with [CPC](../../people/CPC.md), [MF](../../people/MF.md), and MBH, asked the committee to agree to consider the effect of RegExp proposals on linear-time matching implementations. They showed that a JS regex without backreferences can be matched in linear time, and that ECMAScript is the only major language where every lookaround is known to be linear-time matchable.
- Against the background of how common ReDoS vulnerabilities are, the motivation was a facility that lets the user control or judge linearity. Several delegates reported that they already restrain their own use of regex because of the risk of catastrophic backtracking.
- Conclusion: broad support for considering the effect of new proposals on linearity. Consensus that future regex proposals include an impact assessment of regex-matching complexity. A non-blocking concern was that complexity is hard to analyze; non-linearity is not an automatic reason to reject. [AUR](../../people/AUR.md) / [CPC](../../people/CPC.md) / [MF](../../people/MF.md) will bring back linearity-related proposals: stating a preference for [linear matching](../../proposals/linear-matching.md), running linearly, judging whether linear execution is possible, a time limit, and so on.

## Tooling for navigating the ECMA-262 specification and reviewing API proposals

- slide: [link](https://docs.google.com/presentation/d/19iIbMpnV1mxhBcKZAdxd8KlNNpimgpcDefwssylQfuU/edit?usp=sharing)
- MBH and ATI presented, as a TG5 work item, an IDE-like tool for navigating the ECMA-262 specification. It treats the spec's pseudocode as code (ESMeta's premise) and covers about 1,100 abstract operations and built-in algorithms.
- An experimental tool based on JetBrains MPS, focused on reading the existing spec rather than authoring it. ESMeta parses the pseudocode into an AST and provides IDE features such as go-to-definition and diff, while imitating the look of the normative document.
- The demo loaded the 2023, 2024, and 2025 editions and opened an algorithm from a folder structure that corresponds to the table of contents.
- Conclusion: none (an informational presentation).
