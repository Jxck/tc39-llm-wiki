## Immutable ArrayBuffers for Stage 1

- wiki: [Immutable ArrayBuffer](../../proposals/immutable-arraybuffer.md)
- proposal: [proposal](https://github.com/Agoric/tc39-proposal-immutable-arraybuffer)
- slide: [link](https://github.com/Agoric/tc39-proposal-immutable-arraybuffer/blob/main/immu-arrayBuffers.pdf)

[MM](../../people/MM.md) presented (co-champions Peter Hoddie and [RGN](../../people/RGN.md)) the need for immutable bulk binary data: embedding data in ROM (Moddable/XS), avoiding defensive copies of large buffers, and zero-copy sharing between agents that can't use shared-memory threading. The mechanism is `ArrayBuffer.prototype.transferToImmutable` plus a spec change letting TypedArrays backed by immutable buffers be frozen (indexed properties born non-configurable, non-writable). [WH](../../people/WH.md) noted strings can already shim the immediate need; [DE](../../people/DE.md) explored a reader/writer-lock pattern (rejected — immutable buffers can never become writable); [SYG](../../people/SYG.md) noted Wasm memory cannot be detached so it can't use this, and asked about the use case for `sliceToImmutable`. Open questions include the transfer orthogonality, `sliceToImmutable`, error-reporting order, and the SharedArrayBuffer/Atomics relationship.

The conclusion was Stage 1 with no objections.

## DataView get/set Uint8Clamped methods for stage 2

- proposal: [proposal](https://github.com/tc39/proposal-dataview-get-set-uint8clamped)

[JHD](../../people/JHD.md) asked for Stage 2 for filling in the DataView matrix's two gaps: `getUint8Clamped` (identical to `getUint8`) and `setUint8Clamped`. The motivation — generic dynamic dispatch over TypedArray kinds — did not convince: [KG](../../people/KG.md) saw dispatch value only when names line up, [MF](../../people/MF.md) warned against filling in every matrix square, [PHE](../../people/PHE.md) called it setting the wrong direction, and [PFC](../../people/PFC.md) pointed at V8's built-in-function resource costs (citing what was cut from [Temporal](../../proposals/temporal.md)). [YSV](../../people/YSV.md) required use cases completely solved by the proposal — polyfilling does not qualify, since the branch still has to exist.

The conclusion was that the proposal does not advance and remains at Stage 1; alternatives include set-only or a standalone clamp helper.

## Measure object stage 0

- wiki: [Amount](../../proposals/amount.md)
- proposal: [proposal](https://github.com/ben-allen/proposal-measure)
- slide: [link](https://docs.google.com/presentation/d/1yakKCsS3pR0T7eJcaJD2ZUzK6xG6FcoFnrmngkJUcEo)

[BAN](../../people/BAN.md) presented [Measure](../../proposals/amount.md) — an object bundling a value with its unit (and optional precision), supporting mixed units and a `convert` method — as spun out of Smart Units. [SFC](../../people/SFC.md) framed the bigger problem space: the canonical "dimensioned value" input type for Intl formatters, MessageFormat, and currency amounts (overlapping some [Decimal](../../proposals/decimal.md) use cases). The conclusion was Stage 1, plus the start of an informal numeric-representation working group ([SFC](../../people/SFC.md), [PHE](../../people/PHE.md), [JHD](../../people/JHD.md), [YSV](../../people/YSV.md), [JMN](../../people/JMN.md), [CDA](../../people/CDA.md)).

## import defer updates regarding evaluation triggers

- wiki: [import defer](../../proposals/import-defer.md)
- proposal: [proposal](https://github.com/tc39/proposal-defer-import-eval/)
- slide: [link](https://docs.google.com/presentation/d/1yFbqn6px5rIwAVjBbXgrYgql1L90tKPTWZq2A5D6f5Q/edit)

[NRO](../../people/NRO.md) reported two bugs found while testing the Stage 2.7 proposal. First, `[[Get]]` fires less often than the spec assumed, so the rule was generalized: any property query that depends on module contents triggers evaluation — but consensus on that change was not reached ([MM](../../people/MM.md) relaying [KKL](../../people/KKL.md)'s preference for existing-exports-only evaluation; [NRO](../../people/NRO.md) to return with the proposal). Second, the dynamic `import.defer()` form is broken: promise resolution reads `then` on the namespace, evaluating the module immediately. Options ranged from hiding `then` exports on deferred namespaces ([ACE](../../people/ACE.md)'s idea) to special-casing the promise machinery ([JRL](../../people/JRL.md)), but [YSV](../../people/YSV.md) and [SYG](../../people/SYG.md) preferred dropping `import.defer` entirely rather than censoring; [ACE](../../people/ACE.md) worried about closing the door on future use cases, and the deferred-namespace semantics would still need deciding now.

The conclusion was no consensus on the evaluation-trigger change; `import.defer` is expected to be dropped, with follow-ups offline.

## Continuation: TG4: Source Map Specification, 2024 edition approval

- slide: [link](https://docs.google.com/presentation/d/147UbvCUAoW07vkQjYKJrf8SqqmCnmicvVBwEu__lOu4/edit?usp=sharing)

JKP continued the day 1 approval, addressing [MM](../../people/MM.md)'s security concern: non-parser-based recognition (scanning bottom-up for comment-looking lines, as VS Code does) can pick up a source-map URL that parser-based recognition misses, causing unwanted network fetches. A proposed bail-on-backtick/quote rule ([MM](../../people/MM.md), [JRL](../../people/JRL.md)) was challenged by [NRO](../../people/NRO.md) — it misses closing multi-line comments and quotes, and [RGN](../../people/RGN.md) noted URLs may legitimately contain those very characters — and normative changes couldn't happen anyway without returning to TG4. The compromise: publish with an editorial warning that the two recognition methods can disagree and that a normative fix is coming in the living draft.

The conclusion was conditional approval with the editorial note, and agreement to send the 2024 TG4 specification to the Ecma GA.

## Continuation: JSSugar/JS0

- slide: [link](https://docs.google.com/presentation/d/1ylROTu3N6MyHzNzWJXQAc7Bo1O0FHO3lNKfQMfPOA4o/edit)

The JSSugar discussion resumed. Clarified: "less stable" means post-Stage-4 mistakes can be fixed in tools, not that features churn ([SYG](../../people/SYG.md)); [YSV](../../people/YSV.md) remained cautious about any versioning. [PFC](../../people/PFC.md) asked whether non-browser embedders could implement the whole language; [CM](../../people/CM.md) saw core-plus-compiled-languages as a normal pattern. [DE](../../people/DE.md) and [NRO](../../people/NRO.md) argued transpilers are limited to local transforms, so JSSugar doesn't unlock new kinds of language features — engines hide the same complexity. [RBN](../../people/RBN.md) gave concrete emit-size data (standard [decorators](../../proposals/decorators.md) inflating bundles 34-110% in Material Web), disputing [SYG](../../people/SYG.md)'s claim that JSSugar design constraints would have changed the outcome; [SYG](../../people/SYG.md) countered that Google teams still transpile to ES5 because dropping it regresses runtime performance (TDZ, classes). Packaging questions (shipping JSSugar to npm, debugging, patchability) and the adoption/performance feedback loop ([JHD](../../people/JHD.md), [DE](../../people/DE.md)) stayed open.

The conclusion was no conclusion — discussion continues.
