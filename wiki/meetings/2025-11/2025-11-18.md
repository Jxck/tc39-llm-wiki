# 2025-11-18 (Day One)

## Normative: In PluralRules, set compactDisplay only if notation is "compact"

A normative PR that fixes an internal spec bug in `Intl.PluralRules`: set the `compactDisplay` option only when `notation` is `"compact"`. The current spec sets `compactDisplay` on an internal slot even when `notation` is not `"compact"`, and this corrects that inconsistency. The effect on implementations is small. It is a consistency fix to match existing host behavior. There was no opposition in the room, and the committee agreed to merge it as a normative PR.

## Normative: make re-exporting a namespace object in 2 steps behave like 1 step

A fix for a spec bug in which re-exporting a namespace object in two steps (`import * as ns` and then `export { ns }`) behaved differently from doing it in one step, as in `export * as ns from "mod"`. Changing the spec's evaluation order so the two match keeps the module link and evaluation phases consistent. A harmful difference between implementations had been reported, and it was approved as a normative PR.

## Normative: Extend `JSON.parse` and `JSON.stringify` for interaction with the source text of primitive values

A normative PR, related to access to the source text of `JSON.parse` (the `source` reviver argument), that specifies how that interacts with `JSON.stringify` of primitive values. It adds edge-case behavior to the spec for how source text should be treated when a primitive such as a number or a string is round-tripped. The committee agreed to the clarification, and it was merged.

- wiki: [Temporal](../../proposals/temporal.md)

Philip Chimento ([PFC](../../people/PFC.md)) reported progress toward finishing [Temporal](../../proposals/temporal.md) at Stage 4. He shared spec review, test262 coverage, and browser implementations (Firefox / SpiderMonkey have already shipped; V8 and JSC are in progress), and reported that the remaining work is a very small number of edge cases. [Temporal](../../proposals/temporal.md) is already at the shipping stage in several implementations, and the outlook was that final arrival at Stage 4 is close.

## `Error.captureStackTrace` for Stage 2

A proposal to standardize the equivalent of Node.js `Error.captureStackTrace` as an ECMAScript API, so that obtaining a stack trace is handled uniformly across engines. V8-line engines already have an equivalent proprietary extension, and standardizing it is meant to improve interoperability of polyfills and tools. Delegates had questions about the API design and about how it integrates with the error object, and the reaction was broadly positive.

Conclusion: advancement to Stage 2 was approved.

## Intl Locale Info API for Stage 4

Advancement to Stage 4 was proposed for the locale-information APIs on `Intl.Locale`, such as `getTextInfo()` and `getWeekInfo()`. Spec review and test262 tests are done, and shipping in several implementations was confirmed. The committee had further questions about implementation status, and it was shown that those were already resolved.

Conclusion: advancement to Stage 4 was approved.

## Iterator Sequencing for Stage 4

A proposal that concatenates several iterators as `Iterator.concat()`, with advancement to Stage 4 on the agenda. Final spec review and test262 tests are done, and implementations were reported as in progress in the major engines. The committee raised no large objection.

Conclusion: advancement to Stage 4 was approved.

## Keep trailing zeros in `Intl.NumberFormat` and `Intl.PluralRules` update

- wiki: [Intl Keep Trailing Zeros](../../proposals/intl-keep-trailing-zeros.md)

A progress report on an option that keeps trailing fractional zeros in `Intl.NumberFormat` and `Intl.PluralRules`. It is already proceeding as Stage 3. This session checked small spec-text fixes from implementation feedback, and how edge cases are handled. There was no large spec change, and the plan to continue implementation and tests at Stage 3 was confirmed.

## Joint Iteration for Stage 3

- wiki: [Joint Iteration](../../proposals/joint-iteration.md)

A proposal that provides `Iterator.zip()` and similar, for walking several iterables at once, with advancement to Stage 3 on the agenda. API design, error handling (how a short iterable ends the walk), and naming were discussed, and the concerns raised by the committee were mostly resolved.

Conclusion: advancement to Stage 3 was approved.

## export defer for Stage 2.7

Advancement to Stage 2.7 was proposed for the `export defer` syntax (a deferred-evaluation export of a module). There were questions about the state of the spec text and the tests, and it was pointed out that more work is needed on some implementation angles and on interaction with the existing dynamic import.

Conclusion: there was no agreement on Stage 2.7. Discussion continues at the current stage.

## `Error.prototype.stack` accessor for stage 2.7

A proposal to standardize `Error.prototype.stack` as an accessor property. The champion explained that they were not asking to advance to Stage 2.7 at this point, and wanted to propose it again later after more implementation feedback. The committee accepted that plan.

Conclusion: this meeting did not seek a stage advance. It carries over at the current stage.

## Declarations in Conditionals for Stage 2

A proposal for a syntax extension that allows a variable declaration inside the condition of an `if` and similar statements. Several options for the syntax design (a form such as `if (let x = ...)`, and others) were shown, and the committee questioned syntactic ambiguity and the scope rules actively. This session did not reach a conclusion, and discussion continued on Day Three.

Conclusion: no agreement on Stage 2. Continued to Day Three.

## await dictionary for Stage 2 or 2.7

- wiki: [Await Dictionary](../../proposals/await-dictionary.md)

A proposal that lets several Promises be `await`ed together in dictionary (object) form. The champion asked to advance directly to Stage 2.7 without passing through Stage 2, and the committee agreed. The API design was broadly supported, and the relationship to the existing `Promise.all` and similar was also checked.

Conclusion: advancement to Stage 2.7 (directly, without Stage 2) was approved.

## Intl Unit Protocol

A proposal for a foundational mechanism that defines the treatment of units in Intl uniformly, with advancement to Stage 1 on the agenda. The aim explained was a base that the unit argument of `Intl.NumberFormat`, and future unit-related proposals ([Amount](../../proposals/amount.md), Energy Units, and others), can share.

Conclusion: advancement to Stage 1 was approved.

## Import Text

A proposal for a syntax and API that imports a file as text as-is, such as `import text from "./file.txt"`. This session explained it as a new proposal for Stage 1, and then discussed advancing to Stage 2 and, conditionally, to Stage 2.7. There were questions about use cases (reading a config file or a template, and others) and about security considerations.

Conclusion: advancement to Stage 1 and to Stage 2 was approved, and advancement to Stage 2.7 was also approved conditionally, on completing test262 and review.

## TypedArray Concatenation

A proposal for an API such as `TypedArray.prototype.concat()` that concatenates several `TypedArray`s. The committee reacted favorably to the concept itself, but it was pointed out that there is not yet a dedicated repository.

Conclusion: conditional Stage 1 was approved, conditional on creating a dedicated repository.

## TypedArray Find Within

A proposal for an API that searches for an element inside a subrange of a `TypedArray`. As with TypedArray Concatenation, the reaction to the concept was positive, and it was pointed out that a dedicated repository is not yet in place.

Conclusion: conditional Stage 1 was approved, conditional on creating a dedicated repository.

## TypedArray byteOffset Mistake

A discussion that points out an inconsistency or mistake in the existing spec for `TypedArray`'s `byteOffset`, and a direction for fixing it. This session only shared the problem. There was no concrete request to advance a stage. It is expected to be tracked as an issue and, if needed, brought as a normative PR.
