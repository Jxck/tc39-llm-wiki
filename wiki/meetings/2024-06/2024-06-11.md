## Needs Consensus PR: ECMA-402: Specify time zone IDs to reduce divergence between engines

- proposal: [ecma402#877](https://github.com/tc39/ecma402/pull/877)
- slide: [slides](https://docs.google.com/presentation/d/1U_kNIpJb89LTSFh7BBiFIJSpW_epDSnzn4XKtER4IyQ/)

[JGT](../../people/JGT.md) presented the next piece of the multi-year time zone identifier effort (the canonicalization half already went to Stage 3 and merged into [Temporal](../../proposals/temporal.md)). Engines disagree on which IANA IDs are primary: CLDR, used by V8 and JSC via ICU, does not merge time zones across ISO 3166-1 country borders, while SpiderMonkey follows IANA's resolution rules at the cost of complex build steps and user-facing variation. The PR reifies the CLDR behavior as spec (web reality), adds a recommended two-year wait after a city rename (like Kiev to Kyiv) before making the new ID primary, and strengthens the "no observable time zone data updates during an agent's lifetime" recommendation into a requirement. [MF](../../people/MF.md) questioned the country-border rationale; [RGN](../../people/RGN.md) noted ISO 3166-1 codes already cover many significant regions; [DLM](../../people/DLM.md), [SFC](../../people/SFC.md), and [PFC](../../people/PFC.md) expressed support.

The conclusion was consensus: the ECMA-402 PR is approved to align the spec with the CLDR/ICU web reality, reducing current and future divergence between engines.

## eval() changes for trusted types update

- wiki: [Dynamic Code Brand Checks](../../proposals/dynamic-code-brand-checks.md)
- proposal: [proposal#17](https://github.com/tc39/proposal-dynamic-code-brand-checks/pull/17#issuecomment-2142865060)

[NRO](../../people/NRO.md) revisited the Trusted Types host-hook change agreed at the last plenary. The committee had decided to pass only the pieces (parameters and body) of `eval`/`new Function` code to the host, on the assumption that the fully concatenated string was spec-internal — but it turns out the string is already exposed through `new Function(...).toString()`, which (unlike most `Function.prototype.toString` behavior) is not implementation-defined. The PR therefore goes back to passing the fully built string (for example `async function (` plus parameters and body) to the host so it can build its own representation. [MF](../../people/MF.md), [DLM](../../people/DLM.md), and [ACE](../../people/ACE.md) voiced support and there were no concerns.

The conclusion was consensus on the PR.

## Avoid second pass/buffer in base64 setFromBase64/setFromHex methods

- wiki: [Uint8Array to/from Base64](../../proposals/uint8array-base64.md)
- proposal: [proposal](https://github.com/tc39/proposal-arraybuffer-base64)

[KG](../../people/KG.md) brought Stage 3 implementation feedback on the base64 proposal from [PHE](../../people/PHE.md) (Moddable): as specified, validating everything before writing anything means setFromBase64 and setFromHex need a full validation pass or a second buffer whenever the input turns out to be invalid partway through. The change (PR 58) writes the decoded data up to the first error and then throws, leaving an unknowable amount of garbage in the buffer on failure — acceptable because the expected use of a failed decode is to discard the buffer. [SYG](../../people/SYG.md) sent support ahead of time, noting the performance benefits of streaming and bring-your-own-buffer would be lost otherwise, and [LCA](../../people/LCA.md) gave a thumbs up in the room.

The conclusion was consensus on the change: decoded data is written up to the first error in setFromBase64 and setFromHex.

## Option to omit padding in toBase64

- wiki: [Uint8Array to/from Base64](../../proposals/uint8array-base64.md)
- proposal: [PR 60](https://github.com/tc39/proposal-arraybuffer-base64/pull/60)

[KG](../../people/KG.md)'s second piece of Stage 3 feedback, this time from users: base64 in the wild varies on padding, and several web specifications use unpadded base64url, so the previously removed padding option is reintroduced as an `omitPadding` boolean in the options bag (default false, i.e. padding included, matching atob and most encoders; W3C guidelines require boolean options to default to false). The option is orthogonal to the alphabet option, since there is no consensus on whether base64url requires padding — Python's decoder requires it. [RGN](../../people/RGN.md) approved of making the default unconditional.

The conclusion was consensus on adding the omitPadding option.

## Iterator sequencing

- wiki: [Iterator Sequencing](../../proposals/iterator-sequencing.md)
- proposal: [proposal](https://github.com/tc39/proposal-iterator-sequencing)
- slide: [slides](https://docs.google.com/presentation/d/1gOs4UDAcaIF6Dc9z1qXus-ljizrRTSty5O-GbcM9NTs/)

[MF](../../people/MF.md) presented the reworked proposal: the goal of composing an infinite sequence of iterators is dropped as hard to justify, and a new goal from [KG](../../people/KG.md) (no observable difference between the one-iterator and zero-or-more-iterators cases) is added, leaving a static `Iterator.concat` taking zero or more iterators, with full spec text, a polyfill, and tests. The open question is the name: [JHD](../../people/JHD.md) has previously worried that `concat` invites assumptions from `Array.prototype.concat`'s oddities, and [DE](../../people/DE.md) and [KM](../../people/KM.md) warned specifically against carrying forward anything like `Symbol.isConcatSpreadable` ([KM](../../people/KM.md): nobody ever used it); [MF](../../people/MF.md) showed alternative names exist and deferred the bikeshed, which [KG](../../people/KG.md) accepted for Stage 2. [KG](../../people/KG.md) also raised how `Iterator.concat` should close iterator arguments it never reaches, to be settled before Stage 2.7, and [MF](../../people/MF.md) confirmed the infinite case will not be pursued further.

The conclusion was Stage 2, with [NRO](../../people/NRO.md), [JMN](../../people/JMN.md), and [RGN](../../people/RGN.md) as reviewers; the final name (possibly still Iterator.concat) is decided during Stage 2.

## Async Iterators Update

- wiki: [Unordered Async Iterator Helpers](../../proposals/unordered-async-iterator-helpers.md)
- proposal: [proposal](https://github.com/tc39/proposal-async-iterator-helpers)
- slide: [slides](https://docs.google.com/presentation/d/1cjCkBRWwNFu01HUEcWQ6AsSgVGOxTj4cVvz_9XCyAkw/)

[KG](../../people/KG.md) laid out the design for concurrency in the async iterator helpers (inspired by Rust streams): only map, filter, flatMap, and toAsync get concurrency affordances, plus a `.buffered(N)` helper for exploiting them, all order-preserving. Unordered helpers such as buffer_unordered are left out as a separate design space ([MF](../../people/MF.md) supported the split, arguing it deserves the same care as the original async/sync split, and asked for an eager-start parameter for buffered, which [KG](../../people/KG.md) accepted), and the guarantee of results matching the sequential order is weakened in the error case so promises can settle as soon as they are ready. [ACE](../../people/ACE.md) confirmed that global concurrency management (such as capping concurrently open files) is out of scope, and [DE](../../people/DE.md)'s retrospective on async generators awaiting yielded values led [KG](../../people/KG.md) to conclude that syntax, not the await decision, is what limits concurrency there.

The conclusion was no advancement ask — the committee is in favor of this direction and the minimum set of helpers, with unordered concurrency to be explored as a follow-on.

## `Intl.MessageFormat` Stage 1 open question involving error handling design patterns

- wiki: [Intl.MessageFormat](../../proposals/intl-messageformat.md)
- proposal: [proposal](https://github.com/tc39/proposal-intl-messageformat)
- slide: [slides](https://docs.google.com/presentation/d/1kyQqhoc4utHer6o0Gomf7a9rgLwEFHobMLOL6FBlBs0/)

[SFC](../../people/SFC.md) presented the open Stage 1 question for [Intl.MessageFormat](../../proposals/intl-messageformat.md): Unicode MessageFormat distinguishes message errors (detected at construction) from resolution errors (only detectable during formatting), and the question is how to surface the latter. Three options were laid out: an onError callback passed to format (the current proposal), throwing an expressive error object, and an expressive return value. [DLM](../../people/DLM.md), [JWS](../../people/JWS.md), and [EAO](../../people/EAO.md) preferred the callback (consistent with the other Intl formatters and formatToParts); [RGN](../../people/RGN.md) objected to the callback's control-flow and reentrancy implications and floated separate throwing and non-throwing functions; [USA](../../people/USA.md) and TKP leaned callback or return value; PST and [JGT](../../people/JGT.md) floated putting error handling in the constructor, which [USA](../../people/USA.md) and [EAO](../../people/EAO.md) argued distances handling from where the error occurs and is awkward because format-time state is unknown at construction.

The conclusion was no decision: option 2 is undesirable to most delegates, there is no strong objection to option 3 but a majority prefer something else, reentrancy in option 1 remains a concern, and the new options raised (4, 5, and 6) will be considered by the champion group.

## RegExp Escaping

- wiki: [RegExp.escape](../../proposals/regexp-escaping.md)
- proposal: [proposal](https://github.com/tc39/proposal-regex-escaping)

[JHD](../../people/JHD.md) asked for Stage 2.7 for [RegExp.escape](../../proposals/regexp-escaping.md) with one open design question: whether escaping should keep character escapes (for example `\@`) or switch to hex escapes. [RGN](../../people/RGN.md) argued hex escapes are more future-proof, since `\@` is only valid in legacy (non-u/v) modes and a future mode could change that; BSH asked whether the output works under the u/v flags ([RGN](../../people/RGN.md): the output is semantically acceptable in either mode regardless); [MF](../../people/MF.md) doubted `\@`'s behavior could ever change web-compatibly and was neutral between the two; [MLS](../../people/MLS.md) preferred hex escapes for future stability. A temperature check came out even (3 to keep character escapes non-blocking, 3 to switch non-blocking, 19 neutral, nobody blocking), so [JHD](../../people/JHD.md) went with the status quo. [SYG](../../people/SYG.md)'s prepared statement: V8 has no concerns for Stage 2.7 and weakly prefers character escapes.

The conclusion was Stage 2.7 keeping character escapes (no change).

## `Error.isError`

- wiki: [Error.isError](../../proposals/error-is-error.md)
- proposal: [proposal](https://github.com/tc39/proposal-is-error)

[JHD](../../people/JHD.md) asked for Stage 2 for [Error.isError](../../proposals/error-is-error.md), a brand-check predicate for error instances, motivated by debugging, serialization tooling, and structured clone's special treatment of native errors; the proxy-piercing spec text copied from Array.isArray is open to change. [KG](../../people/KG.md) (relayed by [MF](../../people/MF.md)) remains unconvinced by the justification but would not be a sole objector, and [MF](../../people/MF.md) added that brand checking is "icky"; [RGN](../../people/RGN.md) found the exception justified for diagnostics and supported it, and [DMM](../../people/DMM.md) strongly supported the cross-realm use case. DOM exceptions should return true ([JHD](../../people/JHD.md) and [SYG](../../people/SYG.md) agree), with the internal-slot-versus-host-hook mechanism left open per [NRO](../../people/NRO.md)'s relay of V8's preference; [MAG](../../people/MAG.md) probed the cross-realm semantics, which [JHD](../../people/JHD.md) defended as consistent with every existing brand check. [DE](../../people/DE.md) criticized the committee's contradictory demands on proposal authors (requiring and prohibiting brand checks at once), and [MAG](../../people/MAG.md) asked that such decisions be written down and stuck to.

The conclusion was Stage 2: DOM exceptions and host errors will be considered errors, HTML integration will be pursued as fast as possible, it sets no precedent on brand checks either way, and interested parties ([JHD](../../people/JHD.md), [MF](../../people/MF.md), and others) will work toward a consistent brand-check design principle. Reviewers: [ACE](../../people/ACE.md) and [SRV](../../people/SRV.md).

## Deferred import evaluation for stage 2.7

- wiki: [import defer](../../proposals/import-defer.md)
- proposal: [proposal](https://github.com/tc39/proposal-defer-import-eval/)
- slide: [slides](https://docs.google.com/presentation/d/1EjV6QbT4bvcOdWj-gCLwP5fcEWRfewzbrI3vOI11LA8/)

[NRO](../../people/NRO.md) asked for Stage 2.7 for [import defer](../../proposals/import-defer.md), which skips module evaluation until an export is actually read. The previously blocked top-level await semantics stay as-is — deferred imports eagerly pre-evaluate the synchronous parts of the graph — with [ACE](../../people/ACE.md) describing Bloomberg's history of brittle sync-imports-of-async-modules to explain why the module system, not the importer, should make that call. Two changes since last time drew debate: reentrant evaluation of a deferred module involved in a cycle is now an error (the old text violated core spec assumptions and crashed V8 when exercised through Node's require(esm)), and deferred imports now produce a distinct namespace object so property access always throws deterministically when a module fails to evaluate. The distinct-identity change (raised by [SYG](../../people/SYG.md), who otherwise had no blocking concerns, as PR 43) struck [KM](../../people/KM.md), [JHD](../../people/JHD.md), [LCA](../../people/LCA.md), [DMM](../../people/DMM.md), and [SFC](../../people/SFC.md) as weird but non-blocking; [JWK](../../people/JWK.md) noted webpack already generates distinct namespace objects for CommonJS interop, and [ACE](../../people/ACE.md) noted separate objects are actually nicer for userland module emulation.

The conclusion was Stage 2.7, including both additional changes, conditional on the spec editors finishing editorial reviews.
