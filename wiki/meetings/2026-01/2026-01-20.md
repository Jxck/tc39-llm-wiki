## Normative: Add 1 new numbering system "tols" for Unicode 17 #1035

- proposal: [ECMA-402 PR #1035](https://github.com/tc39/ecma402/pull/1035)

SFC presented the annual update of the ECMA-402 numbering-system table, the minimal list of numbering systems engines must support. Unicode 17 added one new system, `tols` (from the Tolong Siki script), and since engines have largely upgraded to ICU 78, where it is available, it can now be required. Apple's YSZ confirmed from the implementer side that requiring it is fine, and DLM reported no concerns.

The conclusion was consensus: ECMA-402 PR #1035 is approved.

## Upsert for Stage 4

- wiki: [Upsert](../../proposals/upsert.md)
- proposal: [proposal](https://github.com/tc39/proposal-upsert)
- slide: [link](https://docs.google.com/presentation/d/1PpQsFGM1V8miLf5Fp5AQO_VASP2WFlu2lM4CkKozrBo/edit?slide=id.g2fb628be09c_0_0#slide=id.g2fb628be09c_0_0)

DLM (Mozilla) asked for Stage 4 for upsert, which adds two methods to `Map.prototype` and `WeakMap.prototype`: `getOrInsert`, which returns the value for a key or inserts a given value when the key is absent, and `getOrInsertComputed`, which takes a callback so the default can be computed lazily. Safari has shipped for a long time and Firefox more recently, both passing the full test262 suite, with additional implementations in V8, Porffor, Kiesel, and Boa, and the spec pull request has editor sign-off.

The conclusion was Stage 4, with multiple voices of support and no objections.

## Temporal update and needs-consensus PRs

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [proposal](https://github.com/tc39/proposal-temporal)
- slide: [link](https://ptomato.name/talks/tc39-2026-01/)

PFC (Igalia, in partnership with Bloomberg) reported that Temporal is closing in on Stage 4: test262 coverage expanded greatly (with implementation bugs filed from the results), V8 and SpiderMonkey are within half a percentage point of 100% conformance, and V8's implementation is now unflagged on the web alongside SpiderMonkey's, with GraalJS scheduled to unflag in its next release. Intl Era/Month Code is being tracked in parallel so the two can reach Stage 4 together. Two normative changes were proposed to eliminate surprise: a `PlainYearMonth` subtraction bug that has sat in the spec for over five years, found by snapshot testing, which the champions propose to fix by removing subtraction of days (restricting `PlainYearMonth` arithmetic to years and months, PR #3253, with a behavior-preserving fallback in PR #3208), and the surprise that `toLocaleString` of the Plain types is subject to the formatter's time zone, visible only across DST shifts or date-line changes and reported by two community members, fixed by PR #3246 on the principle that Plain types are wall-clock times.

The conclusion was consensus on both PR #3253 (restrict the arithmetic) and PR #3246 (drop the time-zone dependency); the fallback PR #3208 was not needed and is withdrawn.

## Intl Era/Month Code for Stage 3

- wiki: [Intl Era/Month Code](../../proposals/intl-era-month-code.md)
- slide: [link](https://notes.igalia.com/p/era-monthcode-stage-3-111th-plenary#/)

BAN (Igalia) presented the remaining normative changes and asked for Stage 3. The changes: dates before the 6 Meiji (1873) reform of the Japanese imperial calendar resolve as Gregorian dates, avoiding problems with extending the lunisolar calendar backward; `islamic-rgsa` is removed from the `ca` option because the calendar was requested by Oracle, never implemented as specified, and used by no country or web content — SFC called shipping it a pure footgun; the list of calendars implementations must support became a closed list ("must consist of" the calendar types table), matching the precedent of units, since calendars are complex enough that implementation divergence is the risk; a table of reference years handles leap months and leap days so rare that some combinations have never occurred in recorded history (reject throws a `RangeError`, constrain clamps to the non-leap month or the last day of the month, like February 29 to February 28); and a bugfix restores the pre-2025 Hebrew calendar difference behavior after the `NonISODateSurpasses` prose was replaced by algorithm steps. SFC explained the hard case of PR #111 as improving round-trippability where it can, and MF confirmed the change never makes the property worse.

The conclusion was that all the normative PRs were approved and the proposal reached Stage 3.

## Deferred re-exports update

- proposal: [proposal](https://github.com/tc39/proposal-deferred-reexports/)
- slide: [link](https://docs.google.com/presentation/d/1lrYTFTYrlhWTZ1tXdaMdJxcOWA7LU6AFkor339wNEkE/edit?slide=id.p#slide=id.p)

NRO (Igalia, with Bloomberg) reported on the two concerns that blocked Stage 2.7 last meeting: spec complexity (a pull request is starting to address it) and the interaction with import defer, which the presentation focused on. Combining the two proposals produces a performance cliff: import defer forces namespace imports, so a library using export defer is still fully loaded — the union of the two benefits is not obtained. Three solution directions were sketched: (1) make export defer defer only execution, not loading; (2) allow listing the bindings you care about, as in `import defer { mainThing } as ns`, which would also help dynamic imports; (3) make namespace imports not load deferred re-exports by default, turning access into an error unless something else loads them. DMM liked option 2 and asked how errors on unlisted bindings would behave; GB endorsed the reframing as an optionality scheme, comparing it to Cargo features; NRO personally prefers listing bindings while GB prefers option 3.

The conclusion was that there is no conclusion yet: the champions aim to reach consensus in the modules group by the next plenary and asked for delegates' first reactions.

MM recalled the original motivation (the fencepost problem when generators are used push-pull, where the first `next` call has nothing to push) and said he feels no urgency, but insisted the champion be consulted before withdrawal rather than set that precedent; NRO mentioned a marginal use case that came up around `AsyncContext` snapshots but did not object; CDA raised the same process point about the late agenda addition.

The conclusion was a conditional withdrawal, pending JHX's approval — with a later update in the notes that JHX is still interested, so the proposal was not withdrawn.

## Import Sync for Stage 2

- wiki: [Import Sync](../../proposals/import-sync.md)
- proposal: [proposal](https://tc39.es/proposal-import-sync/)
- slide: [link](https://docs.google.com/presentation/d/1TGOmmWkAWx9NkmXCgh_IaoW-4aDhhRQyRSow980EOgU/edit?slide=id.g3b508911f70_0_0#slide=id.g3b508911f70_0_0)

GB (Cloudflare) presented the follow-up to the proposal that reached Stage 1 in November 2024: runtimes like bun require `import.meta.require`, and Node.js was told to bring the require-ESM discussion to TC39 rather than standardize it unilaterally, so non-standard sync importers are proliferating and key module-system functionality is being stopgapped by the ecosystem. Use cases are synchronous access to built-in modules, fetching modules already in the registry (optional-dependency checks), and the new synchronous module expressions and module declarations. The spec is written with no major technical blockers: hosts already do sync resolution, import defer has already specified synchronous evaluation, and a `NotSyncError` is thrown when a module is not synchronously available (in flight or using top-level await). JHD required that it work in scripts like dynamic import does, which GB accepted; KG pushed on the framing of synchronously unwrapping a promise and was satisfied that this instead exposes module machinery that is already synchronous; DLM reported Mozilla is not excited (complexity in an already complex system) but would not block; OFR questioned the ergonomics of racy event-handler use (GB: it throws rather than blocks, like `require`); KM asked about a design based on source modules (GB: the source phase does not fetch dependencies, so it does not solve this); NRO suggested the real split is main thread versus worker (workers already block via `importScripts`); and PFC and DMM added interactive-prompt (GNOME) and ServiceNow use cases.

The conclusion was Stage 2, with GB stating that any Stage 2.7 would not be rushed and would require clear implementer support, resolved semantics for deadlocks and the source/defer phases, and strong motivating use cases. NRO volunteered as reviewer.

## Error option limit for stage 1

- proposal: [proposal](https://github.com/BridgeAR/error-limit-option)

RBR (Datadog) proposed a `limit` option in the error constructor options bag, bounding the stack frames captured for that individual error, as a standardized alternative to V8's global `Error.stackTraceLimit`. From code he has seen, about 90% of that API's usage is set the limit, create the error, reset it — usually to cut cost (limit 0 roughly halves the CPU cost of error creation) or to keep only the first frames — and the per-error form removes the failure mode of a global change leaking into unrelated errors. NRO supported it and recommended explicitly leaving what counts as a stack frame implementation-defined; SHS (Google) noted it covers only user-constructed errors, not VM-thrown ones; DLM asked whether the global API could ever be removed and whether it should be standardized anyway (RBR: it cannot be removed, but usage should drop sharply); OFR relayed the reaction that libraries should not be able to hide error frames (RBR: the local limit winning over the global reflects how the API is already used). MM asked that the advancement discussion be held jointly with the next proposal, since the same issues apply to both.

The conclusion was Stage 1, called after the framesAbove discussion once a short problem statement (a standardized cross-engine way to control stack depth per error instance, without manipulating a global knob affecting unrelated errors) was read into the record.

## Error option framesAbove for Stage 1

- proposal: [proposal](https://github.com/BridgeAR/error-frames-above)

RBR presented a second error options-bag property (name open for debate) that hides the stack frames at and above a referenced method — the pattern behind about 90% of `Error.captureStackTrace` usage, where libraries trim their own helper frames. Unlike `captureStackTrace`, the frames are never calculated twice and the hidden frames do not count against the stack limit, so the frames the user cares about survive. MM supported Stage 1 for both proposals but urged bringing them to TG3 soon, since error stack visibility dominates that group's security discussions, and confirmed the proposals coexist naturally with the error-stack-accessor proposal (independent accessors embody the behavior); he also raised whether the Stage 2 `Error.captureStackTrace` proposal should be killed in favor of this (DLM: engines cannot unship it, so it should still be standardized, while RBR hopes usage drops and asked to postpone its progression and reassess in two years). KG, JHD, and CZW clarified the options-bag compatibility picture (Firefox's positional line/column constructor arguments, and `DOMException` takes no options bag); KM asked for a collaborative list of where engine traces differ, which RBR agreed to open as an issue; and PFC warned that a convenient hiding feature will be adopted as an alleged best practice and hurt debugging and the open-source ecosystem, even as RBR argued it only formalizes existing behavior with fewer footguns.

The conclusion was Stage 1, with support from MM, DMM, CZW, JHD, and SFC, after which the limit proposal was called and also reached Stage 1.
