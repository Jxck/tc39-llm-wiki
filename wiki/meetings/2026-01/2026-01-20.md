## Normative: Add 1 new numbering system "tols" for Unicode 17 #1035

- proposal: [ECMA-402 PR #1035](https://github.com/tc39/ecma402/pull/1035)

[SFC](../../people/SFC.md) presented the annual update of the ECMA-402 numbering-system table, the minimal list of numbering systems engines must support. Unicode 17 added one new system, `tols` (from the Tolong Siki script), and since engines have largely upgraded to ICU 78, where it is available, it can now be required. Apple's [YSZ](../../people/YSZ.md) confirmed from the implementer side that requiring it is fine, and [DLM](../../people/DLM.md) reported no concerns.

The conclusion was consensus: ECMA-402 PR #1035 is approved.

## Upsert for Stage 4

- wiki: [Upsert](../../proposals/upsert.md)
- proposal: [proposal](https://github.com/tc39/proposal-upsert)
- slide: [link](https://docs.google.com/presentation/d/1PpQsFGM1V8miLf5Fp5AQO_VASP2WFlu2lM4CkKozrBo/edit?slide=id.g2fb628be09c_0_0#slide=id.g2fb628be09c_0_0)

[DLM](../../people/DLM.md) (Mozilla) asked for Stage 4 for [upsert](../../proposals/upsert.md), which adds two methods to `Map.prototype` and `WeakMap.prototype`: `getOrInsert`, which returns the value for a key or inserts a given value when the key is absent, and `getOrInsertComputed`, which takes a callback so the default can be computed lazily. Safari has shipped for a long time and Firefox more recently, both passing the full test262 suite, with additional implementations in V8, Porffor, Kiesel, and Boa, and the spec pull request has editor sign-off.

The conclusion was Stage 4, with multiple voices of support and no objections.

## Temporal update and needs-consensus PRs

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [proposal](https://github.com/tc39/proposal-temporal)
- slide: [link](https://ptomato.name/talks/tc39-2026-01/)

[PFC](../../people/PFC.md) (Igalia, in partnership with Bloomberg) reported that [Temporal](../../proposals/temporal.md) is closing in on Stage 4: test262 coverage expanded greatly, V8 and SpiderMonkey are within half a percentage point of 100% conformance and both are unflagged on the web, and GraalJS unflags in its next release. [Intl Era/Month Code](../../proposals/intl-era-month-code.md) is tracked in parallel so the two reach Stage 4 together. Two normative changes were proposed to eliminate surprises: a five-year-old `PlainYearMonth` subtraction bug found by snapshot testing, fixed by restricting `PlainYearMonth` arithmetic to years and months (PR #3253, with a behavior-preserving fallback in PR #3208), and `toLocaleString` of the Plain types depending on the formatter's time zone, fixed by PR #3246 on the principle that Plain types are wall-clock times.

The conclusion was consensus on both PR #3253 (restrict the arithmetic) and PR #3246 (drop the time-zone dependency); the fallback PR #3208 was not needed and is withdrawn.

## Intl Era/Month Code for Stage 3

- wiki: [Intl Era/Month Code](../../proposals/intl-era-month-code.md)
- slide: [link](https://notes.igalia.com/p/era-monthcode-stage-3-111th-plenary#/)

[BAN](../../people/BAN.md) (Igalia) presented the remaining normative changes and asked for Stage 3: Japanese-calendar dates before the 6 Meiji (1873) reform resolve as Gregorian; `islamic-rgsa` is removed from the `ca` option (never implemented as specified and unused — [SFC](../../people/SFC.md) called shipping it a pure footgun); the supported calendars become a closed list, following the precedent of units; a table of reference years handles extremely rare leap months and leap days (reject throws a `RangeError`, constrain clamps, e.g. February 29 to February 28); and a bugfix restores the pre-2025 Hebrew calendar difference behavior. [SFC](../../people/SFC.md) explained PR #111 as improving round-trippability where possible, and [MF](../../people/MF.md) confirmed it never makes that property worse.

The conclusion was that all the normative PRs were approved and the proposal reached Stage 3.

## Deferred re-exports update

- proposal: [proposal](https://github.com/tc39/proposal-deferred-reexports/)
- slide: [link](https://docs.google.com/presentation/d/1lrYTFTYrlhWTZ1tXdaMdJxcOWA7LU6AFkor339wNEkE/edit?slide=id.p#slide=id.p)

[NRO](../../people/NRO.md) (Igalia, with Bloomberg) reported on the two concerns that blocked Stage 2.7 last meeting: spec complexity (a pull request is addressing it) and the interaction with [import defer](../../proposals/import-defer.md). Because import defer forces namespace imports, a library using export defer is still fully loaded, so the benefits do not combine. Three directions were sketched: (1) export defer defers only execution, not loading; (2) list the bindings you care about, as in `import defer { mainThing } as ns`; (3) namespace imports do not load deferred re-exports by default. [DMM](../../people/DMM.md) liked option 2 and asked how unlisted bindings would error; [GB](../../people/GB.md) compared the scheme to Cargo features and prefers option 3, while [NRO](../../people/NRO.md) personally prefers option 2.

The conclusion was that there is no conclusion yet: the champions aim to reach consensus in the modules group by the next plenary and asked for delegates' first reactions.

## Withdraw function.sent

- proposal: [proposal](https://github.com/tc39/proposal-function.sent)

[JHD](../../people/JHD.md) asked to withdraw `function.sent`: originally championed by [AWB](../../people/AWB.md), it has not been presented since around 2016-17, and the champion who took it over ([JHX](../../people/JHX.md)) has not brought it back and no longer anticipates doing so. [MM](../../people/MM.md) recalled the original motivation (the fencepost problem when generators are used push-pull, where the first `next` call has nothing to push) and said he feels no urgency, but insisted the champion be consulted before withdrawal rather than set that precedent; [NRO](../../people/NRO.md) mentioned a marginal use case that came up around `AsyncContext` snapshots but did not object; [CDA](../../people/CDA.md) raised the same process point about the late agenda addition.

The conclusion was a conditional withdrawal, pending [JHX](../../people/JHX.md)'s approval — with a later update in the notes that [JHX](../../people/JHX.md) is still interested, so the proposal was not withdrawn.

## Import Sync for Stage 2

- wiki: [Import Sync](../../proposals/import-sync.md)
- proposal: [proposal](https://tc39.es/proposal-import-sync/)
- slide: [link](https://docs.google.com/presentation/d/1TGOmmWkAWx9NkmXCgh_IaoW-4aDhhRQyRSow980EOgU/edit?slide=id.g3b508911f70_0_0#slide=id.g3b508911f70_0_0)

[GB](../../people/GB.md) (Cloudflare) argued that non-standard sync importers (bun's `import.meta.require`, Node.js require-ESM) are proliferating, with use cases in built-in modules, already-registered modules, and module expressions/declarations. The spec reuses existing synchronous machinery (host resolution, [import defer](../../proposals/import-defer.md)'s sync evaluation) and throws a `NotSyncError` when a module is not synchronously available. [JHD](../../people/JHD.md) required that it work in scripts, which [GB](../../people/GB.md) accepted; [KG](../../people/KG.md) was satisfied it exposes already-synchronous module machinery rather than unwrapping a promise; [DLM](../../people/DLM.md) said Mozilla is not excited but would not block; [OFR](../../people/OFR.md), [KM](../../people/KM.md), and [NRO](../../people/NRO.md) probed racy use, a source-module design, and the main-thread/worker split.

The conclusion was Stage 2, with [GB](../../people/GB.md) stating that any Stage 2.7 would not be rushed and would require clear implementer support, resolved semantics for deadlocks and the source/defer phases, and strong motivating use cases. [NRO](../../people/NRO.md) volunteered as reviewer.

## Error option limit for stage 1

- proposal: [proposal](https://github.com/BridgeAR/error-limit-option)

[RBR](../../people/RBR.md) (Datadog) proposed a `limit` option in the error constructor options bag, bounding the stack frames captured for that individual error, as a standardized alternative to V8's global `Error.stackTraceLimit`, about 90% of whose usage is set-create-reset to cut cost or keep only the first frames. [NRO](../../people/NRO.md) supported it and recommended leaving what counts as a frame implementation-defined; [SHS](../../people/SHS.md) noted it covers only user-constructed errors; [DLM](../../people/DLM.md) asked whether the global API could ever be removed ([RBR](../../people/RBR.md): no, but usage should drop); [OFR](../../people/OFR.md) relayed concern about libraries hiding error frames. [MM](../../people/MM.md) asked that advancement be decided jointly with the framesAbove proposal.

The conclusion was Stage 1, called after the framesAbove discussion once a short problem statement (a standardized cross-engine way to control stack depth per error instance, without a global knob affecting unrelated errors) was read into the record, with support from [MM](../../people/MM.md), [DMM](../../people/DMM.md), [CZW](../../people/CZW.md), [JHD](../../people/JHD.md), and [SFC](../../people/SFC.md).

## Error option framesAbove for Stage 1

- proposal: [proposal](https://github.com/BridgeAR/error-frames-above)

[RBR](../../people/RBR.md) presented a second error options-bag property that hides the stack frames at and above a referenced method — the pattern behind about 90% of `Error.captureStackTrace` usage — without computing frames twice or counting hidden frames against the limit. [MM](../../people/MM.md) supported Stage 1 for both proposals but urged bringing them to TG3 soon; he also asked whether the Stage 2 `Error.captureStackTrace` proposal should be dropped ([DLM](../../people/DLM.md): engines cannot unship it, so standardize it anyway; [RBR](../../people/RBR.md) asked to postpone it and reassess in two years). [KG](../../people/KG.md), [JHD](../../people/JHD.md), and [CZW](../../people/CZW.md) clarified options-bag compatibility, and [PFC](../../people/PFC.md) warned a convenient hiding feature would become an alleged best practice that hurts debugging.

The conclusion was Stage 1, with support from [MM](../../people/MM.md), [DMM](../../people/DMM.md), and [JHD](../../people/JHD.md), after which the limit proposal was called and also reached Stage 1.
