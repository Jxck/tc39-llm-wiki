## Don't Remember Panicking Stage 1 Update

- wiki: [Don't Remember Panicking](../../proposals/dont-remember-panicking.md)
- proposal: [proposal-oom-fails-fast](https://github.com/tc39/proposal-oom-fails-fast/tree/master)
- slide: [link](https://github.com/tc39/proposal-oom-fails-fast/blob/master/panic-talks/dont-remember-panicking.pdf)

[MM](../../people/MM.md) (Mark Miller, Agoric) updated his Stage 1 proposal, renamed from "OOM Must Fail Fast" to "Don't Remember Panicking". The spec does not admit out-of-memory or stack exhaustion, but reality does: the prepare-commit pattern (moving money between accounts) is unimplementable under OOM, and browsers today throw-and-continue on best effort while XS fail-stops and reboots. The current shape is a `HostFaultHandler` host hook with a fault taxonomy: engine-internal corruption (fail-stop), engine intact but JS semantics broken (the browser OOM throw), JS-code trouble (an unhandled rejection), and user panic via `Reflect.panic`; the minimal abortable unit is a **dynamic agent cluster** (the transitive closure of synchronously coupled agents — HTML threads since 2017), supporting amnesia-before-confusion (the reboot/refresh/pacemaker story) in the spirit of Erlang's let-it-crash, with postmortem finalization. [DE](../../people/DE.md) worried `Reflect.panic` lets libraries halt whole programs (MM: equivalent to an infinite loop; Agoric made panic ambient for exactly that reason); [PFC](../../people/PFC.md) warned that panicking assert libraries would harm the web; [SYG](../../people/SYG.md) said the only realistic implementation of `Reflect.panic` is a process crash and browsers will not ship an API that looks like a render-process crash; [DLM](../../people/DLM.md) suggested a separate transaction proposal instead (MM: a low-level mechanism enables wider coping).

The conclusion was no conclusion — the topic continued in a continuation the same day, including a temperature check on viability without the panic API.

## Enums for Stage 1

- wiki: [Enums](../../proposals/enums.md)
- proposal: [proposal-enum](https://github.com/rbuckton/proposal-enum)
- slide: [link](https://1drv.ms/p/c/934f1675ed4c1638/EYypvengQohMlG52w1qseW8BCwCkSG0Y-2ip8Zq7pxoOFw?e=Aklyqu)

[RBN](../../people/RBN.md) (Ron Buckton, Microsoft) proposed standardizing enums. The ecosystem is full of enumerated values (`typeof` strings, DOM constants, buffer encodings, Node constants), and Node.js's type stripping cannot handle TypeScript enums because they are not erasable — this proposal is the erasable design. Advantages over an ObjectLiteral: a closed domain (non-configurable, non-writable members; non-extensible; null prototype), a restricted value domain (String/Number/BigInt/Boolean/Symbol), self-reference for bit flags and masks, and tooling recognition. Future directions: ADT enums (Option/Result) feeding extractors and pattern matching, decorators on enums, opt-in auto-initializers (`auto` keyword / `of` clause), and shared enums. Accepted divergences from TypeScript: no auto-numbering by default (a footgun), deprecating declaration merging (TS 6.0), reverse mapping likely dropped, and no `const enum`. [MM](../../people/MM.md) flagged that desugaring has pre-initialization visibility problems (TDZ, issue #25) but was enthusiastic: "I like this proposal… very excited about erasable TypeScript… enums were the biggest hole". [SYG](../../people/SYG.md) pressed on the adoption story — TypeScript must add syntactic distinctions for the divergent semantics — and asked for a browser-POV assessment of DX benefit versus runtime cost.

The conclusion was that the proposal advanced to Stage 1, with support from MM, PFC, JHX, CDA, and NRO.

## `Object.propertyCount` for stage 1 or 2

- wiki: [Object.propertyCount](../../proposals/object-propertycount.md)
- proposal: [object-property-count](https://github.com/ljharb/object-property-count)
- slide: [link](https://github.com/tc39/agendas/blob/main/2025/2025.04%20-%20Object.propertyCount%20slides.pdf)

[RBR](../../people/RBR.md) (Ruben Bridgewater, Invited Expert), presenting for the first time with [JHD](../../people/JHD.md) as co-champion, proposed `Object.propertyCount(target, options)`: today `Object.keys(obj).length` allocates an array just to count, and the pattern appears in production code across Angular, React, Node, and Next.js. The options bag can filter by key type (`'index'`, `'nonIndexString'`, `'symbol'`) and enumerability (`true`/`false`/`'all'`). [MF](../../people/MF.md) saw a performance-only proposal adding no new power — engines should optimize instead, as with `array.length` caching historically; [SYG](../../people/SYG.md) noted these patterns are not all in hot loops where optimizing tiers help, but was convinced by the aggregate cost. [KG](../../people/KG.md) was extremely skeptical of the index/non-index distinction and sparse-array fast paths ("I specifically don't want people doing that"), and [SYG](../../people/SYG.md) added that spec integer-index semantics and V8's internal notions diverge; [MM](../../people/MM.md) and [MAH](../../people/MAH.md) identified the crucial use case as an O(1) "does this array-like have any non-index properties", which SYG called a different problem statement.

The conclusion was Stage 1 (support from DE, KG, DJM, CDA, and JSH), with the skeptics' concerns as non-blockers.

## Explicit Resource Management

- wiki: [Explicit Resource Management](../../proposals/explicit-resource-management.md)
- proposal: [proposal-explicit-resource-management](https://github.com/tc39/proposal-explicit-resource-management)
- slide: [link](https://docs.google.com/presentation/d/1F4kLwEUvBmyyTWq06HQgiJypcCWm3uwOzVDzFQ0xauE/edit#slide=id.p)

[DLM](../../people/DLM.md) (Daniel Minor, Mozilla) reported that SpiderMonkey's implementation of [Explicit Resource Management](../../proposals/explicit-resource-management.md) is complete and in Nightly behind a flag, maintaining a runtime dispose list. The needs-consensus item: disallow `using` declarations in bare `case` statements, where switch fallthrough could skip disposal — without fallthrough, implementations can desugar `using` to try/finally. [RBN](../../people/RBN.md) filed the spec PR (rbuckton/ecma262#14), V8 is willing to rewrite its implementation, and support came from [MM](../../people/MM.md) (strongly), [JHD](../../people/JHD.md) ("switch is bad and it's ok if people can't use a new feature in it"), [PFC](../../people/PFC.md), and [NRO](../../people/NRO.md) (for Babel).

The conclusion was consensus to merge rbuckton/ecma262#14.

## Non-extensible applies to Private for stage 1, 2, 2.7

- wiki: [Non-extensible applies to Private](../../proposals/nonextensible-applies-to-private.md)
- proposal: [proposal-nonextensible-applies-to-private](https://github.com/syg/proposal-nonextensible-applies-to-private)
- slide: [keynote slides](https://github.com/syg/proposal-nonextensible-applies-to-private/blob/main/no-stamping-talks/non-extensible-applies-to-private.pdf)

[MM](../../people/MM.md) presented (SYG co-champion) a proposal extracted from [Stabilize](../../proposals/stabilize.md): adding a private field to a non-extensible object should throw a `TypeError` instead of silently succeeding. Today the behavior is counterintuitive; structs and composites need a fixed shape (extensibility plus return-override could force a shape change); and private-fields-as-syntax-WeakMap creates a hidden communications channel. The change is not backwards compatible: Google's usage counters show 0.000015% of page loads, six German websites (a Cadenza GIS deployment, Axial framework sites, a music festival site), and [SYG](../../people/SYG.md) is doing outreach. The proposal advanced rapidly through the stages in one session: Stage 1, then Stage 2 with [JHD](../../people/JHD.md) and [DE](../../people/DE.md) as reviewers (both signed off), then a conditional Stage 2.7 with [MF](../../people/MF.md) pending (KG and SYG approved).

The conclusion, confirmed later in the meeting, was that it reached Stage 2.7 once MF approved, completing the conditional advancement.

## Continuation of Object.propertyCount for stage 1 or 2

Resuming after the stage grant, [SYG](../../people/SYG.md) argued counting properties and the arrays problem (sparse arrays, the index/non-index split) are different problems and asked to keep them separate; [JHD](../../people/JHD.md)'s "avoid performance cliffs" framing was judged too broad (dictionary mode would creep back in). ## Continuation: Don't Remember Panicking

- wiki: [Don't Remember Panicking](../../proposals/dont-remember-panicking.md)
- proposal: [proposal-oom-fails-fast](https://github.com/tc39/proposal-oom-fails-fast/tree/master)
- slide: [link](https://github.com/tc39/proposal-oom-fails-fast/blob/master/panic-talks/dont-remember-panicking.pdf)

The OOM topic resumed. [SYG](../../people/SYG.md) asked what the host hook buys Agoric specifically; [MM](../../people/MM.md) answered that it helps the language, programmers, the committee, and the formal semantics by making OOM discussable at all. SYG retracted his earlier "not a violation of the spec" — it is one, though pedantically so, since conforming is impossible. [ABO](../../people/ABO.md) noted the HTML spec's "killing scripts" section already covers aborting execution, and [MF](../../people/MF.md) quipped of the host hook's contract: "We say _what_ it must return. We don't say _when_ it must return." On what browsers do today: [SYG](../../people/SYG.md) said Chrome kills the whole process — a dynamic agent cluster would be "pretty much unimplementable and nondeterministic" — and [MLS](../../people/MLS.md) said Safari kills the web content process. SYG is supportive of better specifying real-world resources but not of the host hook becoming a configurable toggle; he prefers an editorial reflection of reality. The two also clashed on process politics: SYG sees a single veto as concentrating procedural power, while MM cited the WHATWG precedent that browsers deciding among themselves should be publicly costly.

The conclusion, per the speaker's summary: extensive discussion, the proposal stays at Stage 1, and there was general agreement that Ecma262 should more robustly specify real-world resource handling.
