## Normative: add notation to PluralRules

- proposal: [ECMA-402 PR #989](https://github.com/tc39/ecma402/pull/989)
- notes: [link](https://notes.igalia.com/p/UpmK0K8eo)

[USA](../../people/USA.md) (Ujjwal Sharma, Igalia) presented a small normative PR adding a `notation` option to `Intl.PluralRules`. PluralRules is a selection API exposing locale plural categories (up to five or six in some languages), and when notation support (scientific, compact, etc.) was added to `NumberFormat` by Unified NumberFormat back in 2018 — e.g. Spanish has a separate plural category in the millions under compact notation — the matching PluralRules support was intended but slipped through the cracks. The PR stores the notation in a new internal slot and threads it into the options AO shared with `NumberFormat`, so both constructors accept the same notation values. TG2 approved it in April 2025. [DE](../../people/DE.md) supported, suggesting it be tracked and merged like a staged proposal once multiple implementations and tests exist, which USA noted is already covered by the ECMA-402 PR progress-tracking wiki.

The conclusion was consensus on the PR, with explicit support from [DE](../../people/DE.md) and [DLM](../../people/DLM.md).

## Normative: Mark sync module evaluation promise as handled

- proposal: [spec PR #3535](https://github.com/tc39/ecma262/pull/3535)
- slide: [link](https://docs.google.com/presentation/d/1kheOg1AZDj-T9n0O-0sbd5IBwvnjiODyJcK1Ez6Q0JU)

[NRO](../../people/NRO.md) (Nicolò Ribaudo, Igalia) presented a normative PR fixing how module evaluation rejections interact with the `HostPromiseRejectionTracker` hook. Non-cyclic Module Records (e.g. Synthetic or host-defined modules such as a WebAssembly import) return an already-settled promise from `Evaluate()` purely for API-signature consistency; the module machinery extracts the rejection by reading the promise's internal slots directly, so the host hook is never told the promise was handled — hosts fire a spurious `unhandledRejection` for a failure the spec machinery itself has already taken care of. The fix explicitly calls the host hook when the rejection is extracted (factored into a new abstract operation, shared with the import defer proposal). It is not observable on the web (which only has Source Text Module Records), and Node.js already behaves as the fixed spec would. [MM](../../people/MM.md), relaying a concern [MAH](../../people/MAH.md) had posted on the PR, objected that spec-internal promises become observable to hosts through the rejection-tracking hooks and may be reflected back to user code — he wanted the spec to advise hosts against this — while [KG](../../people/KG.md) argued the change makes the promises less observable in practice, not more.

The conclusion was that the PR was blocked: [MM](../../people/MM.md) withheld consensus pending [MAH](../../people/MAH.md), who could not be present that day, with explicit support from [SYG](../../people/SYG.md) and others — a follow-on topic later in the week resolved it.

## Note about changed behavior of `Array.fromAsync` after landing #2600

- wiki: [Array.fromAsync](../../proposals/array-from-async.md)
- proposal: [issue #39](https://github.com/tc39/proposal-array-from-async/issues/39#issuecomment-1526744932)

[KG](../../people/KG.md) (Kevin Gibbons, F5) gave a heads-up that landing [ecma262 PR #2600](https://github.com/tc39/ecma262/pull/2600/) changed the behavior of `Array.fromAsync` without any change to its spec text. The PR fixed the `for await` machinery so that when a synchronous iterator yields a promise that rejects, the async-wrapper closes the underlying iterator (a sync iterator cannot clean up the way an async iterable can) — a necessary change for the invariant that iterators are always closed. Since `Array.fromAsync` shares that machinery, its behavior changed too, which was easy to miss because the two live in different places in the spec. Test262 tests were updated in [PR #4450](https://github.com/tc39/test262/pull/4450); [JSC](../../people/JSC.md) noted V8 already passes while other engines do not yet, and that work on `Array.fromAsync` has resumed, hoping to reach Stage 4 within the year.

The conclusion was that this was a notification only — no consensus was requested.

## `AsyncContext` Stage 2 Update

- wiki: [AsyncContext](../../proposals/async-context.md)
- proposal: [proposal-async-context](https://github.com/tc39/proposal-async-context)
- slide: [link](https://docs.google.com/presentation/d/1YkSQIWxCQCLSe1WKFWpndEd-gdf9coE1HRYa_v_z5J0/)

[ABO](../../people/ABO.md) (Andreu Botella, Igalia) updated on `AsyncContext`, addressing Mozilla's earlier negative feedback with two clarifications: it is a power feature for library authors that improves the experience of their users, and it is independently valuable to front-end frameworks. React's transitions lose their context after an `await` (its docs call this a limitation of JavaScript, pending AsyncContext), Solid loses its tracking and ownership scopes, Svelte's server-side `getRequestEvent` has no client-side equivalent, and Vue's active component context only propagates with a build step. Testimonials followed: [CZW](../../people/CZW.md) described Bloomberg's internal framework using an AsyncContext-like mechanism to co-locate multiple application bundles in one environment, and SHS described Google's polyfill for interaction tracing where loose coupling (event listeners, signal effects, RPC middleware) leaves nowhere to pass tracing data explicitly. On web integration, the proposal moved from capturing a snapshot at `addEventListener` time (a leak: the snapshot stays alive with the listener) to a **dispatch context** model — context propagates from the API call that triggers the callback (e.g. `element.click()`), events from outside the agent run in the root context, and a scoped fallback mechanism covers server-side regions. [DLM](../../people/DLM.md) thanked the champions and found the use cases better stated, but Mozilla still sees a very large, case-by-case web-integration implementation cost that the use cases do not yet justify; [SYG](../../people/SYG.md) said Chrome remains positive despite unchanged concerns — having adopters on the record is rare; [DE](../../people/DE.md) pushed for a generic rule specifiable centrally (mostly inferable from WebIDL) rather than per-API work.

The conclusion, per the speaker's summary: multiple frontend frameworks are eagerly waiting for AsyncContext to ship, and while the use cases were found convincing, it is still unclear they are worth the web-integration implementation cost — browsers hold opposite opinions on that tradeoff.

## Temporal Update

On the long-standing concern about BigInt in the spec's internal computations, PFC showed a proof of concept representing epoch nanoseconds and time durations as a pair of 64-bit floats — no nonstandard integer sizes needed, handling even `Duration.prototype.total`'s extra-precise division correctly. ## Composite Keys for stage 1

- wiki: [Composite Keys](../../proposals/composite-keys.md)
- proposal: [proposal-composites](https://github.com/tc39/proposal-composites)
- slide: [link](https://docs.google.com/presentation/d/1n7lj_y02f4QjrTMvRGs3aZXt_zji5nSVYGhmVchMpvI/)

[ACE](../../people/ACE.md) (Ashley Claymore, Bloomberg), after three prior feedback presentations on this design space, proposed "composites" — a reimagining of the Records & Tuples problem space (its withdrawal was a separate agenda item the same day). The problem: two objects representing the same data are two entries in a `Set`, so developers resort to `JSON.stringify` keys with hand-rolled key sorting (CZW confirmed OpenTelemetry ships a custom HashMap doing exactly that). Composites are **frozen-from-birth, non-opaque objects** — not new primitives, no reliance on GC tricks — holding references to arbitrary values, with equality that recurses deeply while both sides are composites and falls back to SameValueZero (pointer equality) for ordinary objects; key order does not matter, and no user code can run during a comparison (WH verified). The equality surfaces in `Composite.equals`, `Map`/`Set` keys, and `Array.prototype.{includes, indexOf, lastIndexOf}` — but only when the argument is a composite, leaving existing semantics untouched. [SYG](../../people/SYG.md) laid out V8's preferred alternative — canonicalizing/interning in the factory so `===` keeps working — which ACE pushed back on: it concentrates cost at creation (the Records & Tuples implementation concern) and [MM](../../people/MM.md) argued canonicalization is impossible if non-registered symbols are allowed as keys (no canonical sorting exists, making it a history-dependent communications channel). [MF](../../people/MF.md) argued for SameValue over SameValueZero since -0 is observable inside composites, while [WH](../../people/WH.md) warned switching would break Map/Set semantics; [KG](../../people/KG.md) said the proposal "gives me everything I personally wanted from Records & Tuples"; [SYG](../../people/SYG.md) cautioned it should stay in the composite-key lane rather than becoming the general immutable-data story; [LCA](../../people/LCA.md) and [PFC](../../people/PFC.md) discussed that Temporal types would not work as composite keys out of the box.

The conclusion was consensus for Stage 1 (explicit support from JH, CDA, DLM/SpiderMonkey, MF, CZW, NRO, MM, SYG, and WH), with the canonicalization alternative and -0 handling to continue being discussed as part of Stage 1.

## Withdrawing Records & Tuples

- wiki: [Records & Tuples](../../proposals/records-and-tuples.md)
- proposal: [proposal-record-tuple](https://github.com/tc39/proposal-record-tuple)
- slide: [link](https://docs.google.com/presentation/d/1afxyqJthBWsOpBvmPFP-VOhT8KyVF_AQlXLj0nkY6v4/)

[ACE](../../people/ACE.md) returned to formally withdraw Records & Tuples: the proposal's core was adding new primitives, which never found a path forward, while the reimagined composites proposal had just reached Stage 1 the same day. [NRO](../../people/NRO.md)'s queue message: "RIP R&T, you'll be missed." [MM](../../people/MM.md) floated composites for Stage 2 on the spot, but [JHD](../../people/JHD.md) pointed out there is no spec text yet. [EAO](../../people/EAO.md) raised naming: "composite" is hard to remember (composite or composable?), and with the "record" space now cleared the name could be reclaimed — or "key" could lean into the use case; ACE was open to anything except "Record", which carries too much TypeScript precedent, and noted the direction question (key-oriented tool vs general data model) should be settled first.

The conclusion was that the Records & Tuples proposal has been withdrawn.
