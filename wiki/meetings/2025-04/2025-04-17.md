## Disposable AsyncContext for Stage 1

- wiki: [Disposable AsyncContext](../../proposals/disposable-asynccontext.md)
- proposal: [proposal-async-context-disposable](https://github.com/legendecas/proposal-async-context-disposable)
- slide: [link](https://docs.google.com/presentation/d/1p_rQ5UagJ3Bgwbds0NL-nBaR3ovJLmyHmKuRMJejs_Y/edit#slide=id.gc6f73a04f_0_0)

[CZW](../../people/CZW.md) (Chengzhong Wu, Bloomberg), [LCA](../../people/LCA.md) (Luca Casonato, Deno), and [GCL](../../people/GCL.md) (Gus Caplan, Deno Land Inc) proposed `using` support for `AsyncContext.Variable`, since `run` forces code into a new function scope — a refactoring hazard and a non-starter for test frameworks splitting setup/teardown ([SHS](../../people/SHS.md): jasmine). Three designs: **A** reuses `using` plus `Symbol.enter`, which can leak synchronously if not disposed; **B** has the `using` syntax itself perform enter/restore; **C** uses unforgeable internal slots, which fails across [ShadowRealm](../../proposals/shadowrealm.md) boundaries. [RBN](../../people/RBN.md) argued B and C break composition with DisposableStack and burden every `using`; [SYG](../../people/SYG.md) called B and C "deeply unpalatable", found A palatable, but urged patience since [AsyncContext](../../proposals/async-context.md) is only Stage 2; [DE](../../people/DE.md) called the feature useful but not essential.

The conclusion was Stage 1 (support from [CDA](../../people/CDA.md) and [ABO](../../people/ABO.md); [MM](../../people/MM.md): "I am very concerned about this and doubtful there's actually a feasible solution, but I am not objecting to Stage 1"), with concerns that B and C change `using` semantics while A allows library composition.

## WHATWG Observables

- proposal: [WICG/observable](https://github.com/WICG/observable)
- slide: [link](https://docs.google.com/presentation/d/1i5_zneksrU7i7ZHcl5EQRzUHGkmXRIQKd-bLfrPRNXY/)

[DMF](../../people/DMF.md) (Dominic Farolino, Google Chrome) gave an informal update on Observables, incubated in WICG for WHATWG DOM after starting as a 2015 TC39 Stage 1 proposal (co-champions [JH](../../people/JH.md) and [MM](../../people/MM.md)). An Observable is "a promise for multiple values": synchronous, lazy, with operators and `EventTarget.when()`; producers are multicast and ref-counted, with AbortSignal cancellation. It is implemented in Chrome and near-complete in WebKit. [MM](../../people/MM.md) lamented the venue change; [MAH](../../people/MAH.md) asked why subscribers are not iterator-shaped ([DE](../../people/DE.md): observables push and events should not buffer); [JSC](../../people/JSC.md) asked about Signal interoperability; [JRL](../../people/JRL.md) asked why `subscribe` returns nothing; [DE](../../people/DE.md) asked to keep operators aligned with iterator helpers and how TC39 could be a more attractive venue earlier.

The conclusion was positive overall feedback, with discussion about increasing early collaboration between WHATWG and TC39.

## Continuation: Normative: Mark sync module evaluation promise as handled (#3535)

- proposal: [spec PR #3535](https://github.com/tc39/ecma262/pull/3535)
- slide: [link](https://docs.google.com/presentation/d/1kheOg1AZDj-T9n0O-0sbd5IBwvnjiODyJcK1Ez6Q0JU)

[NRO](../../people/NRO.md) returned to Monday's blocked PR. [MAH](../../people/MAH.md)'s concern was that the `HostPromiseRejectionTracker` hook exposes spec-internal promises to the host; [NRO](../../people/NRO.md) walked through it with [MAH](../../people/MAH.md) and they concluded the change does not make things worse — it makes them better: most hosts queue unhandled-rejection notification until the promise queue drains, and this change marks the promise handled before draining, so the internal promise is effectively never exposed to a user callback. [MAH](../../people/MAH.md) noted other places in the spec create promises assumed to be internal, which a future holistic review should cover — the underlying worry being that exposing internal promise objects to user code invites mutation and reentrancy until spec and host code can handle promises safely. [MM](../../people/MM.md) confirmed he had held consensus on [MAH](../../people/MAH.md)'s behalf and was satisfied; both are no longer concerned.

The conclusion was positive consensus for the pull request.
