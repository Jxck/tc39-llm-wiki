## Disposable AsyncContext for Stage 1

- wiki: [Disposable AsyncContext](../../proposals/disposable-asynccontext.md)
- proposal: [proposal-async-context-disposable](https://github.com/legendecas/proposal-async-context-disposable)
- slide: [link](https://docs.google.com/presentation/d/1p_rQ5UagJ3Bgwbds0NL-nBaR3ovJLmyHmKuRMJejs_Y/edit#slide=id.gc6f73a04f_0_0)

[CZW](../../people/CZW.md) (Chengzhong Wu, Bloomberg), [LCA](../../people/LCA.md) (Luca Casonato, Deno), and [GCL](../../people/GCL.md) (Gus Caplan, Deno Land Inc) proposed `using` declaration support for `AsyncContext.Variable`. Today `AsyncContext.Variable.run` requires wrapping code in a new function scope — a refactoring hazard (a `break`/`return` no longer means what it did), and a non-starter for test frameworks that split setup/test/teardown across scopes (SHS raised jasmine as the example), so tracing libraries cannot adopt AsyncContext without rewriting their users' control flow. Three solutions were presented: **A** reuses the `using` machinery plus the Stage 1 "enforced using declaration" proposal (`Symbol.enter`) — enter captures and swaps, dispose enforces a balanced stack, and a manual `Symbol.enter` without dispose can leak synchronously, but only visibly to holders of the Variable instance (test frameworks might even want that; cf. `AsyncLocalStorage.enterWith`); **B** has `Symbol.enter` only record intent while the using syntax performs the enter/restore — no synchronous leak, but it hard-codes AsyncContext machinery into every `using` regardless of the RHS; **C** puts unforgeable internal enter/exit slots on `AsyncContext.Scopable`, callable only by the syntax — which cannot work through ShadowRealm callable boundaries. [RBN](../../people/RBN.md) argued B and C break the composition intuition with DisposableStack, and that spec-wise every `using` would pay for AsyncContext snapshot machinery ([NRO](../../people/NRO.md): a snapshot is just a pointer copy; RBN: still overhead in shared-struct locks); [SYG](../../people/SYG.md) called B and C "deeply unpalatable" and found A palatable, but urged patience — the dependency chain is too young (AsyncContext is Stage 2, `using` has shipped only in Chrome); [DLM](../../people/DLM.md) seconded; [DE](../../people/DE.md) said the feature is not essential for AsyncContext (`run` suffices, and `enterWith` ergonomics matter more to the Node.js community) but is useful feedback either way.

The conclusion was that the proposal advanced to Stage 1 (support from CDA and ABO; RBN supports exploring with concerns on B and C; [MM](../../people/MM.md): "you heard negative comments. You have not heard objections to Stage 1. I am very concerned about this and doubtful there's actually a feasible solution, but I am not objecting to Stage 1"). Per the summary: concerns with B and C as they change `using` semantics; solution A allows library composition and syntax integration.

## WHATWG Observables

- proposal: [WICG/observable](https://github.com/WICG/observable)
- slide: [link](https://docs.google.com/presentation/d/1i5_zneksrU7i7ZHcl5EQRzUHGkmXRIQKd-bLfrPRNXY/)

DMF (Dominic Farolino, Google Chrome) gave an informal update on Observables — not a TC39 proposal, but incubated in WICG for upstreaming into WHATWG DOM, presented here because the space started in this committee. History: a TC39 Stage 1 proposal in 2015 (Ben Lesh of RxJS; co-champions JH and [MM](../../people/MM.md)), moved to WHATWG in 2017, revived in WICG with a spec and a Chromium implementation. An Observable is "a promise for multiple values": synchronous delivery, lazy (the producer runs on subscribe), with operators like `filter`/`map` and `EventTarget.when()` as a better `addEventListener`. The producer is multicast and ref-counted — teardown happens only when the last subscriber aborts (a deliberate deviation from userland precedent after TPAC feedback), with cancellation via AbortSignal and resubscription reigniting the producer. Status: implemented in Chrome, near-complete in WebKit (which wanted TC39 feedback first), the most-reacted web standards issue on GitHub, and neutral-to-positive feedback from Mozilla, Node, and WinterCG. In discussion, MM lamented the venue change (DMF: the EventTarget integration and the AbortController/AbortSignal dependency motivated it; [DE](../../people/DE.md) hoped TC39 and WHATWG would design together rather than claim territory); [MAH](../../people/MAH.md) was surprised the subscriber is not iterator-shaped (DE: iterators are pull and bufferable, observables push and events should not buffer); [JSC](../../people/JSC.md) asked for early Observable↔Signal interoperability work (DE: conversion is a couple of lines via `Signal.subtle.watched`/`unwatched`, but the use cases must not be confused — Observables misused for reactive rendering cause glitches); [JRL](../../people/JRL.md) asked why `subscribe` returns nothing (DMF: a synchronously-producing producer could run forever before `subscribe` returns — abort happens inside the handlers); DE asked about keeping operators synchronized with iterator helpers (DMF intends to); and DE asked how TC39 can be a more attractive venue earlier — [SYG](../../people/SYG.md): reputationally, the process-improvement proposals would help.

The conclusion was positive overall feedback, with discussion about increasing early collaboration between WHATWG and TC39.

## Continuation: Normative: Mark sync module evaluation promise as handled (#3535)

- proposal: [spec PR #3535](https://github.com/tc39/ecma262/pull/3535)
- slide: [link](https://docs.google.com/presentation/d/1kheOg1AZDj-T9n0O-0sbd5IBwvnjiODyJcK1Ez6Q0JU)

[NRO](../../people/NRO.md) returned to Monday's blocked PR. [MAH](../../people/MAH.md)'s concern was that the `HostPromiseRejectionTracker` hook exposes spec-internal promises to the host; NRO walked through it with MAH and they concluded the change does not make things worse — it makes them better: most hosts queue unhandled-rejection notification until the promise queue drains, and this change marks the promise handled before draining, so the internal promise is effectively never exposed to a user callback. [MAH](../../people/MAH.md) noted other places in the spec create promises assumed to be internal, which a future holistic review should cover — the underlying worry being that exposing internal promise objects to user code invites mutation and reentrancy until spec and host code can handle promises safely. [MM](../../people/MM.md) confirmed he had held consensus on MAH's behalf and was satisfied; both are no longer concerned.

The conclusion was positive consensus for the pull request.
