## Needs-consensus PR: Support BigInt coercion of integers expressed as exponential-notation strings

- wiki: [BigInt from exponential](../../proposals/bigint-from-exponential.md)
- Slides: [link](https://docs.google.com/presentation/d/1kPYmR8LkoV4AZpSM_ezHCyR2givdk9OiQlwiXHdah4M/edit?usp=drive_link)
- 前回持ち越しの needs-consensus PR(#3857)の再議。整数を表す指数表記文字列(例 `1.5e2`)を `BigInt(string)` で受理し `Number(string)` と揃える提案。[Amount](../../proposals/amount.md) の canonical form(指数表記文字列)が `BigInt` に変換できない問題が発端。
- [MF](../../people/MF.md) は「なぜ bigint を指数表記で書きたいのか分からない」と constructor の拡張に反対し、`BigInt.parse` のような別 method を選好。[KM](../../people/KM.md) は decimal point の許容が混乱を招くと指摘、[RGN](../../people/RGN.md) は有効数字(`1.000e3` と `1e3` の区別)が [Amount](../../proposals/amount.md) に必要と応答。
- [EAO](../../people/EAO.md) は「`BigInt(string)` と `BigInt.parse(string)` が異なる parse をするのは驚きだ」と反対([WH](../../people/WH.md) も +1)。[OFR](../../people/OFR.md) は literal 用途と動的 parse 用途を区別すべきで、[Amount](../../proposals/amount.md) が最終形に達するまで待つべきとも。
- 議論の形勢を受け [RGN](../../people/RGN.md) 自身も staged proposal 化に同意し、その場で Stage 1 を要求。[WH](../../people/WH.md) / [MF](../../people/MF.md) / [JSL](../../people/JSL.md) が明示的に支持。
- 結論: PR は proposal-bigint-from-exponential に転換し **Stage 1 到達**。string parsing と bigint literal 構文拡張の両方をスコープに含めて検討する。

## Needs-consensus PR: make `Promise.try` use PromiseResolve in non-error case

- Slides: [link](https://docs.google.com/presentation/d/1x7FdF7RdGBCI6TVHrbtBMAw5tvXI2mMDthqcd5n8rc4/edit?slide=id.g106f4536d9_0_109#slide=id.g106f4536d9_0_109)
- `Promise.try` が callback の返り値を常に新しい Promise で wrap する現行挙動を、非エラー時は `Promise.resolve` 相当(native Promise ならそのまま返す)に変える normative change(PR #3883)。[KG](../../people/KG.md) が提示。
- `Promise.resolve(func())` + 同期エラー捕捉という直観に一致させ、microtask 2 tick を節約する。async iterator helpers の実装中に順序が乱れたのが動機。userland 実装の模倣に由来する挙動で、[JHD](../../people/JHD.md) も championing 時に意識していなかったとのこと。
- 出荷済み機能の変更だが、microtask 順序や Promise の identity への依存は稀で web 互換と見込む。[MF](../../people/MF.md) / [CM](../../people/CM.md) / [ACE](../../people/ACE.md)(「down with the ticks」)/ [DLM](../../people/DLM.md) / [WH](../../people/WH.md) が支持。
- 結論: 変更に consensus。test262 のテストを先に merge し、実装が追従してから spec PR を land する。

## Import Defer Stage 3 updates

- Slides: [link](https://docs.google.com/presentation/d/1pH5SCZRJaN-HFeOn0WZ9KD64vvunPZdxhyYuMMHZLC8)
- 実装状況: V8 / JSC は flag 付き実装済み(V8 は fuzzing 中)、Deno と Bun はデフォルト有効で出荷済み、Node.js / SpiderMonkey は作業中。
- V8 の fuzzer が発見した spec バグ(issue #85)を報告: TLA を含む cycle で module の status を module 自身で見ているため、`GatherAsynchronousTransitiveDependencies` / `ReadyForSyncExecution` が cycle をまたぐ依存を見落とし assertion が壊れる。`[[CycleRoot]]` の status を見る `IsModuleSccEvaluated` に置き換える修正を提案。[KM](../../people/KM.md) は module loader の不変条件の機械検証を提起([NRO](../../people/NRO.md): MBH と PhD 学生が形式化作業中)。
- issue #83(deadlock になる cycle の扱い)は、defer なしでも同型の deadlock が起きるため spec は変えず WPT テスト側を直す方針。issue #82(synthetic module への `import defer` 禁止)は、best effort の設計原則を保ち throw しない方針([JSL](../../people/JSL.md) は実装裁量を要望、[NRO](../../people/NRO.md) は linter で警告すべきと補足。[JHD](../../people/JHD.md) / [OFR](../../people/OFR.md) も throw に反対)。
- 結論: issue #85 の修正(`[[CycleRoot]]` 参照への変更)に consensus。#83 / #82 は spec を変えず champion group の方針どおり。
