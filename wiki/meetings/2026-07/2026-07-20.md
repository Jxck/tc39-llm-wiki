## Needs-consensus PR: Support BigInt coercion of integers expressed as exponential-notation strings

- wiki: [BigInt from exponential](../../proposals/bigint-from-exponential.md)
- slide: [link](https://docs.google.com/presentation/d/1kPYmR8LkoV4AZpSM_ezHCyR2givdk9OiQlwiXHdah4M/edit?usp=drive_link)
- Revisit of the needs-consensus PR carried over from last time (#3857). It would make `BigInt(string)` accept an exponential-notation string that denotes an integer (for example `1.5e2`), lining it up with `Number(string)`. The trigger was that [Amount](../../proposals/amount.md)'s canonical form (an exponential-notation string) cannot be converted to `BigInt`.
- [MF](../../people/MF.md) opposed extending the constructor: "I don't understand why anyone would want to write a bigint in exponential notation," and preferred a separate method such as `BigInt.parse`. [KM](../../people/KM.md) said allowing a decimal point would be confusing. [RGN](../../people/RGN.md) replied that Amount needs the significant digits (the distinction between `1.000e3` and `1e3`).
- [EAO](../../people/EAO.md) objected: "It would be surprising if `BigInt(string)` and `BigInt.parse(string)` parsed differently" ([WH](../../people/WH.md) agreed, +1). [OFR](../../people/OFR.md) said literal use and dynamic parsing should be kept apart, and that the committee should wait until Amount has a final shape.
- Given how the discussion was going, [RGN](../../people/RGN.md) agreed to turn it into a staged proposal and asked for Stage 1 on the spot. [WH](../../people/WH.md) / [MF](../../people/MF.md) / [JSL](../../people/JSL.md) supported that explicitly.
- Conclusion: the PR was converted into proposal-bigint-from-exponential and **reached Stage 1**. Both string parsing and an extension of bigint literal syntax are in scope.

## Needs-consensus PR: make `Promise.try` use PromiseResolve in non-error case

- wiki: [Promise.try](../../proposals/promise-try.md)
- slide: [link](https://docs.google.com/presentation/d/1x7FdF7RdGBCI6TVHrbtBMAw5tvXI2mMDthqcd5n8rc4/edit?slide=id.g106f4536d9_0_109#slide=id.g106f4536d9_0_109)
- Normative change (PR #3883), presented by [KG](../../people/KG.md): today `Promise.try` always wraps the callback's return value in a fresh Promise. In the non-error case it would instead behave like `Promise.resolve` (a native Promise is returned as-is).
- That matches the intuition of `Promise.resolve(func())` plus synchronous error capture, and saves two microtask ticks. The motivation was ordering going wrong while implementing async iterator helpers. The current behavior comes from copying a userland implementation, and [JHD](../../people/JHD.md) said they had not been aware of it while championing the feature.
- It changes a shipped feature, but dependence on microtask order or Promise identity is rare and it is expected to be web-compatible. [MF](../../people/MF.md) / [CM](../../people/CM.md) / [ACE](../../people/ACE.md) ("down with the ticks") / [DLM](../../people/DLM.md) / [WH](../../people/WH.md) supported it.
- Conclusion: consensus on the change. Land the test262 tests first, and land the spec PR after implementations catch up.

## Import Defer Stage 3 updates

- wiki: [import defer](../../proposals/import-defer.md)
- proposal: [proposal](https://tc39.es/proposal-defer-import-eval/)
- slide: [link](https://docs.google.com/presentation/d/1pH5SCZRJaN-HFeOn0WZ9KD64vvunPZdxhyYuMMHZLC8)
- Implementation status: V8 and JSC have implementations behind a flag (V8 is fuzzing), Deno and Bun have shipped it enabled by default, and Node.js and SpiderMonkey are in progress.
- A spec bug found by the V8 fuzzer (issue #85): in a cycle that contains TLA, the module looks at its own status, so `GatherAsynchronousTransitiveDependencies` / `ReadyForSyncExecution` miss dependencies that cross the cycle and an assertion breaks. The proposed fix replaces that with `IsModuleSccEvaluated`, which looks at the `[[CycleRoot]]` status. [KM](../../people/KM.md) raised mechanically checking module-loader invariants ([NRO](../../people/NRO.md): MBH and a PhD student are formalizing this).
- Issue #83 (cycles that deadlock): the same shape of deadlock happens without defer, so the spec stays as it is and the WPT test is fixed instead. Issue #82 (forbidding `import defer` of a synthetic module): keep the best-effort design principle and do not throw ([JSL](../../people/JSL.md) wanted implementation discretion; [NRO](../../people/NRO.md) added that a linter should warn. [JHD](../../people/JHD.md) / [OFR](../../people/OFR.md) also opposed throwing).
- Conclusion: consensus on the issue #85 fix (consult `[[CycleRoot]]`). #83 and #82 do not change the spec; the champion group's plan stands.

## Thenable Curtailment for 2.7

- wiki: [Thenable Curtailment](../../proposals/thenable-curtailment.md)
- proposal: [proposal](https://github.com/tc39/proposal-thenable-curtailment)
- slide: [link](https://docs.google.com/presentation/d/1kHq_UqMHGGT8ena8yMlJKgHmohDVqxJvV4hiCB12HtU/view?)
- [MAG](../../people/MAG.md) asked for Stage 2.7. The goal is `SafePromiseResolve`, which resolves a Promise without running user code, and to have WebIDL's Promise resolve steps adopt it so the attack surface through thenables is closed. Firefox has a prototype behind about:config; a month of daily use found no breakage.
- The disputed point was that the response to [NRO](../../people/NRO.md)'s review (objects whose internal methods differ from an ordinary object) was heavy-handed enough to "penalize even TypedArrays." [KG](../../people/KG.md) proposed making it a host hook (something like `HostIsSafeToResolve`, defaulting to false), and [MAG](../../people/MAG.md) agreed.
- [JRL](../../people/JRL.md) argued for advancing immediately: "This is a known security vulnerability, and the TypedArray issue is not observable. We should not delay it by two months." [NRO](../../people/NRO.md) / [KG](../../people/KG.md) corrected that it is observable if you install a `.then` getter, and said the host-hook spec text should be written before advancing.
- Conclusion: carried over to a continuation on Wednesday (Day 3). [KG](../../people/KG.md) will help write the host-hook spec text, and advancement will be sought after sign-off from the editors and the reviewers ([JRL](../../people/JRL.md) and [JHD](../../people/JHD.md)).

## Map take for stage 1, 2, or 2.7

- wiki: [Map get and delete](../../proposals/map-get-and-delete.md)
- proposal: [proposal-Map-take](https://github.com/dcrousso/proposal-Map-take)
- Presented by [DRO](../../people/DRO.md). Adds `take` to `Map` and `WeakMap`: get a value and delete it at the same time (get + delete in one hash lookup). Motivated by the common pattern of temporarily holding a pending callback or an in-flight request.
- [KG](../../people/KG.md) would support advancement under **any name other than take** (`getOrDelete`, `extract`, and so on), because the meaning is too different from `Iterator.prototype.take`. [MM](../../people/MM.md) argued it should also exist on Set (both, or neither), and [DRO](../../people/DRO.md) agreed.
- Time ran out and the discussion stopped midway.
- Conclusion: out of time; continuation on Day 2 (the queue carries over).
