## Continuation: Map take for stage 1, 2, or 2.7

- wiki: [Map get and delete](../../proposals/map-get-and-delete.md)
- proposal: [proposal-Map-take](https://github.com/dcrousso/proposal-Map-take)
- Continuation from the previous day. [DRO](../../people/DRO.md) proposed a new method that gets a value from a Map or WeakMap and deletes the entry in one operation, and asked for Stage 1 (2 or 2.7 if possible). [JSL](../../people/JSL.md) / [ACE](../../people/ACE.md) / [DLM](../../people/DLM.md) / [MF](../../people/MF.md) and others supported Stage 1.
- [KG](../../people/KG.md) / [MF](../../people/MF.md) / [CM](../../people/CM.md) objected to the name colliding with `Iterator.prototype.take`, and the direction became a rename to `getAndDelete`. [MM](../../people/MM.md) / [WH](../../people/WH.md) had asked about Set and WeakSet for symmetry, but Set has no `get` and `delete` already reports presence, so it is unnecessary ([MF](../../people/MF.md) / [NRO](../../people/NRO.md); [WH](../../people/WH.md) agreed).
- Returning `undefined` when the key is absent is the same ambiguity `Map.prototype.get` already has ([KG](../../people/KG.md)). [MF](../../people/MF.md) asked that exploring that design space, not this method alone, be a precondition for Stage 2.
- [CDA](../../people/CDA.md) / [MF](../../people/MF.md) were against an immediate Stage 2. [ACE](../../people/ACE.md) volunteered in advance as a spec reviewer.
- Conclusion: **reached Stage 1**. Rename to `getAndDelete`, do not add it to Set or WeakSet, and keep looking for a way to distinguish an `undefined` value from a missing key.

## JSON.parseImmutable

- proposal: [proposal-json-parseimmutable](https://github.com/tc39/proposal-json-parseimmutable)
- Update on a Stage 2 proposal that started as a companion to [Records & Tuples](../../proposals/records-and-tuples.md). After that withdrawal it continues as "a JSON parse that returns a deeply frozen object." PKA / [ACE](../../people/ACE.md) reported the state of the open issues.
- The champions prefer the name `JSON.parseFrozen`. [KG](../../people/KG.md) suggested `parseToFrozen`. [EAO](../../people/EAO.md) strongly preferred passing an options bag to `JSON.parse` (`frozen: true`).
- [KG](../../people/KG.md) / [MF](../../people/MF.md) strongly supported a null prototype on the result (a defense against the security bug of reaching the Function constructor through the prototype). [KG](../../people/KG.md) noted that frozen and null prototype could be separate, orthogonal options.
- For the reviver, [KG](../../people/KG.md)'s idea of passing the options bag in the second-argument reviver slot was well received ([ACE](../../people/ACE.md) / [EAO](../../people/EAO.md) supported it). [KG](../../people/KG.md) / PKA settled that the default should stay the current behavior (mutable). [LGH](../../people/LGH.md) wanted the same shape mirrored onto [JSON modules](../../proposals/json-modules.md) ([import attributes](../../proposals/import-attributes.md)).
- Conclusion: no formal consensus, but a favorable reaction to moving to an options-bag API. Work continues and will come back to the committee.

## Error code property for Stage 2 or 2.7

- wiki: [Error code property](../../proposals/error-code-property.md)
- proposal: [proposal-error-code-property](https://github.com/tc39/proposal-error-code-property)
- [JSL](../../people/JSL.md) asked for Stage 2 (2.7 if possible) for adding `code` to Error as a non-enumerable own property, the same shape as `cause`. Spec text, a test262 draft, and a V8 draft implementation are in place, and editor review has started.
- The only open point was the clash with DOMException raised by [AVK](../../people/AVK.md). DOMException has a numeric `code` as a prototype getter, but [KG](../../people/KG.md) explained that WHATWG treats that as legacy and uses `.name`. [JSL](../../people/JSL.md) / [JHD](../../people/JHD.md) took the position that there is no real conflict, and [JSL](../../people/JSL.md) said that switching the ecosystem convention over to `.name` would itself be breaking.
- [KG](../../people/KG.md) opposed going past Stage 2 without a coherent story for DOMException. [KM](../../people/KM.md) / [MM](../../people/MM.md) / [CDA](../../people/CDA.md) also supported stopping at 2 rather than 2.7, and [LVU](../../people/LVU.md) agreed, suggesting DOMException could bridge the gap with an options bag. [MM](../../people/MM.md) supported it after confirming that SuppressedError also gains an options bag and can be passed `cause` / `code`.
- Conclusion: **reached Stage 2**. Further advancement is conditional on alignment with DOMException, and the committee asked for that path to be filed as an issue on the proposal.

## Declarations in Conditionals for Stage 2 or 2.7

- proposal: [proposal-Declarations-in-Conditionals](https://github.com/tc39/proposal-Declarations-in-Conditionals)
- [DRO](../../people/DRO.md) asked for Stage 2 for allowing a variable declaration in the condition of `if` / `while`. There is now formal spec text, and the design was updated so the binding is not visible in `else` (a reference is a TDZ ReferenceError).
- Visibility in `else` was the main dispute. [OFR](../../people/OFR.md) / NPU strongly wanted it visible, as in C++. [KG](../../people/KG.md) / [MF](../../people/MF.md) / [CM](../../people/CM.md) / [MM](../../people/MM.md) supported keeping it invisible. [KG](../../people/KG.md) cited early disposal of `using` as the biggest motivation.
- There was no support for a runtime TDZ error. [KM](../../people/KM.md) / [MM](../../people/MM.md) / [WH](../../people/WH.md) argued for an early error (SyntaxError, or an early ReferenceError), and [DRO](../../people/DRO.md) agreed. [LVU](../../people/LVU.md) / [JRL](../../people/JRL.md) preferred resolving to an outer binding, as block scoping would.
- [JHD](../../people/JHD.md) relayed the position of the absent [RBN](../../people/RBN.md) and blocked Stage 2 / 2.7 because the cross-cutting concern with pattern matching is unresolved. [MM](../../people/MM.md) also opposed advancing now, from the point of view of refutable patterns. [MF](../../people/MF.md) set the deadline for that alignment at one meeting from now.
- Conclusion: no advancement. Alignment with the pattern matching champions, and the decision of whether a binding reference in `else` is an early error or is allowed, both carry over.

## Async iterator helpers open questions

- proposal: [proposal](https://github.com/tc39/proposal-async-iterator-helpers)
- slide: [link](https://docs.google.com/presentation/d/17_mL3guxupbKWKr1EbDdML9K9kPTqElbf9xgoZZDBh0)
- [KG](../../people/KG.md) gave a design update on concurrent async iterator helpers (map / filter / flatMap, and buffered), with no request to advance. A userland implementation and an interactive demo are public. The design principles: order-preserving, the helper owns the underlying iterator, no values are lost, and `{done: false}` after `{done: true}` is incoherent.
- The committee agreed on a fast path that skips the await microtask tick when a mapper or predicate returns a primitive, with support from [NRO](../../people/NRO.md) / [JHD](../../people/JHD.md).
- The disputes were defending against an incoherent underlying iterator, and early out-of-order delivery, which only map can do. [MM](../../people/MM.md) preferred the defensive side (no early delivery) for consistency with filter. [WH](../../people/WH.md) / [KG](../../people/KG.md) / [SHS](../../people/SHS.md) / [RGN](../../people/RGN.md) opposed making well-behaved users pay for the ill-behaved case.
- Error ordering was also sorted out, including awaiting the underlying `return` before delivering the error when the mapper throws. Time ran out; the remaining open questions go to the next meeting.
- Conclusion: the committee agreed to skip the await for a primitive return value. The other open questions stay unresolved and need more discussion time.

## Composites update

- proposal: [proposal](https://github.com/tc39/proposal-composites)
- slide: [link](https://docs.google.com/presentation/d/1vTRHdRzIZQF69Q5Nx_VDkCkm2mn1rJK-CTtDiSqA9x0/)
- Update on composites, the successor to [Records & Tuples](../../proposals/records-and-tuples.md) for compound Map and Set keys. [ACE](../../people/ACE.md) presented benchmarks of experimental implementations with and without interning. Both beat `JSON.stringify`, with the winner depending on key size and iteration count.
- [MM](../../people/MM.md) strongly supported interning not for performance but because it avoids revising the spec for Map, Set, and `Array.prototype.includes` ([SHS](../../people/SHS.md) also +100). [ACE](../../people/ACE.md) noted a polyfill would not need to patch existing methods.
- Storing composites in a WeakMap or WeakSet is heading toward being forbidden across the board, following the registered-Symbol precedent ([MM](../../people/MM.md)).
- Whether `{a: 1}` and `{a: 1, b: undefined}` are the same key (dropping `undefined`) split the room. [ACE](../../people/ACE.md) / [EAO](../../people/EAO.md) preferred dropping it. [MF](../../people/MF.md) / [KG](../../people/KG.md) opposed that and said `undefined` should be respected as an ordinary value.
- Conclusion: pivot to the interning approach, and do not allow weak retention of composites. The treatment of `undefined` stays under discussion and will come back to the committee before a Stage 2 request.
