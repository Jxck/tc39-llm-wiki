## Decimal stage 1 update

- wiki: [Decimal](../../proposals/decimal.md)
- slide: [link](https://notes.igalia.com/p/tc39-2026-07-decimal/)
- [CLA](../../people/CLA.md) presented a [Decimal](../../proposals/decimal.md) (Stage 1) update in place of [JMN](../../people/JMN.md). The problem is that binary float64 betrays what programmers who "think in base 10" expect (the 0.1 + 0.2 problem). The current design was restated: decimal128 (34 significant digits, normalized only for toString and comparison) and an object-based API.
- [Amount](../../proposals/amount.md) / [Intl Keep Trailing Zeros](../../proposals/intl-keep-trailing-zeros.md) cover preserving and transporting precision, and `Math.fma` / `Math.sumPrecise` cover reducing rounding error, but the core — arbitrary [decimal](../../proposals/decimal.md) arithmetic — is still unsolved. [EAO](../../people/EAO.md) framed [Amount](../../proposals/amount.md) as something that could be used for an internal conversion if [decimal](../../proposals/decimal.md) arrives, but that does not depend on it. [WH](../../people/WH.md) added that [Amount](../../proposals/amount.md) is a different problem (0.1 yards → feet still leaves a rounding).
- [JHD](../../people/JHD.md) restated the long-standing Stage 2 blocking concern: "an object API does not solve it; it should be a primitive." [KM](../../people/KM.md) opposed a new primitive because it is a change that cuts across the whole engine and is not worth it unless the developers who use it every day are in the double-digit percents. [DLM](../../people/DLM.md) agreed.
- [ACE](../../people/ACE.md) said that from real use at Bloomberg an object API works well enough, and that not being a primitive should not be blocking.
- Conclusion: time ran out with the concern about an object API and the browsers' concern about a primitive still side by side. Discussion continues on GitHub and elsewhere.

## Duration units in Amount and Intl Sequence Units

- wiki: [Intl Sequence Units](../../proposals/intl-sequence-units.md), [Amount](../../proposals/amount.md)
- slide: [link](https://tc39.es/proposal-intl-sequence-units/slides/time-units.html)
- [SFC](../../people/SFC.md) raised how time and duration units should be treated in sequence units (foot-and-inch and the like). TG2 was split, so both positions were brought to plenary with no recommendation.
- Position 1 (exclude): durations are full of footguns (DST, the length of a calendar month), and there is already a proper path that took nine years in [Temporal](../../proposals/temporal.md) plus `Intl.DurationFormat`. Adding a degraded version to `Intl.NumberFormat` would become a long-term pain point. Position 2 (include): alignment with CLDR units.xml, the ergonomics of `convertTo`, and avoiding a branch just for time in generic unit-conversion code. [WH](../../people/WH.md) supported position 2.
- [PFC](../../people/PFC.md) argued that it is important not to create a second mechanism whose duration-conversion rules differ from [Temporal](../../proposals/temporal.md). [SFC](../../people/SFC.md) replied that even if conversion is allowed, [Temporal](../../proposals/temporal.md)'s constraints (what is possible without a relative-to) are the ceiling, which diverges from CLDR, where months and years can be converted. [SFC](../../people/SFC.md) / [PFC](../../people/PFC.md) will look closely at units.xml for months and quarters.
- [RGN](../../people/RGN.md) argued that it would be perverse for [Amount](../../proposals/amount.md), which allows any well-formed unit string, to reject only time units, and that expressing sequence time units and converting them in line with CLDR should be supported. [EAO](../../people/EAO.md) also raised a new question: should `toLocaleString` on a time [Amount](../../proposals/amount.md) accept DurationFormat options?
- Conclusion: keep iterating on the proposal in light of the new angles (a hybrid, and automatically choosing NumberFormat or DurationFormat when formatting an [Amount](../../proposals/amount.md)).

## Linear Matching

- wiki: [Linear Matching](../../proposals/linear-matching.md)
- slide: [link](https://docs.google.com/presentation/d/19Y18Lt165cSwqLI7K7aeA6IbSp9FOC1psrC2_MfaLs4/edit)
- [MF](../../people/MF.md) asked for Stage 1 on behalf of a champion group with [AUR](../../people/AUR.md) / [CPC](../../people/CPC.md). The problem is ReDoS: a regexp evaluated in super-linear time hangs unrecoverably. It is a vulnerability class that constantly produces CVEs, linters cannot detect it reliably, and there is no built-in mitigation.
- Candidate solutions, not fixed at Stage 1: asking the engine whether linear execution is possible, an exec variant with a linear guarantee, a regex flag, falling back to a linear implementation after a timeout or resource limit, and specifying a subset that is guaranteed linear.
- [KG](../../people/KG.md) / [OFR](../../people/OFR.md) / [KM](../../people/KM.md) were concerned about an API that exposes differences between engines or between versions (once you have answered "linear," you cannot unship it). [CPC](../../people/CPC.md) replied that defining a "subset that must be linear" in the spec would make implementations uniform. [OFR](../../people/OFR.md) said V8's experimental linear engine has no ship plan, that backtracking wins on average performance so it must be opt-in, and that the cost of carrying a second engine is high.
- [WH](../../people/WH.md) / [AUR](../../people/AUR.md) flagged that "linear" is only in the length of the input and can still be exponential in the length of the regex. [MM](../../people/MM.md) opposed solutions that introduce dynamic non-determinism such as a timeout (a deterministic fallback that returns the same result for the same input is acceptable) and supported Stage 1.
- Conclusion: **reached Stage 1** (broad support from [JHD](../../people/JHD.md) / [DJM](../../people/DJM.md) / [CPC](../../people/CPC.md) / [PFC](../../people/PFC.md) / [SFC](../../people/SFC.md) / [LVU](../../people/LVU.md) / [CDA](../../people/CDA.md) / [MM](../../people/MM.md) / [WH](../../people/WH.md) and others; no opposition).

## `Intl.DateTimeFormat` Alignment With Other Standards

- wiki: [Intl.DateTimeFormat Alignment With Other Standards](../../proposals/intl-datetimeformat-alignment.md)
- slide: [link](https://docs.google.com/presentation/d/1JAb9AFDNdgrcDMS24iTZPTqi5p3uzHLr8JDZOI-5CYM/edit)
- [EAO](../../people/EAO.md) asked for Stage 1 for a new proposal. Datetime-formatting API design is underway in HTML (a WHATWG proposal by [LCA](../../people/LCA.md) to add a format attribute to the `<time>` element) and in Unicode MessageFormat. The motivation is to use the same formatting options in HTML, JavaScript, and MessageFormat.
- Add `dateFields` / `timePrecision` to `Intl.DateTimeFormat`, and also consider aligning names such as `dateLength` (an alias of dateStyle) and `timeZoneStyle` (an alias of timeZoneName). No new data or behavior: it is expressible as a mapping onto the existing datetime component options.
- The current API also allows nonsensical combinations such as "July at 36." The direction is to prevent that with a design based on ICU4X semantic skeletons. The HTML PR is at stage 1 of the WHATWG process, so spelling changes can be negotiated in both directions.
- [JSL](../../people/JSL.md) / [SFC](../../people/SFC.md) / [LVU](../../people/LVU.md) supported it. [SFC](../../people/SFC.md) added that the problem statement is good but the solution still needs work.
- Conclusion: **reached Stage 1** (approved with essentially no debate).

## Private declarations

- slide: [link](https://docs.google.com/presentation/d/1Cmk_vpi6yID9dJjZqqSfKMhvYmO2xXGRakAxcXvHq4s/edit?usp=sharing)
- [KG](../../people/KG.md) restarted private declarations, which had been asleep at Stage 1 for seven years (the previous champion was [JRL](../../people/JRL.md)). It allows a private-field declaration in any scope other than a class body, and adds syntax to attach a field declared outside to an object literal or a class. The motivation is friend classes and non-class object factories.
- The semantics are exactly those of existing private fields (explainable with a WeakMap). It does not introduce reification or dynamic attachment to an existing object. [MM](../../people/MM.md) was uncomfortable with the `[#x]:` syntax, but after confirming the WeakMap semantics said "if I can get over the syntax, I will probably come around to supporting it." [JHD](../../people/JHD.md) supported it strongly because first-class protocols become much simpler.
- [EAO](../../people/EAO.md) / [OFR](../../people/OFR.md) asked for the motivation to be spelled out: why is a non-enumerable property keyed by a shared Symbol not enough? [KG](../../people/KG.md) / [JHD](../../people/JHD.md) replied that real privacy is essential to defend an invariant, and [PFC](../../people/PFC.md) pointed out that a Symbol leaks through `Object.getOwnPropertySymbols`. [EAO](../../people/EAO.md) also worried about syntax that lets you use something that is not first-class as if it were.
- Forbidding the declaration at script top level is the leading option ([KM](../../people/KM.md) / [OFR](../../people/OFR.md)). The syntax (`[#x]` versus `with #x`) carries over as a Stage 2 bikeshed.
- Conclusion: out of time. It will be discussed again with a longer time box ([KG](../../people/KG.md) gave up on going straight to 2.7 next time).

## Fused Multiply-Add for Stage 1 or 2

- wiki: [Fused Multiply-Add](../../proposals/fused-multiply-add.md)
- slide: [link](https://docs.google.com/presentation/d/e/2PACX-1vQ5JHSa97CYNyS42bllFQ0CX-ctDlDSPTMG7kKAEflEwqrl3K-dqOlvdFyIq1eDp2k-BoNG2yfueHpQ/pub?start=false&loop=false&delayms=3000)
- [WH](../../people/WH.md) presented a proposal to add FMA, required by IEEE 754-2008 (compute x × y + z as the mathematical value and round only once at the end), as `Math.fma`. The direct trigger was that the previous meeting's spec text for unit conversion in [Amount](../../proposals/amount.md) needed it. A userland implementation is hundreds of lines and slow, and every major language already provides it.
- `high = a * b` and `low = Math.fma(a, b, -high)` yield the exact product, and combined with `Math.sumPrecise` an exact dot product can be computed too. [MM](../../people/MM.md) supported it after confirming the invariant "if the exact mathematical value is representable, return that."
- [DLM](../../people/DLM.md) described the WASM discussion of uneven hardware support and slow software fallbacks. [PFC](../../people/PFC.md) / [KM](../../people/KM.md) confirmed that it lowers to a single instruction on ARMv8, x86-64 (SSE), and RISC-V.
- Two issues remain. On argument coercion, the louder view was that the existing agreement "new APIs do not coerce" should win over consistency with the other `Math` functions ([WH](../../people/WH.md) / [MM](../../people/MM.md) / [RGN](../../people/RGN.md) initially). [PFC](../../people/PFC.md) / [MF](../../people/MF.md) / [KG](../../people/KG.md) took that view, and `Math.sumPrecise` throws too. [RGN](../../people/RGN.md) withdrew the other position. The name, `fma` versus `multiplyAdd` / `mulAdd` ([SFC](../../people/SFC.md) prefers the latter for discoverability), will be looked at later.
- Conclusion: **reached Stage 2**. Reviewers are [JHD](../../people/JHD.md) and [MF](../../people/MF.md). Resolve the name and coercion, then seek Stage 2.7 later.

## Needs-consensus PR: Normative: Allow `Locale.p.getNumberingSystems` to return >1 item

- proposal: [ecma402#1074](https://github.com/tc39/ecma402/pull/1074)

## Continuation: Thenable Curtailment for 2.7

- wiki: [Thenable Curtailment](../../proposals/thenable-curtailment.md)
- slide: [link](https://docs.google.com/presentation/d/1kHq_UqMHGGT8ena8yMlJKgHmohDVqxJvV4hiCB12HtU/view)
- Continuation from Day 1. To handle host objects that can override internal methods, spec text was presented for a host hook that returns true when an override of getOwnProperty or getPrototypeOf might run user code (the default implementation returns false. The hook itself must not run user code). [NRO](../../people/NRO.md)'s review is in.
- [MM](../../people/MM.md) asked whether a host that implements the host hook wrong is out of conformance. [MAG](../../people/MAG.md) / [KG](../../people/KG.md) / [MF](../../people/MF.md) settled that the host-hook specification is normative, an implementation that does not follow the spec is non-conforming, and with host cooperation it is in principle testable in test262 ([PFC](../../people/PFC.md) added that you cannot prove the negative). [MM](../../people/MM.md) was satisfied with that account.
- The 2.7 entrance criteria were also checked (confirmation to the editors, and [MF](../../people/MF.md)'s editorial LGTM).
- Conclusion: **consensus for Stage 2.7** ([MM](../../people/MM.md) / [JHD](../../people/JHD.md) supported it explicitly).

## temperature checks relating to https://github.com/tc39/proposal-bigint-from-exponential

- wiki: [BigInt from exponential](../../proposals/bigint-from-exponential.md)
- proposal: [proposal-bigint-from-exponential](https://github.com/tc39/proposal-bigint-from-exponential)
- [RGN](../../people/RGN.md) ran two temperature checks on this proposal, which reached Stage 1 on Day 1, to save one design iteration.
- The first was whether to extend bigint literal syntax, as in `1e6n`. [JHD](../../people/JHD.md) was in favor; [EAO](../../people/EAO.md) said a literal is unnecessary. The result was Strong Positive 5 / Positive 4 / Following 3 / Confused 2 / Indifferent 2 / Unconvinced 0.
- The second was whether the new syntax should spread to `BigInt(string)` and the existing implicit conversions (`==` / `<` [comparisons](../../proposals/comparisons.md), TypedArray / DataView / `Atomics.store`, `BigInt.asIntN`, and so on), or whether the existing behavior should stay and only an opt-in static method should gain it. Web compatibility was explicitly out of scope this time. The result was Strong Positive 4 / Positive 3 / Following 2 / Confused 2 / Indifferent 1 / Unconvinced 0.
- Conclusion: both were mixed. The results will be taken into account as the proposal develops.

## Continuation: Async iterator helpers open questions

- slide: [link](https://docs.google.com/presentation/d/17_mL3guxupbKWKr1EbDdML9K9kPTqElbf9xgoZZDBh0/edit)
- [KG](../../people/KG.md) had given the time to Private declarations, so only one of the open questions on concurrent async iterators was taken up in the remaining five minutes. The issue is the order and concurrency of closing both the outer iterator and the inner iterator returned by the mapper when `.return` is called on the iterator that `flatMap` returns.
- [KG](../../people/KG.md) preferred "inner first, sequentially," by analogy with breaking out of a nested loop. [MF](../../people/MF.md) agreed with inner-first but preferred concurrent for speed, and [WH](../../people/WH.md) also supported innermost-first.
- The remaining, more complicated questions are planned for a time box on the order of two hours next time.
- Conclusion: the committee prefers inner-first. Concurrent versus sequential stays unresolved ([KG](../../people/KG.md) will coordinate with [MF](../../people/MF.md)).
