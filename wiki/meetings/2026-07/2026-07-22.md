## Duration units in Amount and Intl Sequence Units

- 提案ページ: [Intl Sequence Units](../../proposals/intl-sequence-units.md)、[Amount](../../proposals/amount.md)
- Slides: [link](https://tc39.es/proposal-intl-sequence-units/slides/time-units.html)
- [SFC](../../people/SFC.md) が sequence units(foot-and-inch 等)における time/duration units の扱いを提起。TG2 で見解が二分したため、推奨案なしで plenary に両論を提示した。
- position 1(除外): duration は footgun が多く(DST・暦月長)、[Temporal](../../proposals/temporal.md) + `Intl.DurationFormat` に 9 年かけた正道があるのに `Intl.NumberFormat` に劣化版を足すと長年の pain point になる。position 2(包含): CLDR units.xml との整合、`convertTo` の ergonomics、汎用 unit 変換コードで time だけ分岐する摩擦の回避。[WH](../../people/WH.md) は position 2 を支持。
- [PFC](../../people/PFC.md) は [Temporal](../../proposals/temporal.md) と異なる duration 変換規則を持つ第 2 の仕組みを作らないことが重要と主張。[SFC](../../people/SFC.md) は変換を認めるとしても [Temporal](../../proposals/temporal.md) の制約(relative-to なしで可能な範囲)が上限で、months/years 変換を認める CLDR とは乖離すると応答。months/quarters の扱いは [SFC](../../people/SFC.md)/[PFC](../../people/PFC.md) が units.xml を精査する。
- [RGN](../../people/RGN.md) は任意の well-formed unit 文字列を許す [Amount](../../proposals/amount.md) で time units だけ拒否するのは perverse であり、sequence time units の表現と CLDR 準拠の変換は支持すべきと主張。[EAO](../../people/EAO.md) からは time 系 [Amount](../../proposals/amount.md) の `toLocaleString` で DurationFormat の options を受けるべきかという新論点も出た。
- 結論: 新たな観点(hybrid 案、[Amount](../../proposals/amount.md) format 時の NumberFormat/DurationFormat 自動選択)を踏まえ、提案の iteration を継続。

## Linear Matching

- 提案ページ: [Linear Matching](../../proposals/linear-matching.md)
- Slides: [link](https://docs.google.com/presentation/d/19Y18Lt165cSwqLI7K7aeA6IbSp9FOC1psrC2_MfaLs4/edit)
- [MF](../../people/MF.md) が [AUR](../../people/AUR.md)/[CPC](../../people/CPC.md) との champion group を代表して Stage 1 を要求。regexp が超線形時間で評価され unrecoverable に hang する ReDoS は CVE が常時発行される脆弱性クラスで、linter でも確実に検出できず、組み込みの対策が無いことを問題設定とした。
- 解決策の候補として、engine への linear 実行可否の問い合わせ、linear 保証付きの exec 変種、regex flag、timeout/resource limit 後の linear 実装への fallback、linear 保証 subset の仕様化を列挙(solution は Stage 1 では未確定)。
- [KG](../../people/KG.md)/[OFR](../../people/OFR.md)/[KM](../../people/KM.md) は engine 差や version 間差を露出する API に懸念(一度 linear と答えたら unship 不能になる)。[CPC](../../people/CPC.md) は仕様で「linear 必須の subset」を定義すれば実装間で uniform になると応答。[OFR](../../people/OFR.md) は V8 の実験的 linear engine に出荷予定は無く、平均性能では backtracking が優るため opt-in 必須で、第 2 の engine を持つ実装負荷も高いと指摘。
- [WH](../../people/WH.md)/[AUR](../../people/AUR.md) は「linear」が入力長についてのみで regex 長には指数的になりうる点への注意を喚起。[MM](../../people/MM.md) は timeout のような dynamic non-determinism を導入する解には反対しつつ(同一入力に同一結果を返す deterministic fallback は容認)、Stage 1 は支持。
- 結論: **Stage 1 到達**([JHD](../../people/JHD.md)/[DJM](../../people/DJM.md)/[CPC](../../people/CPC.md)/[PFC](../../people/PFC.md)/[SFC](../../people/SFC.md)/[LVU](../../people/LVU.md)/[CDA](../../people/CDA.md)/[MM](../../people/MM.md)/[WH](../../people/WH.md) ら多数が支持、反対なし)。

## `Intl.DateTimeFormat` Alignment With Other Standards

- 提案ページ: [Intl.DateTimeFormat Alignment With Other Standards](../../proposals/intl-datetimeformat-alignment.md)
- Slides: [link](https://docs.google.com/presentation/d/1JAb9AFDNdgrcDMS24iTZPTqi5p3uzHLr8JDZOI-5CYM/edit)
- [EAO](../../people/EAO.md) が新提案の Stage 1 を要求。HTML(`<time>` 要素に format 属性を足す [LCA](../../people/LCA.md) の WHATWG 提案)や Unicode MessageFormat で datetime formatting の API 設計が進行中で、HTML / JavaScript / MessageFormat で同じ formatting options を使えるようにするのが動機。

- 現行 API が「July at 36」のような nonsensical な組合せを許す問題も、ICU4X の semantic skeleton に基づく設計で防ぐ方向。HTML PR は WHATWG プロセスの stage 1 段階のため、綴りの変更は双方向に交渉可能。

## Private declarations

- Slides: [link](https://docs.google.com/presentation/d/1Cmk_vpi6yID9dJjZqqSfKMhvYmO2xXGRakAxcXvHq4s/edit?usp=sharing)
- [KG](../../people/KG.md) が 7 年前から Stage 1 のまま眠っていた private declarations を再始動(旧 champion は [JRL](../../people/JRL.md))。private field の宣言を class body 以外の任意 scope に許し、外で宣言した field を object literal や class に付与する構文を足す。friend class や非 class の object factory が動機。
- semantics は既存 private fields と完全に同一(WeakMap で説明可能)で、reification や既存 object への動的付与は導入しない。[MM](../../people/MM.md) は `[#x]:` 構文に違和感を示したが、WeakMap semantics の確認後は「syntax を乗り越えれば賛成に回るだろう」とした。[JHD](../../people/JHD.md) は first-class protocols が大幅に簡素化されるとして強く支持。
- [EAO](../../people/EAO.md)/[OFR](../../people/OFR.md) は「共有 Symbol keyed の非 enumerable property でなぜ不足か」と motivation の明示を要求。[KG](../../people/KG.md)/[JHD](../../people/JHD.md) は invariant の防衛には真の privacy が不可欠と反論し、[PFC](../../people/PFC.md) も Symbol は `Object.getOwnPropertySymbols` で漏れると指摘。[EAO](../../people/EAO.md) は first-class でないものを first-class のように使わせる構文への懸念も示した。
- script top-level での宣言は禁止が有力([KM](../../people/KM.md)/[OFR](../../people/OFR.md))。構文(`[#x]` か `with #x` か)は Stage 2 の bikeshed として持ち越し。
- 結論: 時間切れ。より長い time box を取って再度議論する([KG](../../people/KG.md) は次回の 2.7 直行を断念)。

## Fused Multiply-Add for Stage 1 or 2

- 提案ページ: [Fused Multiply-Add](../../proposals/fused-multiply-add.md)
- Slides: [link](https://docs.google.com/presentation/d/e/2PACX-1vQ5JHSa97CYNyS42bllFQ0CX-ctDlDSPTMG7kKAEflEwqrl3K-dqOlvdFyIq1eDp2k-BoNG2yfueHpQ/pub?start=false&loop=false&delayms=3000)
- [WH](../../people/WH.md) が IEEE 754-2008 で必須化された FMA(x × y + z を数学的値として計算し最後に 1 回だけ丸める)を `Math.fma` として追加する提案。前回会合の [Amount](../../proposals/amount.md) の unit conversion の spec 記述で必要になったのが直接の契機で、userland 実装は数百行かつ低速、主要言語は全て提供済み。
- `high = a * b` と `low = Math.fma(a, b, -high)` で exact product が得られ、`Math.sumPrecise` と組み合わせて正確な dot product も計算できる。[MM](../../people/MM.md) は「正確な数学的値が表現可能ならそれを返す」invariant を確認して賛成。
- [DLM](../../people/DLM.md) は WASM で hardware support の不均一と software fallback の遅さが議論になった経緯を紹介。[PFC](../../people/PFC.md)/[KM](../../people/KM.md) は ARMv8 / x86-64(SSE)/ RISC-V で単一命令に lower されることを確認した。
- 残る論点は 2 つ。引数の coercion は、他の `Math` 関数との一貫性([WH](../../people/WH.md)/[MM](../../people/MM.md)/当初の [RGN](../../people/RGN.md))より「新 API は coerce しない」という既存合意を優先すべきとの声([PFC](../../people/PFC.md)/[MF](../../people/MF.md)/[KG](../../people/KG.md)、`Math.sumPrecise` も throw)が優勢で、[RGN](../../people/RGN.md) も撤回。名前も `fma` か `multiplyAdd`/`mulAdd` か([SFC](../../people/SFC.md) は discoverability から後者を推す)を今後検討する。
- 結論: **Stage 2 到達**。reviewer は [JHD](../../people/JHD.md) と [MF](../../people/MF.md)。名前と coercion を解決して将来 Stage 2.7 を諮る。
