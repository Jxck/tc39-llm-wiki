## Module Import Hook and new Global for Stage 1

- slide: [link](https://github.com/endojs/proposal-new-global/blob/main/slides/slides.pdf)

[KKL](../../people/KKL.md) and [ZTZ](../../people/ZTZ.md) presented, toward Stage 1, a proposal for a new `Global` constructor that separates the global from the realm, plus an import hook. Motivations included Compartment / sandbox use, isolating AI-generated code, test runners, and emulating other hosts. Strong concerns came from [KG](../../people/KG.md), [MAG](../../people/MAG.md), [JHD](../../people/JHD.md), and others: "it looks like a sandbox but it is not actually a sandbox." There was also an implementation concern that the HTML spec assumes a one-to-one realm and global ([MAG](../../people/MAG.md)), and overlap with import maps ([KG](../../people/KG.md)). Time ran out. The conclusion was that the problem statement needs to be revised, and it was tabled for the day (continued discussion went to a Continuation session later the same day).

## Import Buffer for Stage 1

- slide: [link](https://proposal-import-buffer.vercel.app/)

[STY](../../people/STY.md) (Vercel) presented an `import buffer` proposal that uses import attributes to import an arbitrary byte sequence as a module. It started as an `ArrayBuffer` proposal. With support from [NRO](../../people/NRO.md), [JSL](../../people/JSL.md), [KM](../../people/KM.md), [MM](../../people/MM.md), and others, it was changed to a `Uint8Array` (backed by an immutable `ArrayBuffer`), and the attribute name was agreed to change from `type: "buffer"` to `type: "bytes"`. It was confirmed that the main design of the spec had settled, and consensus was reached not only for Stage 1 but through Stage 2 (`Import Bytes has Stage 2`). Adding `type: "text"`, which [EAO](../../people/EAO.md) proposed, was carried as a separate proposal.

## Continuation: How to make thenables safer?

## Continuation: Module Import Hook and new Global for Stage 1

- slide: [link](https://github.com/endojs/proposal-new-global/blob/main/slides/stage1.pdf)

[ZTZ](../../people/ZTZ.md) presented a revised problem statement ("how to evaluate a module and its dependencies in the context of a new Global scope inside the same realm") and announced that the proposal name would provisionally change to `proposal-module-global`. It was confirmed among [JHD](../../people/JHD.md), [KG](../../people/KG.md), and [KKL](../../people/KKL.md) that if the one-to-one relationship of realm and global cannot be broken, the proposal itself does not hold, but an optimistic outlook on feasibility was shared. Issues for Stage 2 and later also came up, such as how to handle a ModuleSource import hook across workers. The conclusion was consensus for Stage 1 under the new problem statement.
