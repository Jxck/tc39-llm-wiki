## `F.p.toString` incompat for builtin accessors

[KM](../../people/KM.md) (Keith Miller, WebKit/JSC) raised the interpretation of "normative optional" for the `get` prefix on builtin accessors in `Function.prototype.toString`. JSC's optional behavior had come to be depended on by sites as a way to tell "whether this is Safari," so it was hard to change the spec's choice. The discussion agreed that normative optional does not mean "free to choose on every execution" but "always the same result for the same inputs of the same abstract operation."

The conclusion was that the intent of normative optional was not to allow that kind of dynamic choice, so no spec change was needed to match JSC's behavior. In the future, enumerating the existing legacy getters and treating them as exceptions in Annex B may be considered.

## Spec/implementations divergence on module evaluation promises settlement order

[NRO](../../people/NRO.md) (Nicolò Ribaudo) reported that the order in which module-evaluation promises from a dynamic import settle differs across three groups: the ECMA-262 spec, Safari / Bun / JSC, and Chrome / Deno / XS, and SpiderMonkey. Fulfillment order is child → parent, which everyone agrees on, but rejection order disagreed between the spec and implementations. A temperature check gathered strong support for changing the spec's rejection order to match fulfillment (child → parent).

The conclusion was strong opposition to the third option (allowing a non-deterministic order). SpiderMonkey wanted to keep the status quo, but would follow the committee's decision. Consensus was reached on changing the rejection order to match the fulfillment order.

## TypedArray copyWithin inconsistently responds to midstream shrinking

[RGN](../../people/RGN.md) (Richard Gibson) presented a problem (issue #3618): if user code such as `valueOf` shrinks the `ArrayBuffer` in the middle of `TypedArray.prototype.copyWithin`, forward iteration and reverse iteration do not behave the same. The spec fully aborts the copy when the range is incomplete during reverse iteration, but the majority of real implementations (other than LibJS) copy "the largest remaining prefix," the same as forward.

The conclusion was consensus on the normative change in PR #3619 (re-clamp to the updated length, and copy consistently regardless of direction). That removes an observable difference between forward and reverse.

## Missing name property for `%IntlSegmentsPrototype%[%Symbol.iterator%]`

[USA](../../people/USA.md) (Ujjwal Sharma) presented a simple normative change, ECMA-402 PR #1015, that adds the missing `name` property (a Symbol.iterator name equivalent to `"Segments Iterator"`) on the `Intl.Segmenter.prototype[Symbol.iterator]` object. It is a change to match web reality, and it has no substantial effect on behavior.

The conclusion was consensus, with explicit support from two or more people.

## Freezing the Array Iterator

[KG](../../people/KG.md) (Kevin Gibbons) presented an exploratory item, not yet a proposal repository, that freezing `Array.prototype[Symbol.iterator]` and `ArrayIterator.prototype.next` (not reassignable) would make static analysis and optimization easier. [MM](../../people/MM.md) (Mark Miller) replied that the cost of mutability is a problem that exists across the whole language, and that it should be handled not by an ad hoc special case but by a general optimization such as an isFrozen check, and by fixing override mistakes and introducing a lockdown / harden style of mode. [JHD](../../people/JHD.md), [MAH](../../people/MAH.md), and others also raised concerns about polyfill compatibility and about constraining future language evolution.

No conclusion was reached (`No conclusion`). [KG](../../people/KG.md) intended to discuss it again at the next meeting, and bringing it to TG3 was also proposed.

## Proposed code of conduct addition: "write your own comments"

[KG](../../people/KG.md) (Kevin Gibbons) proposed adding, to the Code of Conduct (or a separate document that stands in for it), a rule that forbids posting LLM-generated prose as-is. The wording shown was: "you should write the idea itself, and you must not have an LLM expand or explain the idea and then post that output. Machine translation is allowed, but the translation must not add new content." [JHD](../../people/JHD.md) agreed with the substance but opposed adding it to the Code of Conduct itself, and supported linking it as a separate document (`AI_policy.md`). [WH](../../people/WH.md) argued that using an LLM to compress prose, and using it for a grammar check, should be allowed.

The conclusion was consensus not to add it directly to the Code of Conduct, but to write it in a new `AI_policy.md` inside `how-we-work` and link to it from the Code of Conduct. The allowed range, such as grammar checks, will have its wording settled later.

## [Temporal](https://github.com/tc39/proposal-temporal) normative PR

- wiki: [Temporal](../../proposals/temporal.md)
- slide: [link](https://docs.google.com/presentation/d/1xaHux5EvR9zXQWnnr0r76ffCdDejmy383XrkrmSPStk/edit?slide=id.p#slide=id.p)

[NRO](../../people/NRO.md) (Nicolò Ribaudo), on behalf of [PFC](../../people/PFC.md), presented a normative change based on an implementation convenience when V8 split the logic of [Temporal](../../proposals/temporal.md) into a Rust implementation. For methods such as `until`, the order of reading options (get) and casting (cast) changes from the old "repeat get-cast-validate for each option" to "get-cast every option, then validate at the end." That can delay when some errors are thrown. [KG](../../people/KG.md) pointed out that this discussion also relates to the option-bag design of other proposals.

The conclusion was consensus on this normative change.

## [Uint8Array base64+hex](https://github.com/tc39/proposal-arraybuffer-base64) for Stage 4

- slide: [link](https://github.com/tc39/proposal-arraybuffer-base64)

[KG](../../people/KG.md) (Kevin Gibbons) asked for Stage 4 for the base64 / hex conversion proposal, which is implemented in JavaScriptCore and SpiderMonkey and implemented in V8 with a plan to ship in about a month. Related to the [Temporal](../../proposals/temporal.md) item just before, they discussed whether the read-and-validate order of this proposal's `lastChunkHandling` and `alphabet` options (repeating get-validate for each option) is an appropriate standard pattern for future option-bag design. [JHD](../../people/JHD.md) confirmed "future option bags should be unified on this pattern," and [KG](../../people/KG.md) broadly agreed.

The conclusion was consensus for Stage 4, with Chrome's agreement as well. The committee confirmed a policy that future proposals with an option bag follow this proposal's pattern.

## AsyncContext web integration update

- wiki: [AsyncContext](../../proposals/async-context.md)
- slide: [link](https://docs.google.com/presentation/d/1d64udRyuYplXajTCMQkGrVh2jff464_7D75dZ6pSxiE/edit?usp=sharing)

[ABO](../../people/ABO.md) (Andreu Botella) reported progress on web integration of [AsyncContext](../../proposals/async-context.md) since the previous meeting in May. Mozilla's DOM team had opposed the proposal because of the complexity of web integration and a memory-leak concern. After discussion at the Web Engines Hackfest, they are prototyping in Gecko, and checking safety, for same-agent and cross-agent messaging APIs such as `MessageChannel`, `BroadcastChannel`, `IndexedDB`, and `LocalStorage`. [MM](../../people/MM.md) confirmed that there is no effect on the JavaScript specification itself, and that the changes are only on the web-spec side.

The conclusion was that this is a progress report toward Stage 2.7, and this meeting made no decision. Resolving Mozilla's concern is the next step.
