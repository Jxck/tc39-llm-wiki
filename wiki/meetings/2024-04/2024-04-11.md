## Decimal for stage 2

- wiki: [Decimal](../../proposals/decimal.md)
- proposal: [proposal](https://github.com/tc39/proposal-decimal)
- slide: [slides](https://docs.google.com/presentation/d/1kXurIVl4kjzclwFgfzJqohtPyryeKI7Mn9C_w7aAYp8/)

JMN and LIU presented Decimal for Stage 2, with production use cases from Bloomberg (ACE: decimal fields flowing through C++, Python, and JS systems) and Alibaba's DingTalk sheets (following Excel's 15-digit precision workaround). The ecosystem survey found MikeMcl's decimal libraries alone used by 10k+ packages, often undermined by converting back to Numbers. The data model is IEEE-754 Decimal128 with a "normalize by default" compromise (trailing zeros preserved but stripped by default in serialization; comparisons by mathematical value). WH's extensive review found the spec short of Stage 2 criteria — the IEEE 754 references don't actually define the operations, there are no Number conversions, and remainder/negation semantics need rework; SYG showed the exactness check for Number inputs is unimplementable as presented; EAO found the Intl.NumberFormat integration underspecified; JHD and MM were unwilling to advance (MM preferring libraries).

The conclusion was no advancement — Decimal stays at Stage 1, and WH will work with the champions offline.

## Shared Structs Discussion

- wiki: [Shared structs](../../proposals/shared-structs.md)
- proposal: [proposal](https://github.com/tc39/proposal-structs)
- slide: [slides](https://docs.google.com/presentation/d/1a53adMbL_Uqb1KxnY-r6Ie6n1PQXvNw3JgUOvRYFido/)

SYG laid out the feature set for this year's Stage 2 ask (no advancement requested yet): unshared structs (fixed layout, sealed, one-shot initialization, non-generic methods), shared structs that may only reference primitives and other shared objects, realm-local prototypes to attach methods, and an auto-correlation registry keyed by source location. MAH accepted the source-location key is unforgeable (not a communication channel) but flagged the tension with JavaScript virtualization; WH probed the memory model (no tearing, but in-place string mutation optimizations are off the table); MM accepted the necessity of methods on power-user feedback but wants the feature narrowly opt-in. Shared fixed-length arrays, Mutex/ConditionVariable (usable with `using`), a default-unordered memory model with allocation-as-publication, and alignment with the shared WasmGC proposal round out the package.

The conclusion was that the champions will engage MM further on the methods decision, with the Stage 2 ask planned for the next meeting.

## Strict Enforcement of 'using'

- wiki: [Strict Enforcement of 'using'](../../proposals/using-enforcement.md)
- proposal: [proposal](https://github.com/rbuckton/proposal-using-enforcement)
- slide: [slides](https://1drv.ms/p/s!AjgWTO11Fk-TkqpmyWWWHf6TPYt2gg?e=fPIwaL&nav=eyJzSWQiOjI1NiwiY0lkIjoyMTg5ODA3Nzk5fQ)

RBN presented an opt-in stricter enforcement for `using`: APIs return an object with a `[Symbol.enter]()` method that `using` unwraps, guiding users toward `using`/`DisposableStack` without forcing every host API to bifurcate. MM liked the getter-based alternative (making `[Symbol.dispose]` a getter) enough to see no need for a new mechanism, but KG argued the alternatives give no real enforcement — the error arrives in the distant future or not at all — while GB supported a protocol-level guarantee. RBN himself was unconvinced it was necessary and prefers it as a follow-on proposal that does not hold back Explicit Resource Management.

The conclusion was Stage 1 (MM and KM supportive of Stage 1 only, opposing Stage 2).

## Stop Coercing Things pt 4

- slide: [slides](https://docs.google.com/presentation/d/1aumShXqYgQV38Bg_L3FfJvGKIupJVCxs_C-Iz3r_tRE/edit)

KG returned with part 4 of the non-binding coercion guidelines: in future APIs (except close cousins of existing ones), throw a TypeError instead of coercing between primitive types (null, boolean→string, boolean→number) and reject primitives where an object — especially an options bag — is expected (already the rule in ECMA-402). Support was unanimous. The iterable-strings question (whether iterable-taking positions should accept strings) was discussed but deferred — MF wants to survey existing APIs first and floated a `String.prototype.codePoints` companion — and WH warned the guidelines must not prevent explicit coercions.

The conclusion was consensus on the non-binding guidelines; the iterable question returns with the next iterable-taking API.

## (continuation) Extractors

- wiki: [Extractors](../../proposals/extractors.md)
- proposal: [proposal](https://github.com/tc39/proposal-extractors)

RBN worked through the remaining queue from day 3. WH identified a no-line-terminator problem — extractors would change the meaning of existing code like `let x\n (a) = b`, and banning line terminators inside some function calls makes calls inconsistent — which must be resolved before Stage 2, plus an elision mismatch between the cover grammar and the refined grammar (a spec error to fix). ## Signals for Stage 1

- wiki: [Signals](../../proposals/signals.md)
- proposal: [proposal](https://github.com/proposal-signals/proposal-signals)
- slide: [slides](https://docs.google.com/presentation/d/1MJqndTS5RmTEwTbtLTPsEloc-a_MWR8daQINgDim2RA/edit#slide=id.g1f570b058be_0_573)

DE, YK, and JRA presented Signals for Stage 1: a mutable, automatically tracked dependency graph (Signal.State, Signal.Computed, and a `subtle` namespace with Watcher for framework-provided effects), built with framework authors — hypothetical Preact and Vue integrations showed shared data code across renderers, on the model of how Promises were standardized. Concerns from the queue: JHD raised the React "rules of hooks" analogy and capability separation (class instances vs plain objects, issues #94/#124), RBN asked how Signal.subtle.Watcher relates to a future events/observables mechanism (issue #111), MAH objected to the observable global mutable state (currentComputed), and SYG asked whether standardizing would disadvantage React (champions said no, and React has been open to communication).

The conclusion was Stage 1, with polyfill and framework integration work continuing via public channels.
