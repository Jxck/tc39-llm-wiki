## Reality and spec differ on property key resolution timing for o[p] = f()

- proposal: [issue #3295](https://github.com/tc39/ecma262/issues/3295)
- proposal: [PR #3307](https://github.com/tc39/ecma262/pull/3307)

RKG presented a normative fix for `o[p] = f()`: the spec requires ToPropertyKey(p) to run before f(), while all engines evaluate f() first. The PR loosens the [[ReferencedName]] handling so the key conversion happens after the right-hand side is evaluated, matching reality.

The conclusion was consensus to merge the PR.

## Discard Bindings for Stage 2

- wiki: [Discard bindings](../../proposals/discard-bindings.md)
- proposal: [proposal](https://github.com/tc39/proposal-discard-binding)
- slide: [slides](https://1drv.ms/p/s!AjgWTO11Fk-TkqpoWw0poDW3dawBQg?e=O3UP1c)

RBN presented discard bindings for Stage 2, with the central open question being `void` versus `_` as the discard marker. JHD objected to `void` on Tennent's Correspondence grounds, MM argued strongly for `void` and against `_`, while JRL and WH preferred `_`; WH also showed that `void` breaks the cover grammar in cases like `await void x`, `void /`, and `void + x`.

## eval/new Function changes for Trusted Types as Normative PR or Stage 3

- wiki: [Dynamic Code Brand Checks](../../proposals/dynamic-code-brand-checks.md)
- proposal: [ecma262#3294](https://github.com/tc39/ecma262/pull/3294)
- slide: [slides](https://docs.google.com/presentation/d/14AjvbW2-aNvlirB-7pPhIAeM7oWKtjqONRcyp9ID7gg/edit?usp=sharing)

NRO presented the Trusted Types changes for eval/new Function, asking for a normative PR or Stage 3. Consensus was reached with changes: the host hook returns a string or null instead of calling ToString (per MF and KG), and for `new Function` the host rebuilds the string rather than receiving the full concatenation. MF will review; MM supported advancing (preferring 2.7 but fine with 3), while JHD asked why this wasn't a needs-consensus PR, which MM also objected to.

The conclusion was Stage 3 with the changed host-hook shape.

## Module sync assert for stage 2

- proposal: [proposal](https://github.com/tc39/proposal-module-sync-assert)

JWK presented a module-level directive asserting that a module's subgraph stays synchronous, turning an accidental top-level await into a linking error (service workers, polyfills, library authors). DR objected that a library's sync assertion can break downstream consumers who don't care, and that this belongs in tests or tooling; SYG and MF argued the error happens either way and tools could check it. DE pushed back on dismissing it as "just a tooling concern", given TC39's role in unifying the tooling ecosystem.

The conclusion was no advancement: engines doubted browser value, and without spec text it didn't qualify for Stage 2 — JWK will write spec text and return.

## bringing back Error.isError, for stage 1 or 2 (or even 2.7)

- wiki: [Error.isError](../../proposals/error-is-error.md)
- proposal: [proposal](https://github.com/ljharb/proposal-is-error)

JHD brought back Error.isError nine years after it was rejected: Error remains the only builtin whose instances cannot be brand-checked, which matters for debugging, RunKit's cross-realm serialization, and structuredClone's error handling (KG confirmed structuredClone checks the slot). NRO suggested a structuredClone-based workaround but retracted it over side effects. MM supports Stage 1 but opposes the static form (checking an internal slot on a non-this argument, preferring a prototype-inherited method), KG defended practical membrane transparency, MF called brand checking "icky" but supported Stage 1, and SYG raised the DOMException categorization question — it is not a real 262 error yet sits in Error.prototype's chain.

The conclusion was Stage 1, with the DOMException and internal-slot concerns to resolve before Stage 2.
