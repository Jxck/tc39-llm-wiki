## Don't call well-known Symbol methods for RegExp on primitive values

- proposal: [spec PR #3009](https://github.com/tc39/ecma262/pull/3009)

[GCL](../../people/GCL.md) (Gus Caplan, Deno) presented a needs-consensus PR motivated by Node.js and Deno hardening the JavaScript that their implementations run: `String.prototype.{match, matchAll, replace, replaceAll, search, split}` should no longer look up the RegExp protocol symbol (`Symbol.match` etc.) on the argument when it is a primitive (in practice a string), because tampering with that lookup can execute user code where an implementation never expects it. core-js had shipped the proposed behavior for years without anyone complaining, and [JHD](../../people/JHD.md) and [OMT](../../people/OMT.md) were supportive.

The conclusion was consensus, with [KG](../../people/KG.md) calling for future symbol-based protocols to follow this precedent of omitting primitives (as the disposable protocol already does). Deno will write the Test262 tests.

## Float16Array for stage 4

- wiki: [Float16Array](../../proposals/float16array.md)
- proposal: [proposal](https://github.com/tc39/proposal-float16array)

[KG](../../people/KG.md) (Kevin Gibbons, F5) asked for Stage 4 for `Float16Array`, `Math.f16round`, and the related DataView methods. The spec was simple but the implementations were "several orders of magnitude more difficult"; JavaScriptCore and SpiderMonkey are shipping, and Chrome plans to enable it by default in Chrome 135 (stable on April 1). Adoption by other web specs has started, with Canvas (higher color-depth canvases) and WebNN making use of `Float16Array`.

The conclusion was Stage 4, with support from [DLM](../../people/DLM.md) (SpiderMonkey) and [SYG](../../people/SYG.md) (confirming the Chrome plan), plus a +1 from [LGH](../../people/LGH.md), who had implemented it in a smaller engine.

## Redeclarable global eval vars for stage 4

- wiki: [Redeclarable global eval vars](../../proposals/redeclarable-global-eval-vars.md)
- proposal: [proposal](https://github.com/tc39/proposal-redeclarable-global-eval-vars)

[SYG](../../people/SYG.md) (Shu-yu Guo, Google) recapped the proposal: dropping the `[[VarNames]]` special case on the global object so that a global lexical binding is allowed to shadow a `var` introduced through direct eval, which the current spec rejects. The behavior had already shipped in all three engines (Chrome had it from the start, with nobody complaining), and the spec PR has editorial reviews.

The conclusion was Stage 4, with support from [DLM](../../people/DLM.md) and no objections.

## RegExp Escaping for stage 4

- wiki: [RegExp Escaping](../../proposals/regexp-escaping.md)

[JHD](../../people/JHD.md) (Jordan Harband) asked for Stage 4 for `RegExp.escape`. Firefox and Safari have shipped it, two polyfills exist, and Chrome has implemented it behind a stage flag; [SYG](../../people/SYG.md) admitted it had fallen through the cracks and should ship in Chrome 135 or 136.

## Temporal normative PR and status update

- wiki: [Temporal](../../proposals/temporal.md)
- proposal: [proposal](https://github.com/tc39/proposal-temporal)
- slide: [link](http://ptomato.name/talks/tc39-2025-02/#8)

[PFC](../../people/PFC.md) (Philip Chimento, Igalia) reported that [Temporal](../../proposals/temporal.md) is approaching the required two full implementations: it is enabled by default in Firefox Nightly (a Mozilla Hacks article drove a surge of interest), the MDN documentation is complete, and SpiderMonkey is close to 100% Test262 conformance (Ladybird at 97%). The one needs-consensus item, requested by [ABL](../../people/ABL.md), is that creating a `Temporal.PlainMonthDay` from a string whose year is outside the supported `PlainDate` range should keep working for the ISO 8601 calendar but throw a `RangeError` for other calendars, where honoring it would mean calculating, say, a million lunar years into the future.

The conclusion was consensus on the normative change (PR #3054). [DLM](../../people/DLM.md) added that Firefox hopes to ship it in the next few months if Nightly goes well.

## ShadowRealm Status Update

- wiki: [ShadowRealm](../../proposals/shadowrealm.md)
- proposal: [proposal](https://github.com/tc39/proposal-shadowrealm)
- slide: [link](http://ptomato.name/talks/tc39-2025-02/#1)

[PFC](../../people/PFC.md) (work in partnership with Salesforce) reported that the W3C TAG adopted a new design principle ("expose everywhere") for APIs fundamental enough to exist in every JS environment, which resolves part of the earlier question of which Web APIs a [ShadowRealm](../../proposals/shadowrealm.md) global contains. `crypto.subtle` stays out for now because its spec depends on an event loop, which [KG](../../people/KG.md) pushed back on as a spec-writing artifact rather than a real constraint. The remaining blocker is use cases: [KM](../../people/KM.md) relayed feedback that the ongoing maintenance burden on every current and future web spec needs stronger justification, and [SYG](../../people/SYG.md) and [DE](../../people/DE.md) agreed the deciding factor is use cases weighed against that cost; [MAH](../../people/MAH.md) questioned whether library-level use cases should not already suffice.

The conclusion was a status update only: the champions will gather use cases framed in terms of end users of the web and return with another update.

## Decorators implementation updates

- wiki: [Decorators](../../proposals/decorators.md)
- proposal: [proposal](https://github.com/tc39/proposal-decorators)
- slide: [link](https://slides.com/pzuraq/decorators-for-stage-3-2022-03-977778)

[KHG](../../people/KHG.md) (Kristen Hewell Garrett) gave the implementation status: TypeScript and Babel transforms are widely adopted, comprehensive Test262 tests are written but not merged, V8's implementation (from the Edge team) awaits review, and SpiderMonkey is around 75%. The sticking point is that no engine wants to ship first: [SYG](../../people/SYG.md) said the Edge patches are not prioritized because Chrome does not want to be first, [DLM](../../people/DLM.md) said SpiderMonkey's work has been paused for a year and a half, and [MLS](../../people/MLS.md) (Apple) also declined to prioritize it, none explaining how the decision was made.

The conclusion was the status quo: no one plans to ship currently. [DE](../../people/DE.md) urged engines to give clearer signals (including whether they would rather see the proposal withdrawn), noting Stage 3 was supposed to be the committee's prioritization signal.

## Curtailing the power of "Thenables" for Stage 1

- wiki: [Thenable Curtailment](../../proposals/thenable-curtailment.md)
- proposal: [proposal](https://github.com/mgaudet/proposal-thennable-curtailment)
- slide: [link](https://docs.google.com/presentation/d/1Sny2xC5ZvZPuaDw3TwqOM4mj7W6NZmR-6AMdpskBE-M/edit#slide=id.p)

MG (Matthew Gaudet) presented the recurring security problem of objects unexpectedly treated as thenables (e.g. WebIDL dictionaries inheriting a `then` planted on `Object.prototype`), a source of repeated engine bugs and CVEs; Firefox telemetry showed 0.13% of pages resolving a `then` off a standard prototype. Directions ranged from an exotic `Object.prototype` to a new "internal proto" slot consulted by promise resolution. [MAH](../../people/MAH.md) wanted it generalized to safe promise resolution and re-entrancy, while [SYG](../../people/SYG.md) and [KG](../../people/KG.md) argued for prioritizing the concrete thenable-CVE class.

The conclusion was Stage 1, with broad support for accepting even a somewhat unprincipled fix if it reduces vulnerability risk ([DE](../../people/DE.md): CVE costs are paid by web users; [KG](../../people/KG.md): corner-case complexity is paid only by the people in the room). Re-entrancy stays in scope where a harmonious solution falls out.

## `Math.clamp` for Stage 1 or 2

- wiki: [Math.clamp](../../proposals/math-clamp.md)
- proposal: [proposal](https://github.com/CanadaHonk/proposal-math-clamp)
- slide: [link](https://docs.google.com/presentation/d/14QGuyCHlsSr4ZSCkbFuaFZk8793EAMS1nAkdW_csLhA/edit)

[OMT](../../people/OMT.md) (Oliver Medhurst) proposed `Math.clamp(val, min, max)` and reached for Stage 2 directly, arguing the name and argument order are de facto standard across languages and npm packages. The argument order `(val, min, max)` found broad agreement, but real design space surfaced: a static `Math.clamp` versus a `Number.prototype.clamp` method ([MF](../../people/MF.md), [JHD](../../people/JHD.md) — the method shape would also dissolve the ordering question), what to do with NaN in the min/max arguments ([KG](../../people/KG.md)), [WH](../../people/WH.md)'s observation that clamping between +0 and -0 should not throw, and [SFC](../../people/SFC.md)'s concern that the motivation slides showed other implementations exist but not when clamp is actually the right tool for the job.

The conclusion was Stage 1 (not 2), with [OMT](../../people/OMT.md) agreeing that the Math-versus-prototype placement should be settled before advancing further.

## Immutable ArrayBuffer

- wiki: [Immutable ArrayBuffer](../../proposals/immutable-arraybuffer.md)
- proposal: [proposal](https://github.com/tc39/proposal-immutable-arraybuffer)
- slide: [link](https://github.com/tc39/proposal-immutable-arraybuffer/blob/main/immu-arraybuffer-talks/immu-arrayBuffers-stage2-7-as-presented.key)

[MM](../../people/MM.md) (Mark Miller, Agoric) reported three normative issues resolved since Stage 2: `transferToImmutable` gains an optional `newByteLength`, the accessor stays named `immutable`, and `sliceToImmutable` is added; order-of-operations is left open for implementer feedback. External feedback: WebGPU out of scope, no Wasm interference, WebTransport negative on cross-address-space transfer, and [RGN](../../people/RGN.md) drafted HTML structured-clone text. [WH](../../people/WH.md) required `sliceToImmutable` to match existing `slice` semantics when `end < start`, and [SYG](../../people/SYG.md) made review and merge of the HTML-side text a Stage 3 blocker.

The conclusion was Stage 2.7, with the champions committing to the `slice` consistency fix and to stating normatively that hosts cannot modify immutable buffers (after [KG](../../people/KG.md) walked back his claim that the spec already implied it).

## Limited ArrayBuffer

- proposal: [proposal](https://github.com/tc39/proposal-limited-arraybuffer)
- slide: [link](https://docs.google.com/presentation/d/1u6JsSeInvm6F4OrmCSLubtDvFVdjw1ESeE5-c_YflHE/)

[JWK](../../people/JWK.md) (Jack Works) explained that [Immutable ArrayBuffer](../../proposals/immutable-arraybuffer.md) has taken over his proposal's original freeze-in-place motivation, leaving two use cases: handing out a read-only view of a buffer whose write handle the host keeps (the WebGPU case, avoiding a new exotic view type in web specs), and sharing a limited slice that the holder cannot expand to the whole buffer (the Wasm memory case). [KG](../../people/KG.md) and [JRL](../../people/JRL.md) argued the remaining use cases are valuable (the latter citing how often libraries ignore TypedArray bounds), while [SYG](../../people/SYG.md) warned that aliasing buffers in engines is scary and potentially costly, and [MLS](../../people/MLS.md) added page-alignment concerns for limited ranges.

The conclusion was to stay at Stage 1 and keep exploring rather than withdraw.

## `Number.isSafeNumeric`

- proposal: [proposal](https://github.com/Lxxyx/proposal-number-is-safe-numeric)
- slide: [link](https://docs.google.com/presentation/d/1Noxi5L0jnikYce1h7X67FnjMUbkBQAcMDNafkM7bF4A/edit?usp=sharing)

[LIU](../../people/LIU.md) (ZiJian Liu, Alibaba) proposed `Number.isSafeNumeric`, a validator for strings whose conversion to a number keeps their mathematical value unchanged, motivated by API data handling, form validation, and financial calculations. [WH](../../people/WH.md) objected that the definition breaks interoperability — there is no way to print a Number as a string the function accepts — and that the MAX_SAFE_INTEGER condition is unrelated to exactness; [MF](../../people/MF.md) found the proposal confused about how floats work. [SFC](../../people/SFC.md) found the motivation plausible but suggested a `parseSafe` shape, and [SYG](../../people/SYG.md) said he could not discern the problem statement ([KG](../../people/KG.md): Stage 1 is agreeing on a problem statement, and it is not clear what this one is).

The conclusion was not to advance: the champion was asked to draft a succinct problem statement, file it as an issue, and bring it back during the same meeting if possible.
