## A unified vision for measure and decimal

- wiki: [Amount](../../proposals/amount.md), [Decimal](../../proposals/decimal.md)
- proposal: [measure](https://github.com/tc39/proposal-measure/), [decimal](https://github.com/tc39/proposal-decimal/)
- slide: [link](https://notes.igalia.com/p/tc39-2025-02-plenary-decimal-measure-unity)

[JMN](../../people/JMN.md) (Jesse Alama, Igalia) and [EAO](../../people/EAO.md) (Eemeli Aro, Mozilla) asked whether the decimal and measure proposals should be merged, arguing a unified numerics solution with an easy on-ramp to localization (as [Temporal](../../proposals/temporal.md) did for dates) is greater than its parts; [SFC](../../people/SFC.md) defended keeping them together, and [EAO](../../people/EAO.md) floated an opaque "[Amount](../../proposals/amount.md)" type. The committee pushed back: [DLM](../../people/DLM.md) reported Mozilla was skeptical of merging and of unit conversion, [MF](../../people/MF.md) wanted each part justified on its own, and [WH](../../people/WH.md) argued decimal arithmetic and units are separate concerns.

The conclusion was that there is little to no support for merging outside the champion group; unit conversion is a secondary/separate concern; and support exists for at least two proposals, possibly three, with concern that separating them might obscure the value of the sum.

## Stable Formatting update

- wiki: [Stable Formatting](../../proposals/stable-formatting.md)
- proposal: [proposal](https://github.com/tc39/proposal-stable-formatting)
- slide: [link](https://docs.google.com/presentation/d/14KQA1Gyy0reIyouHtzp5ofYRrcwRjkY6GajeknLWhg0/edit?usp=sharing)

[EAO](../../people/EAO.md) (Eemeli Aro, Mozilla) reported support for a `zxx` locale for [stable formatting](../../proposals/stable-formatting.md) behavior, with the alias still open (`null`, which is uncomfortably close to `undefined`; a well-known symbol such as `Intl.Stable`; or a longer string). [RGN](../../people/RGN.md) distinguished character-classification changes from new Unicode versions (acceptable) from revisions of the UAX#29 rules themselves (which should be snapshotted), and noted environments needing determinism can simply exclude unstable APIs. Root-locale access for `Intl.Collator`, `Intl.Segmenter`, and `toLocale{Lower,Upper}case` was kept distinct from stability and left to TG2.

The conclusion was that [PR #18](https://github.com/tc39/proposal-stable-formatting/pull/18) can be merged, the alias for `zxx` needs further consideration, and if `zxx` explicitly means "stable", another special locale identifier may be needed for the root locale.

## `Error.captureStackTrace()` for Stage 1

- wiki: [Error.captureStackTrace](../../proposals/error-capture-stack-trace.md)
- proposal: [proposal](https://github.com/mgaudet/proposal-error-capturestacktrace)
- slide: [link](https://docs.google.com/presentation/d/1SFdS9n5JR7Jqz29s7ApvkqDOqOfPW-IaBR2orK828As/edit?usp=sharing)

[MAG](../../people/MAG.md) (Matthew Gaudet, Mozilla) asked for Stage 1 to standardize `Error.captureStackTrace()`, a Chrome-only API since at least 2015 that JSC/WebKit shipped in August 2023 — with SpiderMonkey now implementing it to avoid a web interoperability split, which makes three engines and hence a spec. The method attaches the current stack to any object, with an optional `constructor` argument to elide frames above it. Implementations diverge: V8 installs a getter property, JSC defines a string-valued data property (SpiderMonkey is following JSC). [JHD](../../people/JHD.md) confirmed it does not touch internal slots, and [DE](../../people/DE.md) and [MM](../../people/MM.md) supported Stage 1.

The conclusion was Stage 1, with the summary noting most people would strongly prefer that it produces a data property and does not interfere with the `[[ErrorData]]` internal slot.

## Discussion about shipping non-standard features

[CDA](../../people/CDA.md) reopened a stifled discussion about implementers shipping non-standard features and notifying the committee. [JHD](../../people/JHD.md) proposed no process change, just a courtesy: drop a line on Reflector or Matrix before shipping non-standard stuff, since people here care. [DE](../../people/DE.md) called TypeScript's practice of explaining upcoming features to the committee a good model, stressing it must not become a time to object, and [SYG](../../people/SYG.md) reported V8 plans nothing new with observable behavior (parse hints, currently in origin trial, being the interesting exception), pointing to the Chrome and Mozilla release notes as the standing channel; [MLS](../../people/MLS.md) said Apple rarely ships non-standard features.

The conclusion was only a discussion: the committee prefers early notification (before or after shipping) of non-standard work, with no process change made.

## Error Stack Accessor

- wiki: [Error Stack Accessor](../../proposals/error-stack-accessor.md)
- proposal: [proposal](https://github.com/ljharb/proposal-error-stack-accessor)

[JHD](../../people/JHD.md) (Jordan Harband) split his decade-old error stack proposal in two and brought the piece that only standardizes what browsers already do: an accessor property `Error.prototype.stack` whose getter throws on non-objects, returns `undefined` off error objects for web compatibility, tolerates implementation-defined behavior, and whose setter throws on non-objects and otherwise sets a shadowing own data property — so borrowing the getter still reaches the original stack. [DLM](../../people/DLM.md) reported initial Firefox nightly telemetry as positive for web compatibility, [KG](../../people/KG.md) flagged that `DOMException`s (real errors now, with `[[ErrorData]]`) only sometimes have stacks and that `new DOMException` in Chrome would gain one, and [SYG](../../people/SYG.md) asked to work out the DOMException interaction in an HTML PR.

The conclusion was Stage 2, with [MF](../../people/MF.md) and [NRO](../../people/NRO.md) as spec reviewers, and the requirement that an HTML integration PR be directionally approved (and possibly merged) before Stage 2.7.

## Intl Locale Info API Update in Stage 3

- wiki: [Intl Locale Info](../../proposals/intl-locale-info.md)
- proposal: [proposal](https://github.com/tc39/proposal-intl-locale-info)
- slide: [link](https://docs.google.com/presentation/d/14ColNEWDFlAnPGW6GSPSk6gbcdTmSy4pYuYXOwDlZX8)

[SFC](../../people/SFC.md) (Shane Carr, Google), presenting for an unwell [FYT](../../people/FYT.md), recapped the proposal — additional `Locale` information derived purely from CLDR, such as week data for building calendar widgets — and sought consensus on normative PR 99, which settles week-numbering on the ISO 8601 algorithm in all cases. [MM](../../people/MM.md) contributed the naming suggestion that the relevant CLDR tables be called "WeekMap", which [SFC](../../people/SFC.md) happily took.

The conclusion was consensus on PR 99, with remaining open issues such as issue 76 (fallback behavior, which Mozilla has flagged as blocking) to be resolved before the proposal can advance.

## Stabilize integrity traits status update

- wiki: [Stabilize](../../proposals/stabilize.md)
- proposal: [proposal](https://github.com/tc39/proposal-stabilize)
- slide: [link](https://github.com/tc39/proposal-stabilize/blob/main/stabilize-talks/stabilize-stage1-status-update.pdf)

[MM](../../people/MM.md) (Mark Miller, Agoric) reported that non-extensible will not be unbundled, and the hope is to bundle the "fixed" trait into non-extensible, pending Google's usage counters. The override mistake may be fixed globally with narrow carve-outs for the legacy lodash pattern (via [JRL](../../people/JRL.md)), again pending browser measurement, possibly strict-mode only. [JHD](../../people/JHD.md) probed edge cases (a stabilized pending promise, built-ins writing `lastIndex`/length), which [MM](../../people/MM.md) took under advisement.

The conclusion was that if all this works out, only the "non-trapping" trait remains as the root trait — possibly renamed from "stabilize" back to "fixed" — addressing a major source of proxy re-entrancy hazards without threatening proxy transparency.

## Records and Tuples future directions

- wiki: [Records & Tuples](../../proposals/records-and-tuples.md)
- proposal: [proposal](https://github.com/tc39/proposal-record-tuple)
- slide: [link](https://docs.google.com/presentation/d/1uONn7T91lfZDV4frCsxpwd1QB_pU3P7F6V2j9jEPnA8/)

[ACE](../../people/ACE.md) (Ashley Claymore, Bloomberg) reopened the dormant [Records & Tuples](../../proposals/records-and-tuples.md) to explore a redesign, given implementer feedback against new primitives, interning, and deep-comparison `===`. [DE](../../people/DE.md) framed the new direction: shallowly immutable objects that are composite-key comparable from birth, so `Map`/`Set` can treat them as structurally equal without changing `===`. [KG](../../people/KG.md) (with [MF](../../people/MF.md)) was positive — [composite keys](../../proposals/composite-keys.md) working with `groupBy`/`Map`/`Set` is "the main thing that I personally want out of records and tuples". [JGT](../../people/JGT.md) and [JRL](../../people/JRL.md) discussed React use cases, [LCA](../../people/LCA.md) hoped [Temporal](../../proposals/temporal.md) types could opt in later, and [MAH](../../people/MAH.md) worried about old code that expects reference equality.

The conclusion was feedback generally positive to continue exploring this direction, with noted concern about complexity when existing code expects objects in a `Map` to use reference equality only.

## Use cases for ShadowRealm

- wiki: [ShadowRealm](../../proposals/shadowrealm.md)
- proposal: [proposal](https://github.com/tc39/proposal-shadowrealm)

[PFC](../../people/PFC.md) (Philip Chimento, Igalia) argued TC39 and the web platform mean different things by "use cases": per the W3C TAG, they must be framed from the end user's perspective, so he reframed [ShadowRealm](../../proposals/shadowrealm.md) around plugin isolation; [MM](../../people/MM.md) added supply-chain risk. [SYG](../../people/SYG.md) said the real bar is in WHATWG and browser buy-in beyond JS engines. [KG](../../people/KG.md) and [PFC](../../people/PFC.md) noted the requirement to include host APIs came from the committee itself ([MAH](../../people/MAH.md): "So we brought this on ourselves?"), and [JSL](../../people/JSL.md) advised agreeing on the problem statement with WHATWG first.

The conclusion was a shared understanding rather than a decision: the champions need to frame use cases in end-user terms for the web platform, and the Stage 3 blocker is web platform integration agreed in advance.
