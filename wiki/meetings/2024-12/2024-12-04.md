## Import Sync discussion, request for Stage 1?

- wiki: [Import Sync](../../proposals/import-sync.md)
- proposal: [proposal](https://github.com/guybedford/proposal-import-sync)
- slide: [link](https://docs.google.com/presentation/d/1GW_OCoVjd6OJi9BKSlQzQKqxrB0GUKHKFof4s3rn9yk/edit)

[GB](../../people/GB.md) presented the demand for synchronous module access that surfaced in Node PR #55730 (`import.meta.require`; Bun is today the only runtime with a syntactic `require` inside ESM) — warning that if TC39 ignores it, platforms will keep inventing importers with divergent semantics. Use cases: synchronous access to built-ins, conditional loading, reaching dependencies already in the registry, and a sync executor for module virtualization, expressions and declarations. What changed to make this discussable at all: module resolution is now fully synchronous on all platforms, and [import defer](../../proposals/import-defer.md) already layered the needed semantics on top of the async baseline. The sketched design, `import.sync`, would have roughly `import defer` semantics (throwing a "not available synchronously" error where loading would be needed); [ACE](../../people/ACE.md) pushed back that defer's existence is no free pass — Bloomberg has been working to remove exactly these assumptions-about-what-else-has-loaded; [SYG](../../people/SYG.md) was concerned about threading a new sync path through the module machinery and browser/server divergence ("let my crankiness be noted in the notes"), while [JSL](../../people/JSL.md) would rather standardize the thing than chase Node's extension, and [JHD](../../people/JHD.md) suggested revisiting the old conditional-import idea. [GB](../../people/GB.md) reframed the ask as Stage 1 for the **problem space** (optional dependencies, sync execution, conditional loading), not the `import.sync` design.

The conclusion was Stage 1 for exploring the sync-import problem space (support from [MM](../../people/MM.md), [JWK](../../people/JWK.md), [KKL](../../people/KKL.md); [SYG](../../people/SYG.md) explicitly noting no current path to Stage 2), with [MM](../../people/MM.md) asking that it be coordinated with XS's `importNow`.

## ESM phase imports for Stage 2.7

- wiki: [ESM Phase Imports](../../proposals/esm-phase-imports.md)
- proposal: [proposal](https://github.com/tc39/proposal-esm-phase-imports)
- slide: [link](https://docs.google.com/presentation/d/1qfnmqPkpuAqTv-1pll1Y6EkEHElf_58BtNBQSw9dpq8/edit#slide=id.g305421a9f36_0_11)

[GB](../../people/GB.md) reported on the four investigations identified at Stage 2, the proposal now defining a JS `ModuleSource` in ECMA-262 (the primitive for module expressions/declarations, motivating `new Worker(source)`). Cross-spec: presented at the HTML whatwg meeting (2024-10) and WebAssembly CG with interest and no negative concerns; a draft HTML PR proves out worker substantiation (with import-map cloning defaults), to be filed only after Stage 3. Keying: the primary key is URL+attributes (parent-relative for declarations/expressions) with the immutable source text as a secondary key — importing a source always returns an instance of **that** source, so same-key/different-source gets a second registry entry, and eval-ish sources get a fresh eval key on every serialization ([MM](../../people/MM.md) probed the resulting incoherence of locally-canonical but per-transfer-unique instances; [GB](../../people/GB.md): cross-agent key synchronization was ruled out as too costly). The source/instance ModuleRecord refactor is postponed — observable semantics are maintained via inaccessible "ghost" instances ([MM](../../people/MM.md) satisfied the semantics are consistent though he believes the refactored spec would be simpler; [NRO](../../people/NRO.md) agreed — "the refactoring makes everything much easier to read. But it's a lot of work"). The compartments deep-dive introduced per-compartment canonical instances via a compartment key on `ModuleInstance`, with [KKL](../../people/KKL.md) generalizing it to "cohorts" (shared-struct prototype registries are the same concept) and predicting the ModuleInstance constructor simplifies into options on the ModuleSource constructor. On process, [SYG](../../people/SYG.md) asked that cross-spec advancement move in lockstep (an explicit WHATWG signal of intent would be the clean future mechanism) and [DLM](../../people/DLM.md) confirmed 2.7 is a fine time to resolve cross-spec issues per the ShadowRealm precedent.

The conclusion was Stage 2.7 by conditional consensus — [MM](../../people/MM.md) objects for now only on time-to-review grounds and will approve asynchronously after TG3 weekly discussions before the next plenary (any needed tweaks come back to the committee, per [NRO](../../people/NRO.md)/[DE](../../people/DE.md)); [JHD](../../people/JHD.md) asked for a tracking issue in the repo to record the approval.
