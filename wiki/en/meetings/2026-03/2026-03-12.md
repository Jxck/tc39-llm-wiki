# 2026-03-12 (113th TC39 Meeting, Day 3)

## First-class Protocols Update (continuation)

- slide: [link](https://tc39.es/proposal-first-class-protocols/slides/2026-03/)
- [LVU](../../people/LVU.md) walked through the previous day's presentation again and confirmed the current design (members are declared explicitly with `requires`, an external Symbol can also be used as a computed property name, and a protocol is immutable) and the open questions.
- [EAO](../../people/EAO.md) asked about turning it into multiple inheritance for classes. The champions were negative: a protocol does not use the prototype chain and instead copies members, and that is the territory of the mix-ins proposal.
- Against the Symbol-first design, [PFC](../../people/PFC.md) / [EAO](../../people/EAO.md) were concerned that "it looks like a string key but it is a Symbol" is counterintuitive. [SFC](../../people/SFC.md) was skeptical of Symbol-first because many existing protocols are string-based. [RBN](../../people/RBN.md) suggested a C#-style `extends ParentClass, ProtocolA, ...` notation.
- The name stays `protocol`, because the TypeScript team has opposed calling it `interface`.
- Conclusion: no stage transition. It stayed at collecting feedback to firm up the design toward Stage 2.

## test262 coverage strategies

- The problem raised: test262 does not cover the branches of built-in algorithms well enough (especially the order in which input-validation steps run), and the existing tests are cumbersome.
- [RGN](../../people/RGN.md) presented a proof of concept that relaxes inputs which cause an abrupt completion, from early to late, and tried efficient branch coverage with proxy-based probing.
- The discussion also included doing it by code generation rather than dynamic evaluation, but a concern was raised that contribution and review against test262 would become high-friction.
- It was pointed out that proxy-based probing avoids optimizations, so coverage of the non-proxy path may also be needed separately.
- Conclusion: further progress will take the form of test262 PRs (a direction that gathers the throw-style tests per top-level algorithm).

## TypedArray concat

- slide: [link](https://github.com/tc39/proposal-typedarray-concat/blob/tc39-plenary-march-2026/slides-export.pdf)
- [JSL](../../people/JSL.md) did not ask to advance the stage, and took the committee's temperature on whether to support iterables. They said the name is leaning away from `concat` toward a `from list` style.
- Iterables add a lot of complexity: they have to be fully consumed, and a type mismatch has to coerce or throw. [RGN](../../people/RGN.md) / [PHE](../../people/PHE.md) said existing ecosystem use cases (Node's buffer concat, and others) do not need it.
- [MF](../../people/MF.md) said "iterables and array-likes are being considered for the same reason (convenience), so the yes or no should match," and agreed to leave them out after [JSL](../../people/JSL.md) explained that the first version is TypedArray and ArrayBuffer only. [KM](../../people/KM.md) strongly wanted no support for `Symbol.isConcatSpreadable`.
- Conclusion: iterables are not adopted. The function name will change from `concat`. The ask to advance the stage carries to May.

## Tree-shakeable methods

- slide: [link](https://docs.google.com/presentation/d/1zy10o54PMuh2c9Liz6RH5R3bnBpe-3-sy0uEXbACzjQ/edit?usp=sharing)
- EBW (presenter Evan B. Winslow) raised the scale of dead code shipped on the web. Methods get in the way of tree-shaking, but they are convenient, so they get used.
- Bikeshedding a concrete syntax was a non-goal. The presentation aimed at agreeing that the problem space is worth solving.
- Conclusion: several proposals were named that could help in this area, including protocols, call-this, pipeline, extensions, and a new idea of deferring code inside an async function.
- There were also several voices that expect a linter- or bundler-based solution more than a syntax-based one, and more discussion is needed to explore the design space.

## TypedArray findWithin continuation

- slide: [link](https://github.com/tc39/proposal-typedarray-findwithin/blob/tc39-plenary-march-2026/slides-export.pdf)
- As with concat, [JSL](../../people/JSL.md) did not ask for a stage, and reported removing `contains` and removing iterable support (following the concat precedent).
- The open question is the name of the new function, or whether overloading `indexOf` / `lastIndexOf` is enough. With no iterable support there is no coercion, so the only behavior change is that passing a TypedArray returns an index rather than the traditional `-1`.
- [KG](../../people/KG.md) / [MF](../../people/MF.md) supported the overload (Node's buffer indexOf is a long precedent). [RGN](../../people/RGN.md) / [NRO](../../people/NRO.md) were concerned about backward-compatibility risk at web scale, wanted a dedicated method, and argued that a use counter should be put in browsers at Stage 2 to check.
- Conclusion: iterables are not adopted, as with concat. Overload versus a new function was not settled; the committee leans toward a new function. It will be brought back in May.

## Thenable Curtailment for Stage 2

- wiki: [Thenable Curtailment](../../proposals/thenable-curtailment.md)
- slide: [link](https://docs.google.com/presentation/d/1i0jY_e-A3rkd9256VzirJdPVtHInYNGjtYq_KrTBMuo/edit)
- A response to the problem that a thenable with any `then` property is special-cased in promise resolution and keeps causing security bugs. [MAG](../../people/MAG.md) proposed 'Safe Resolve' (name not fixed), which delays resolution by one tick only when user code might run.
- As an experiment, every C++ promise resolution was put through this path and the web platform tests were run. Almost all passed (the failures are the kind that observe resolution timing, and can be removed or adjusted). Web compatibility looks likely.
- Open questions: whether to expose it to userland, and the name. [MM](../../people/MM.md) presented a rewrite that does not introduce a new state and instead forwards to a spec-internal promise. [KG](../../people/KG.md) offered switching the safe-resolve behavior with a second argument to the resolve function. [MF](../../people/MF.md) was also interested in exposing a predicate.
- Conclusion: reached Stage 2 (support from [KG](../../people/KG.md) / [PFC](../../people/PFC.md) and others; no objection). [MAG](../../people/MAG.md) will keep looking at userland exposure (probably through a second argument to the resolve function).

## Iterator Includes

- wiki: [Iterator Includes](../../proposals/iterator-includes.md)
- The spec text of `iterator.includes`, approved just before, has a bug: passing a non-integer as the second argument throws without closing the receiver. A PR fixing that was presented.
- The fix is that it was not following the convention that an iterator should be closed even on a consumer-side error state (including an invalid argument).
- Conclusion: the PR was approved (several approvals, no objection).

## Towards Structured Concurrency

- slide: [link](https://docs.google.com/presentation/d/1vYh__pmW0QuIhxz9jPQbUXdkIrzD5p7Wjl6oTdKSBZI/edit?usp=sharing)
- Not a concrete proposal. A vision of a direction the language could go. [KG](../../people/KG.md) introduced structured concurrency (bind concurrency to a scope; the scope does not exit until child tasks complete or shut down; an error in one task cancels the others).
- It is an idea of about ten years, by analogy with structured programming. Other languages have moved the discussion along, but TC39 has barely taken it up.
- Conclusion: broad support from the committee for a direction that stacks extensions which can be motivated independently of AbortController / AbortSignal, and that uses the new `using` syntax heavily to build a path toward structured concurrency. Safari commits only to AbortController-based cancellation and will not introduce another kind of cancellation.
