# 2026-03-10 (113th TC39 Meeting, Day 1)

## import defer interaction with tc39/ecma262#3715, and normative PR Shield dynamic import defer against `Promise.prototype` monkey patch

- slide: [link](https://docs.google.com/presentation/d/1T1M7X-cS_ODKOl6Nsq-_YmHusVoD6bPtAS_MHzxzgTw)
- Two normative PRs for import defer were presented. The first closes a leak: dynamic import defer uses `PerformPromiseAll` to wait on async dependencies, so monkey-patching `Promise.prototype.then` can observe a spec-internal top-level capability promise. The change does not call `then` and instead uses built-in steps equivalent to PerformPromiseThen (found while implementing it in V8).
- The second fixes a problem that appears when this is combined with the namespace re-export normative PR already agreed in ECMA-262: a re-export of a deferred namespace was incorrectly made eager. The fix propagates the phase correctly.
- [KG](../../people/KG.md) supported both strongly, and said they would like to generalize it if possible, but that it should move forward even piecemeal.
- Conclusion: both changes reached consensus.

## Abort Protocol Discussion

- slide: [link](https://github.com/jasnell/discussion-abort-protocol/blob/main/slides-export.pdf)
- [JSL](../../people/JSL.md) raised whether abort / cancellation should enter the language. The ecosystem has converged on WHATWG's AbortController / AbortSignal, but that is not a language feature and some environments do not have it. The ask was for the language to have abort signaling that can satisfy the existing solution with a minimal change (a discussion to confirm agreement, not a proposal).
- [MM](../../people/MM.md) likened a synchronous callback to a Unix signal handler and treated it as dangerous, recommending a bit check at a safe point. [KG](../../people/KG.md) replied that it has not been a real problem on the web for nearly ten years. [JHD](../../people/JHD.md) questioned whether AbortSignal is the best and said it should be generalized as "task cancellation."
- [RBN](../../people/RBN.md) shared the history of a past cancellation proposal (it stalled because coordination with WHATWG was hard) and listed places where cancellation would be useful: `import()` calls, `then` continuations, shared structs. Design issues (synchronous callbacks, combinators, alignment with AbortSignal) stay under discussion.
- Conclusion: broad agreement that it should enter the language. [JSL](../../people/JSL.md) will join the champions of the existing older cancellation proposal, rather than start a new one, and restart it.

## TypedArray concat for Stage 2

- slide: [link](https://github.com/tc39/proposal-typedarray-concat/blob/tc39-plenary-march-2026/slides-export.pdf)
- Stage 2 ask for a proposal that gives TypedArray / ArrayBuffer / SharedArrayBuffer a static concat method that can be optimized. The argument is an iterable, length may be omitted (truncate / zero-fill), and an options bag specifies resizable / immutable.
- Issues: the name (`concat` collides with String, Node Buffer, and `Iterator.concat`; `fromChunks` / `concatFrom` and others were considered), and the order of consuming the iterable (consume everything and then validate, or validate while copying; this affects observability).
- [DLM](../../people/DLM.md) blocked the current problem statement. The blocking concern is that the only implementation optimization is a rope-like structure, and TypedArray / ArrayBuffer should stay linear. [KM](../../people/KM.md) also opposed ropes (they expect O(1) access). There was no opposition to a concat whose purpose is ergonomics, but the wording of the problem statement is the problem.
- Conclusion: objection to the wording of the problem statement. [JSL](../../people/JSL.md) will revise the wording and ask for Stage 2 again on Day 3.

## RegExp Buffer Boundaries for Stage 2.7

- wiki: [RegExp Buffer Boundaries](../../proposals/regexp-buffer-boundaries.md)
- slide: [link](https://1drv.ms/p/c/934f1675ed4c1638/IQCTgpGYlj_dTblwh8sK7M9HAQRbd5eUz4b_XF4t1rxe_38?e=TDhJ9C)
- A proposal that introduces `\A` / `\z` zero-width assertions, which match the start or end of the input regardless of multiline mode (requires the `u` / `v` flag). Because of progress on RegExp Modifiers, the semantics are already in the language. It is syntactic sugar that provides the same syntax as other languages (PCRE and eight or more others), to improve portability and reuse of regexes generated by an LLM.
- `\Z`, which includes a trailing newline, was removed once at Stage 2, with room to consider adding it later for linters and TextMate grammars. The spec is simple, and test262 and engine262 implementation PRs have been filed.
- [DLM](../../people/DLM.md) blocked it: it was a late addition to the agenda, and the team's regex experts had not had time to review. [OFR](../../people/OFR.md) followed, and said pressure should not be put on additions past the deadline. [WH](../../people/WH.md), as a reviewer, said there was no problem.
- Conclusion: advancement was blocked for lack of review time (to be resubmitted in May).

## Amount for Stage 2

- wiki: [Amount](../../proposals/amount.md)
- slide: [link](https://docs.google.com/presentation/d/1SAD0bgB_SOWrtz1YZuySC4YHdMxBs0vTnS7buQa311c/edit?slide=id.g3cb9b164150_1_50#slide=id.g3cb9b164150_1_50)
- Stage 2 ask for [Amount](../../proposals/amount.md), which attaches a unit to a number (marked with an asterisk). The design was refreshed from the old mathematical value to one that holds a number, bigint, or decimal string depending on the input type. Unit conversion was reintroduced with CLDR's units.xml as a normative reference, and the API was greatly simplified (`.with()` and the fraction / significant-digits accessors were removed). Arithmetic is done in number space and relies on 402's FormatNumericToString.
- [WH](../../people/WH.md) raised, as blocking-level concerns, a procedural problem (the proposal spec was swapped three hours before the meeting and could not be reviewed) plus (1) a localization error that returns 2m as 79 inches for a US person height (a mixed unit "foot+inch" is needed), and (2) an exact-conversion error where multiple rounding of 7 feet → inches becomes 83 inches on truncate. They emphasized that the cause is multiple rounding, not the choice of double versus decimal.
- Discussion of preserving conversion precision ([JRL](../../people/JRL.md): "increasing precision after an infinite-precision conversion is wrong"). Implementers ([OFR](../../people/OFR.md) and [DLM](../../people/DLM.md)) supported conversion in number space.
- Conclusion: Stage 2 was not asked this time. The plan is to keep working on the rounding problem with [WH](../../people/WH.md) and ask for Stage 2 in May.

## Intl: Keep Trailing Zeros for Stage 3

- slide: [link](https://docs.google.com/presentation/d/13zyaDAuriW2A4pwzklf0EZhOSUUmWqZxyIjzCcjWkXU/edit?usp=sharing)
- A Stage 2.7 proposal that fixes the current behavior in which `Intl.NumberFormat` / `Intl.PluralRules` ignore trailing zeros of a digit-string input. The new option value `trailingZeroDisplay: "stripToMinimum"` can still select the old behavior. Behavior for number / bigint input is unchanged.
- Two remaining issues were discussed. #15: whether a very small value (for example `"1.2e-10"` with maxFractionDigits 5) should currently become `"0.0"`. [NRO](../../people/NRO.md) said `0.0` is the worst (it suggests wrong significant digits) and supported a bottom output (following maxFractionDigits) or a plain `0`. #17: trailing zeros of an integer (`"700"` → `7.00E2` or `7E2`). [NRO](../../people/NRO.md) and [SFC](../../people/SFC.md) supported `7.00E2` (3 significant digits). [WH](../../people/WH.md) preferred `7E2`.
- [EAO](../../people/EAO.md) planned not to ask for Stage 3 this time, because of the amount of spec-text change.
- Conclusion: #15 is resolved in the direction of changing the behavior. #17 keeps the current behavior (trailing zeros of an integer stay significant). Advancement goes to a future meeting.

## `JSON.parseImmutable` update

- slide: [link](https://docs.google.com/presentation/d/1NXb3HWjt0BiVJl2SZlAVeSvZIBlzO1z9X28hJL28w7s)
- With [Records & Tuples](../../proposals/records-and-tuples.md) withdrawn, the path of `JSON.parseImmutable`, which was tied to it, was discussed. The options were (1) withdraw, (2) return composites, (3) return a plain object / array that is deeply `Object.freeze`d (the champions' preference).
- [MF](../../people/MF.md), [JHD](../../people/JHD.md), and [ACE](../../people/ACE.md) said composites are unsuitable (the use is centered on keys and is not data-oriented, there is no tuple equivalent, and a JSON array cannot be handled). [MM](../../people/MM.md) cited the advantage of composites for safety across realms, while reserving judgment. They pointed out that a frozen object can leak a realm because it inherits `Object.prototype`.
- [NRO](../../people/NRO.md) and [JSC](../../people/JSC.md) suggested renaming to `parseFrozen` or similar if it returns frozen. [MM](../../people/MM.md)'s idea of not needing a reviver was withdrawn because [KG](../../people/KG.md) said parse-with-source-text assumes a reviver. [KG](../../people/KG.md) offered an options-bag plan instead of a different name.
- Conclusion: the sense was that it is still useful after the [Records & Tuples](../../proposals/records-and-tuples.md) withdrawal, in the direction of option 3 (deeply frozen). The name, reviver behavior, and whether it must be sent back to Stage 1 are undecided (continuing offline).

## TypedArray find within for Stage 2

- slide: [link](https://github.com/tc39/proposal-typedarray-findwithin/blob/tc39-plenary-march-2026/slides-export.pdf)
- Stage 2 ask for a proposal that searches for a subsequence inside a TypedArray. Currently three methods, `search` / `searchLast` / `contains`. The needle is a TypedArray or an iterable (a string throws).
- [WH](../../people/WH.md) pointed out a footgun: an iterable needle silently fails to find a type mismatch (for example a 64-bit int array with a number needle, or a Float32Array searched with `1.1`), and said the needle should be coerced to the haystack type. [KM](../../people/KM.md) pointed out that an iterable is actually more expensive because of a per-element object allocation. [KG](../../people/KG.md) agreed with a plan to remove the iterable argument for now.
- Discussion of the argument that `contains` is unnecessary (replaceable by `search` returning -1, and the name is misleading), of throw versus -1 on the wrong type, and of whether SharedArrayBuffer can be supported (whether a needle snapshot is needed). [RBN](../../people/RBN.md) / [RGN](../../people/RGN.md) were on the -1 side, and it was settled that the SAB footgun is already tolerated.
- Conclusion: it did not reach Stage 2 (changes are needed: remove `contains`, remove the iterable needle, and for SAB hold it without a snapshot). On [MF](../../people/MF.md)'s suggestion, the plan is not a conditional advance but to ask again in Day 3's overflow slot (continued to Day 3).

## Iterator Includes for Stage 1, 2, or 2.7

- wiki: [Iterator Includes](../../proposals/iterator-includes.md)
- slide: [link](https://docs.google.com/presentation/d/1a-1RQayP-tcJd2VAhFGoiL_dRT8gD8_qrp__qSgC1A4)
- A new proposal for `Iterator.prototype.includes`, which checks whether an iterable contains a value (the same motivation as `Array.prototype.includes`, plus a JS-specific motivation that a SameValueZero comparison is hard to write by hand). [KG](../../people/KG.md) redefined it as "a feature you want on iterables such as Map, FormData, and NodeList, not on iterator," which helped understanding.
- The design follows Array (the name `includes`, SameValueZero, a second argument for how many to skip). The second argument can be replaced with `drop`, but it was kept in the end because of compatibility with Array and because forbidding a negative index already diverges. NaN, a negative, and a non-integer throw.
- [EAO](../../people/EAO.md)'s idea of Python-style `in` syntax was rejected by [KG](../../people/KG.md) and [MF](../../people/MF.md): "the meaning of the existing `in` operator cannot be changed, and it would slow down every `in`." Support for composites follows equality on the composites proposal side ([ACE](../../people/ACE.md): if they are interned, no extra spec is needed).
- Conclusion: it obtained Stage 1 and 2, and with sign-off from reviewers ([RGN](../../people/RGN.md) and others) and editors ([JHD](../../people/JHD.md) and [RBN](../../people/RBN.md)) it advanced through to Stage 2.7.
