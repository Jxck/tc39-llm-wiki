# 2025-11-19 (Day Two)

## Async iterator helpers recap/update/polyfill

Kevin Gibbons ([KG](../../people/KG.md)) recapped the implementation status of async iterator helpers (`AsyncIterator.prototype.map` and others) and of the sync iterator helpers. He shared polyfill availability, progress in each engine, and how previously noted spec edge cases (early return and error propagation) had been handled. The session was mainly a status update. There was no request to advance a stage.

## Iterator Join for stage 1, 2, or 2.7

- wiki: [Iterator Join](../../proposals/iterator-join.md)

A proposal for `Iterator.prototype.join()`, which concatenates an iterator's elements with a separator. It gives iterators the equivalent of `Array.prototype.join`, and advancing to Stage 2.7 was on the agenda. There were questions about the API design and about behavior on an infinite iterator, and it was broadly supported.

Conclusion: advancement to Stage 2.7 was approved.

## Composites comparator choice

Led by Ashley Claymore ([ACE](../../people/ACE.md)), the committee discussed how to choose a comparator for Composites (values with structural equality). Two TCQ temperature checks covered design choices such as how to intern values, and whether inserting into a leaked WeakMap should throw. Both supported interning, and supported throwing when inserting into a leaked WeakMap. There was no formal request to advance a stage. The session confirmed a design direction.

## Concurrency Control stage 1 update

A Stage 1 progress report on a proposal to bring concurrency control (something like locks and semaphores) into JavaScript. Use cases were organized, and the relationship to existing related specs such as the Web Locks API was explained. Feedback from the committee was requested on the design direction from here. There was no request to advance, and it continues at Stage 1.

## `Object.propertyCount` for Stage 2

A proposal for `Object.propertyCount`, which returns the number of enumerable properties of an object, and `Object.keysLength`, which returns only the number of string keys. The discussion settled on splitting the two APIs, and only `Object.keysLength` was supported for Stage 2. `Object.propertyCount` stays at Stage 1 because spec-design concerns remain (interaction with Proxy and with the receiver).

Conclusion: `Object.keysLength` advanced to Stage 2, and `Object.propertyCount` continues at Stage 1.

## WHATWG Stages

A discussion of how to apply TC39's stage concept, and of the coordination process, for specification proposals defined by other standards bodies such as WHATWG. The substance was procedural cleanup for managing proposals across organizations. It did not advance any particular proposal.

## Spec-defined or Implementation-defined limits

A policy discussion of whether various limits in the ECMAScript specification (string length, array length, and so on) should be defined by the spec or left implementation-defined. Differences between existing implementations, and interoperability problems, were shared, and the committee was asked how much of that range should be written into the spec from here. There was no concrete stage advance and no normative PR.

## Module-declaration like proposals in other areas of the web

A policy discussion of how syntax patterns similar to module declarations (`import` / `export`) should be treated in other parts of the web (extensions of HTML `<script type=module>`, CSS `@import`, and so on). The point was keeping the syntax TC39 defines consistent with other bodies' specifications. No stage decision was made for a particular proposal.

## Comparisons

- wiki: [Comparisons](../../proposals/comparisons.md)

A progress report on a proposal for comparing values (a deep comparison that extends something like `Object.is`). Several API-design options were discussed, but the committee did not reach agreement, and the plan is to keep working on the design at Stage 0.

Conclusion: no stage advance. It continues at Stage 0.
