## `Object.propertyCount` for Stage 2

RBR brought back `Object.propertyCount`, which had been agreed at Stage 1 last time, with the scope reduced by splitting out pieces such as obtaining non-index string properties and detecting a sparse array into separate proposals. The committee tangled on the design of a three-state option (enumerable / non-enumerable / all) and on the API shape (an options bag or separate methods). [KG](../../people/KG.md), [MF](../../people/MF.md), and others were skeptical of adding a new API to fill out the existing system of `Object.keys` / `getOwnPropertyNames`. [MM](../../people/MM.md) further argued that this proposal is tightly related to the following three (`Array.isSparse`, `Array.getNonIndexStringProperties`, and `Object.getOwnPropertySymbols` options), that the four should be considered as one, and asked to postpone the discussion.

### Conclusion

[MM](../../people/MM.md) and [KG](../../people/KG.md) objected to advancement to Stage 2, and it did not advance. Too many APIs across the four proposals, and overlap of the problem areas, remained the main concerns.

## `Array.isSparse` for Stage 1

RBR proposed `Array.isSparse` (or `isDense`), which tells whether an array is sparse (has holes), as Stage 1. The motivation was correctness and performance (as with `Object.keys().length`, inefficient hole checks are done in places such as Node.js's `assert` implementation). Implementers ([KM](../../people/KM.md), [OFR](../../people/OFR.md)) pointed out that in V8 it can be O(1) in some cases, but in JSC it is always O(n), and a strong concern was raised about exposing non-deterministic performance that depends on the engine. [WH](../../people/WH.md) pointed out a polarity problem of the API: "even if it returns false, that does not guarantee there are no holes (considering array-likes, it becomes three-valued)." Renaming to `isDense`, and problems of proxies and of shape changes (the internal representation does not change even if it is densified), were also discussed.

### Conclusion

[WH](../../people/WH.md) and [KM](../../people/KM.md) questioned whether a solution even exists in the problem space, and objected. There was support from [ZTZ](../../people/ZTZ.md), [OFR](../../people/OFR.md), and others, but it did not advance to Stage 1. It was said that there is a path to propose it again if a persuasive problem statement comes with benchmarks and similar.

## `Array.getNonIndexStringProperties` for Stage 1

- slide: [link](https://github.com/BridgeAR/array-get-non-index-string-properties/blob/main/slides/07.2025%20-%20proposal-slides.pdf)

RBR proposed, as Stage 1, a helper that obtains the non-index string properties on an array or TypedArray (for example `index`, `groups`, and others attached to the array that a regexp `match` / `matchAll` returns). [MM](../../people/MM.md) supported it as a strong motivation that, because the current spec enumerates index properties first, there is no way to obtain only the non-index properties, and proposed including non-enumerable ones, not only enumerable. Whether to limit it to arrays or generalize it toward `Reflect.ownKeys`, and support for proxies and array-likes, were sorted out as issues for Stage 2 and later.

### Conclusion

There was strong support from [MM](../../people/MM.md), [NRO](../../people/NRO.md), [USA](../../people/USA.md), and others, and it reached Stage 1 with no objection.

## `Object.getOwnPropertySymbols` options for Stage 1

- slide: [link](https://github.com/BridgeAR/object-get-own-property-symbols-options/blob/main/slides/07.2025%20-%20proposal-slides.pdf)

RBR proposed adding an enumerable-filter option to `Object.getOwnPropertySymbols`. Most symbol-keyed properties are non-enumerable and used for hiding, so the motivation is to avoid the overhead of the caller checking enumerability one by one. [KG](../../people/KG.md) and [KM](../../people/KM.md) argued strongly that it should be a dedicated method that fills the matrix of the existing `Object.keys` / `getOwnPropertyNames` / `getOwnPropertySymbols`, not an options bag. [MM](../../people/MM.md) was concerned about the whole API growing, and restated the position that the four proposals should be reconsidered as one problem.

### Conclusion

There was broad support from [KG](../../people/KG.md), [KM](../../people/KM.md), [MF](../../people/MF.md), [MM](../../people/MM.md), and others, and it reached Stage 1 with no objection ([KG](../../people/KG.md) disliked the name while agreeing with the problem area itself).
